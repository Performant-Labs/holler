## Known flaky test — read before touching CI

**`roster_stays_accurate_under_concurrent_body_load`**
(`crates/holler-cli/tests/load_roster_scale_test.rs`) is genuinely
unresolved. Timeline, so the history isn't re-litigated:

1. Original CI margin (150s) was too tight under real shared-runner
   contention — fixed in #311 by widening to 240s. Insufficient.
2. Root cause diagnosed with Grok's help as GitHub-hosted `ubuntu-latest`/
   `macos-latest` being historically ~2-vCPU shared runners, and the test's
   warm-up phase firing every peer's first `say` as one simultaneous burst
   — exactly the shape that starves a small scheduler regardless of
   timeout. Fixed in #313: `PEER_COUNT` 12→8, staggered warm-up starts.
   **This fix passed clean on its own PR run.**
3. Despite that, it has since failed intermittently again — including
   **once on a genuine self-hosted Uranus runner**, not just GitHub-hosted,
   which is a real, only-partially-understood signal that the fix is not
   fully sufficient under heavy concurrent load, not just a GitHub-hosted
   problem.
4. As of this session's end, it is the single most disruptive flake in the
   suite. It has no self-hosted macOS fallback (macOS CI has no self-hosted
   equivalent — see "CI infrastructure" below), so macOS will always be
   exposed to whatever GitHub-hosted contention exists that day.

**If this keeps blocking PRs:** the two real options are (a) reduce
`PEER_COUNT` further and re-verify, or (b) accept it as a documented,
pre-approved-to-rerun flake and stop trying to make it deterministic on
shared hosted runners. Do not keep widening the timeout — that was already
tried and shown insufficient.

## CI infrastructure — what changed this session

non-fork) runs to a self-hosted fleet on **Uranus** (4 runners) and

## Not yet started — filed, deliberately deferred

Three related security-hardening issues came out of comparing Holler's
pairing/transport story against iTerm2's Buddy pairing system (researched
via Grok). All are real, all are cheap **now** and expensive **after**
v0.1.0 ships with paired bodies in the field — but none are urgent, and
none should be started without discussing sequencing with the operator
first.

- **[#322](https://github.com/Performant-Labs/holler/issues/322)** — give
  the hub a long-lived X25519 keypair; carry its public half in the
  `hub token mint` join line; `body join` pins it (hard failure on
  mismatch, never trust-on-first-use). Closes the gap where the hub has no
  identity beyond whatever certificate the reverse proxy happens to
  present.
- **[#323](https://github.com/Performant-Labs/holler/issues/323)** —
  replace the bearer credential in `circuit/authenticate` with a
  transcript-bound signature challenge, so no long-lived secret crosses
  the wire on every reconnect. Depends on #322 (needs a body keypair too).
  Also simplifies ADR 0008: the hub's store would hold public keys, not
  HMAC digests of a shared secret.
- **[#321](https://github.com/Performant-Labs/holler/issues/321)** — the
  larger future design #322/#323 are the pre-message/identity layer for:
  a full Noise XK handshake, replay-bound transcripts, a pairing SAS, and
  *conditional* appendices for a rendezvous relay and push notifications
  (both explicitly gated on "don't build until X happens" triggers — no
  relay-capable user or mobile surface exists yet). Filed as a design
  capture, not scheduled work.

**#322 and #323 are one wire break** (join-line format and
`circuit/authenticate`'s payload both change) — if either is picked up,
do both together, before v0.1.0 (#319) cuts a release. After that point the
same change requires a hard re-pair of every body in the field.

## Gotchas for whoever picks this up

- **Don't trust a subagent's "I'll wait for the notification" as real
  progress.** A dispatched background agent's turn ending is terminal —
  it cannot actually wait for anything. Multiple times this session an
  agent reported "waiting on CI" after its own turn had already ended;
  always re-verify directly against `gh pr checks`/`gh run view` rather
  than trusting that claim.
- **Rebasing a PR onto `main` before a self-hosted-routing PR merges
  doesn't pick up that routing.** Bit us once (#310) — a rebase timed
  right before #312 merged still ran on GitHub-hosted, not self-hosted,
  because the workflow file it inherited predated the change. If a PR's
  CI seems to be running on the wrong runner, check `git log` on its
  branch against when the routing change actually merged, not just
  whether a rebase happened.
- **The org-wide CI contention this session was unusually bad** because
  many PRs' CI was running back-to-back for hours. If CI looks flaky in
  a way that doesn't match the "known flakes" list above, check whether
  it's just a quieter night now — the same test that failed 3/3 times
  this session might pass cleanly under normal load.
