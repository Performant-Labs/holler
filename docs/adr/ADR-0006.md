# ADR 0006 — v1 deployment: loopback `ws` behind a TLS-terminating proxy; a tailnet is the supported path

**Status:** accepted
**Issue:** #7
**Date:** 2026-09-08
**Depends on:** [ADR 0004](https://github.com/Performant-Labs/holler/issues/5)
**Supersedes:** holler-server ADR-0004's "any underlay *may* make the TCP path exist" stance and ADR-0010's Tailscale paragraph (their technical claims are kept). **Executes:** holler-server#313, #314; defers holler-server#205 (native TLS) to v2.
**Amended:** 2026-09-11 — added point 6 and its consequence, making explicit the trust boundary that points 1–5 only implied. Clarification of an existing decision; nothing in points 1–5 changes.

## Decision

1. The hub binds **loopback `ws` only**. Any non-loopback exposure is a **reverse proxy** that terminates TLS 1.3 and forwards the WebSocket upgrade to `ws://127.0.0.1:41807`. This is compliant with the loopback-only rule because the proxy→hub hop is loopback.
2. **The supported v1 path is a Tailscale tailnet**: `tailscale serve --bg 41807` on the hub machine (HTTPS certs + MagicDNS enabled in the admin console). Bodies dial `wss://<hub>.<tailnet>.ts.net`. The Let's Encrypt certificate validates against the OS trust store the body already uses (`rustls-tls-native-roots`) — zero cert distribution. Any other proxy (Caddy, Traefik, nginx) is equally acceptable and documented.
3. **Native TLS in the hub** (`--tls-cert`/`--tls-key`, X25519MLKEM768 preference) is **v2** — tracked, not required.
4. Tailscale is an **underlay and a proxy, never identity**: `circuit/join` with a minted token is still required; a tailnet IP is never trusted as auth; Holler never calls Tailscale.
5. **Rebuttal to "a third party is now in the middle"** (for the README, verbatim): TLS terminates on *your* hub machine with a private key that never leaves it; Tailscale sees no frame content; direct peers stay LAN-direct; DERP only ever carries encrypted WireGuard if a direct path fails. The dependency is on certificate issuance and DNS, not on your data.
6. **The proxy is inside the hub's trust boundary — it must be a machine you control.** Because TLS terminates at the proxy and the proxy→hub hop is plaintext `ws` on loopback (point 1), the proxy sees **every frame in the clear**: `circuit/join`'s join secret and `circuit/authenticate`'s credential ([ADR 0007](ADR-0007.md)), and every prompt and reply. The supported path is safe by construction because `tailscale serve` runs **on the hub machine itself** — "the proxy" and "the hub" are one trust domain, which is exactly what makes point 5's rebuttal true. That property does not survive moving the proxy elsewhere: terminating Holler's TLS on a host you do not control — a shared ingress, a managed load balancer, a third-party edge — hands that operator your credentials and your conversations. Point 2's "any other proxy is equally acceptable" is therefore conditional on the proxy being **yours**, not merely on it being correctly configured. This is a statement of the trust boundary, not a mechanism: nothing in the hub can detect or enforce where its proxy runs.

## Why

Interoperability on a private fleet is blocked by certificates, not by NAT: the machines can already reach each other. `tailscale serve` supplies both the proxy and a publicly-trusted certificate with no infrastructure, so the "one paste per machine" convenience claim holds today — and the client already dials `wss://` (holler-client#65 closed 2026-09-06). Implementing TLS in the hub would have gated Phase 2 on work the deployment does not need.

## Consequences

- `hub serve` refuses any non-loopback `--listen` (exit 3) with a message naming the proxy path and `docs/deploy.md`; `body join` refuses plain `ws://` to a non-loopback host.
- The SSH-tunnel scripts are retired (ADR 0002).
- The quickstart shows one machine (loopback) and two machines (tailnet) — never a `ws://<public-host>` form. A doc test greps `README.md` and `docs/**/*.md` for `ws://` followed by anything but `127.0.0.1`/`[::1]` and fails.
- Reverse-proxy idle timeouts must exceed the 15 s presence beat (recommend ≥ 120 s); peer addresses in hub logs are the proxy's (auth is by token, not address).
- The proxy is a **trusted component, not merely a transport** (point 6). `docs/deploy.md` says so where it documents the Caddy/Traefik/nginx alternatives, and must not present an off-box or third-party ingress as equivalent to the on-box `tailscale serve` path. Reducing the proxy's privilege — so that a compromised or untrusted one learns nothing — requires an end-to-end layer below the transport, which is [#321](https://github.com/Performant-Labs/holler/issues/321), not this ADR.

## Not decided here

Native hub TLS and its certificate model (v2); prefix-scoped tokens (ADR 0005 reserves the grammar).
