# ADR 0010 — Presence is status; the roster is a TTL tri-state driven by periodic presence

**Status:** accepted
**Issue:** [#11](https://github.com/Performant-Labs/holler/issues/11)
**Date:** 2026-09-09
**Depends on:** [ADR 0004](ADR-0004.md), [ADR 0005](ADR-0005.md)
**Supersedes:** `holler-server` ADR-0006 (presence is status)
**Executes:** [#186](https://github.com/Performant-Labs/holler/issues/186) (landed)

## Decision

The roster answers one question — **who can be hollered at right now** — and it is never a proxy for "is the process up" or "is a TUI attached." `holler-server` ADR-0006 already drew that line; this ADR keeps it and replaces v1's one-shot, merge-based presence with a periodic, replace-based one, because the one-shot version had a race that could permanently hide a session.

1. **Presence is periodic, not one-shot.** A body sends `session/presence` on a fixed beat (15s), not only once at connect. A single lost frame is never fatal to visibility — the next beat repeats it.
2. **Replace, not merge.** Every `session/presence` frame **replaces** that token's entire set of roster rows: sessions present in the frame are upserted `connected` with `last_seen: now`; sessions this token previously advertised but that are **absent** from the new frame go `gone` **immediately**. v1 merged incoming rows into whatever the roster already had, which is how a session that stopped being advertised could linger forever.
3. **Any frame touches liveness, not just presence.** A `session/update`, a `ping`, or any other frame from a body's connection refreshes `last_seen` for **all** of that token's rows and flips `reconnecting` back to `connected`. Successful traffic of any kind is proof of life; the roster does not wait for the next presence beat to notice a connection is fine. A touch from an unrecognized token is a silent no-op, never a panic, and it never refreshes a *different* token's rows.
4. **TTL tri-state**, swept every 30s: `connected` → `reconnecting` once `last_seen` is 45s stale, → `gone` at 180s, and the row is pruned entirely at 360s. This is a bounded, decaying signal — "wrong for a bounded window, never wrong indefinitely" — not a single connect/disconnect edge.
5. **Explicit close is gone, immediately.** An explicit disconnect, a revoked token, or a `circuit/authenticate` that supersedes an older connection for the same token marks that token's rows `gone` right away, without waiting for the TTL sweep. v1's "explicit close" concept survives under this name; what is retired is treating a *missed heartbeat* the same as an explicit close (point 4 already separates "stale" from "gone").
6. **Collision policy protects a healthy body, not a stale claim.** A `session/presence` naming a routable name already held by a *different* token is rejected only while that holder's row is `connected`. If the holder has aged to `reconnecting` or `gone`, the new claim **replaces** the row outright — same name, new locator — and the displaced holder's later presence for that name is the one now rejected. Because presence repeats every beat, a rejected claim is retried automatically the moment the genuine holder ages out; a lost presence race can no longer permanently hide a session the way it could in v1.
7. **`stalled` is a hub-derived display hint, not a wire state and not a trigger.** A session showing `working` with no `session/update` for a threshold (default 5 minutes) is shown as `stalled` in `roster` and carried in a `session_busy` error's `data` (ADR 0009); no body ever sends `stalled` on the wire. It means *look*, never *interrupt* — a shared inference backend can starve a healthy session's prefill for minutes with zero updates, and an orchestrator that auto-interrupts on `stalled` would discard work seconds from resuming.

## Why

The old one-shot-presence design had a real, numbered failure (`holler-server#243`): a lost presence race at connect time could permanently hide a session from the roster, because there was no periodic re-assertion to correct it and no window in which a stale claim was allowed to be overtaken. Moving to a repeating beat plus replace-not-merge semantics turns that permanent failure into a bounded, self-healing one — a rejected or lost claim is retried on the very next beat, so the session reappears within one TTL window instead of staying invisible until a human notices and restarts something. Deriving `stalled` from `last_update_at` rather than a wire flag keeps the roster answering a body-reported truth (presence) plus a hub-side inference clearly labeled as an inference, rather than asking every body implementation to guess when its own generation backend is merely slow.

## Consequences

- `crates/holler-hub/src/roster.rs` keys rows by routable name (ADR 0005) and treats `client_id`/peer address/connection handle as mutable locator fields on that row, exactly as ADR 0005 already required; this ADR fixes the state machine that decides `connected`/`reconnecting`/`gone`/pruned and when a row may be replaced.
- The sweep interval (30s) and the three TTL thresholds (45s/180s/360s) are named constants (`HOLLER_ROSTER_SWEEP_MS`, `HOLLER_ROSTER_RECONNECT_MS`, `HOLLER_ROSTER_GONE_MS`, `HOLLER_ROSTER_PRUNE_MS`) so an operator can tune them for a slower network without a code change.
- `roster` (default) shows `connected` and `reconnecting` rows; `--all` additionally shows `gone` rows. `--prefix` composes with `--all` (ADR 0005 §4's transitive match).
- The README's orchestrator guidance says explicitly that `stalled` means *look*, never *interrupt* — this is documentation, not a protocol guard, because the roster has no way to distinguish a starved-but-healthy session from a genuinely wedged one without the operator's judgment.

## Not decided here

- The busy-turn refusal (`-32009 session_busy`) and the atomic `interrupt SESSION TEXT` redirect that reads `stalled`/turn-age from this roster — [ADR 0009](ADR-0009.md).
- Routable-name grammar, labels, and the addressing scheme this roster keys on — [ADR 0005](ADR-0005.md).
- The `wait` CLI verb's own full contract — [holler#142](https://github.com/Performant-Labs/holler/issues/142) / [docs/orchestrating.md](../orchestrating.md) — is its own story; it consumes this roster's per-row watch channel (`Roster::subscribe`) but is documented there, not here.
