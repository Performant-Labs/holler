# ADR 0020 — Remote hub-admin control: same channel, existing credential, no scope split yet

**Status:** accepted
**Issue:** [#21](https://github.com/Performant-Labs/holler/issues/21)
**Date:** 2026-09-27
**Depends on:** [ADR 0004](ADR-0004.md), [ADR 0007](ADR-0007.md)
**Decides:** the open questions raised in [#507](https://github.com/Performant-Labs/holler/issues/507), part of epic [#506](https://github.com/Performant-Labs/holler/issues/506)
**Clarified by:** the [#506 brief](../handoffs/506-brief.md) (2026-09-27) — §1's "the same credential, via `--token`" does not work as written: since ADR 0018/0019, a body's bound credential is not a string, it is the identity persisted at `<state>/body/credential.json` (plus its X25519 identity key), tied to one already-joined body's local state directory. There is no `--token` value the admin verbs could take that means "this credential." The remote form is `--server URL` alone; the credential and pinned hub key come from whatever body identity already lives in local state on the machine running the command. A consequence, not a bug: reusing the credential this way means the machine running remote admin must already have joined a body on that hub — there is no lighter path that authenticates for admin only without also registering as a body. That gap is exactly what "Not decided here" below defers.

## Decision

The hub-only verbs (`roster`, `say`, `interrupt`, `answer`, `wait`, `hub status`, `hub query`) get a remote form — `--server URL` alone, reading whatever body credential already lives in local state — by answering #507's five open questions as follows:

1. **Credential type: no new admin token, for now.** A remote admin client authenticates with the **same credential** a body already uses to connect (the bound credential from `circuit/authenticate`, ADR 0007), read from that machine's local `<state>/body/credential.json`, not passed on the command line (see "Clarified by" above). No new "admin token" type is minted here. A distinct admin credential — one that cannot join as a body, and a join token that cannot administer — is deferred to a later story (see "Not decided here").
2. **Scope: read-write, no split.** Every verb above is available to any valid credential over this channel; there is no read-only vs. read-write distinction yet, and no ACL enforcement at the hub. A scoping/ACL layer (so a monitoring integration does not need write access just to poll the roster) is deferred to a later story.
3. **Wire shape: the same channel.** This reuses the existing hub WebSocket connection and JSON-RPC 2.0 protocol (ADR 0004) with new methods for the admin verbs — not a second channel or port.
4. **Error codes: deferred.** New codes for "credential lacks scope" and "not a valid admin credential" are meaningless while #1 and #2 stand as decided (there is only one credential type and no scope check to fail); they are deferred alongside #1 and #2.
5. **Rate limiting / abuse posture: deferred.** No new lockout or abuse posture is introduced for this surface now; it reuses whatever posture already applies to an authenticated connection on this channel. A dedicated posture is deferred to a later story.

This unblocks [#508](https://github.com/Performant-Labs/holler/issues/508) (hub: implement the control channel) and [#509](https://github.com/Performant-Labs/holler/issues/509) (CLI: `--server`/`--token` on the verbs) to start against a fixed decision, at the cost of a known, accepted gap: **any bound body credential can, today, also drive the admin verbs remotely** once this lands. That gap is deliberate and temporary, not an oversight.

## Why

The epic (#506) exists because of a real, working deployment gap (the forge/pfleet SSH-hop workaround), and the credential-separation and scope questions #507 raised are real but do not need to be settled before the basic remote path works. Reusing the existing credential and channel gets `roster`/`say`/etc. working remotely with no new wire surface, no new token lifecycle, and no new operator commands to learn — the smallest change that closes the gap. Credential separation and ACLs are real hardening, owed before this is exposed to any less-trusted caller than "the same operator who already holds a body credential for this hub," but that hardening is separable follow-up work, not a precondition for the first working version.

## Consequences

- `docs/protocol/v2.md` gains new JSON-RPC methods for the admin verbs, documented as usable over the **same authenticated connection** `circuit/authenticate` already establishes — no new handshake.
- `hub token mint`/`list`/`revoke`/`delete` (ADR 0007 §4) are unchanged; there is still exactly one token/credential type.
- The remote forms of `roster`/`say`/`interrupt`/`answer`/`wait`/`hub status`/`hub query` (#509) take `--server URL` only; there is no `--token`/`--hub-key` flag on them, unlike `body join` — they read the local body identity instead of taking one on the command line.
- Every existing and future holder of a bound credential for a hub can, from #508 onward, remotely drive every admin verb against that hub, **provided the machine running the command has already joined a body on it**. This must be stated plainly in `docs/deploy.md` (#510), not left implicit.
- This ADR does not touch #437 (session hold/drain); `hold`/`release`, once #437 lands, join this same surface under the same decision.

## Not decided here

- **A distinct admin credential type**, separate from the body join credential, so a credential minted for remote admin use cannot join as a body and vice versa. Real follow-up work, tracked against #507's open question 1 until a new issue is filed for it.
- **A read-only/read-write scope split**, and hub-side ACL enforcement of it. Follow-up against #507's open question 2.
- **New error codes** for scope/credential-type failures (would continue the `-32011`/`session_held` numbering convention, #441) — follow-up against #507's open question 4, once #1 and #2 above are revisited.
- **A rate-limiting/abuse posture specific to this surface**, as distinct from the existing body-connection lockout posture (docs/deploy.md) — follow-up against #507's open question 5.
