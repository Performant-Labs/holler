## Context

On 2026-10-07 five records each claimed to say which session a pane was on (the TUI, the hub's registration, and the
fleet launcher's `sessions.toml`, `last-session` and `owned-sessions`), and nothing kept them in step. Orders ran in a session
the pane did not show, a repair re-registered the old session by guessing, a wedged harness server went unnoticed for three
days, and every launch left a stray session behind. Epic #633 makes Holler the only thing that changes a pane. This ADR
ratifies the contract the epic fixed and the code that already implements part of it, and decides the questions the epic
left open.

**Sources, in order of precedence.** The merged code wins over the epic's prose wherever they differ, and this ADR says so
at each difference. The code is `crates/holler-pane/` (#637), `crates/holler-proto/src/methods.rs` (#637), and
`crates/holler-hub/src/{pane_dispatch.rs,panes/mod.rs,profile/mod.rs,profile/rename.rs}` (#669). Files that a later story
creates are named with the story that creates them; they do not exist on `main` yet.

## Decision

### 1. Ratified: the records

The records live in `holler-pane` (`src/pane.rs`, `src/profile.rs`). Every stored record and every params struct refuses
unknown fields (`deny_unknown_fields`): a peer that does not know a field cannot read, change and write back a record and
drop that field silently. Optional fields are left out when absent and read back as absent. Every timestamp is `i64`
milliseconds since the Unix epoch.

**`Pane`**, one per pane, keyed by `name`:

| Field | Type (merged) | Notes |
|---|---|---|
| `name` | `PaneName` | A newtype over `holler_proto::vocab::SessionName`, so a pane name obeys the [ADR 0005](ADR-0005.md) grammar. It is also the tmux session name. Names such as `hj-c1r2` are names, not positions. |
| `generation` | `u64` | See section 8. |
| `herdr` | `HerdrPane { session, workspace, pane_id, grid: GridPos, label? }` | `pane_id` is Herdr's opaque id (`PaneId`). `label` is observed, never recorded: launch and relaunch write none (section 2; amended 2026-10-11, #808). |
| `host` | `HostInfo { name, tmux, cwd, herdr_api_version? }` | `herdr_api_version` is the string `HerdrPort::version()` reports, recorded by a verb, never by the Herdr adapter, which writes no record (section 10). |
| `harness` | `HarnessInfo { kind, port?, pid?, health }` | `kind` is the closed enum `HarnessKind` (`opencode`, and `claude` since #831, section 15); `health` is `"healthy"`, `{"unhealthy": reason}` or `"unknown"`. Amended 2026-10-11 (#831): `port` is optional, present for `opencode` and absent for `claude`, and `pid` is the process of a `claude` pane (the process is the harness, section 15). An `opencode` launch writes no `pid` since #802 (the server is a process of the pane's tmux session, which the host stops); a record written earlier still reads with one. |
| `session_of_record` | `Option<String>` | THE session: the TUI shows it and the hub drives it. The epic wrote `Option<SessionId>`; the merged type is a plain string. |
| `role` | `PaneRole` | `agent` or `orchestrator`. |
| `hold` | `Hold` | `"none"`, `{"parked": {reason, release_when, since}}` or `"drained"`. This is the park state of a pane, **not** the prompt hold of the hold and release verbs (`holler_proto::SessionHold`). |
| `last_observed` | `LastObserved { shown?, driven?, at }` | Written by reconcile, never inferred (I6). |
| `profile` | `Option<ProfileName>` | The profile the pane belongs to, at most one (C5). Membership is this field only. |
| `model` | `ModelSpec { provider, model_id, effort }` | Recorded by launch, relaunch (#644) and import (#650) (C1). |
| `opencode_agent` | `Option<AgentKey>` | Amended 2026-10-10 (#700). The OpenCode agent the pane's hub-delivered messages run as; absent means the server's default agent. `AgentKey` is a name, never a secret (I7): a non-empty token of ASCII letters, digits, `-` and `_`, anything else `agent-key-invalid` (an open code), on decode too. `ProfileSpec` carries the same optional field after `model`; the spec flag `--agent KEY` sets it on `launch` and `relaunch`, the launch record writes it, and `profile create --from-current` copies it. Applying it is #642's. |
| `env` | `Vec<EnvVarName>` | Names only (I7). |
| `context` | `ContextCeilings { soft, hard }` | `u32` each; the ceilings a watchdog reads. |
| `command` | `Option<Argv>` | B2. |
| `probe` | `PaneProbe { check?: Argv, expect: Vec<String>, last?: ProbeResult }` | B1. |

**`Profile`**: `name: ProfileName`, `slug`, `generation`, `panes: Vec<ProfileSpec>`, `created`, `updated`. On read the
stored `slug` must equal the slug derived from the name, or the record does not load. **There is no `log` field** (ruling 8;
the epic listed one): the append-only change log is read only through `ProfileStore::log`, so `cas_put` cannot rewrite
history. A log entry is `ProfileLogEntry { at, generation, actor, change }`, `change` being `created`, `{"updated": {summary}}`,
`{"renamed": {from}}` or `deleted`.

**`ProfileName`** is a display name (spaces allowed). Parsing trims it and refuses a name that is empty, longer than 64
characters, has a control character, or has no ASCII letter or digit (all `usage`). `slug()` is the one slug rule: ASCII
letters and digits lower-cased, each run of anything else one `-`, no leading or trailing `-`. Two names with the same slug
are the same profile for uniqueness. **`Actor`** (who made a profile write) is a trimmed, non-empty name of at most 64
characters with no control character.

**`ProfileSpec`**, one pane of a profile, names and non-secret values only (I7): `pane: String`, `herdr { workspace, grid }`,
`host { cwd }`, `harness { kind, port_policy }`, `model`, `role`, `env`, `context`, `command?`, `check?`, `expect`. `pane` is
plain text, not a `PaneName`, because a spec may name a pane that does not exist or belongs to another profile (a *detached
spec*, for example after `profile create --from`).

**`Argv`** (B2) is a JSON array of strings. Nothing in Holler passes a stored command through a shell. A bare string, or an
array with a non-string element, is `command-not-argv`. `Argv::from_json` reads the text of the `--command-json` and
`--check-json` flags (text that is not JSON is `usage`).

**`EnvVarName`** (I7) is the one guard for environment entries (ruling 7): a `=` anywhere is `profile-secret-refused`; an empty
name, or one with whitespace or a control character, is `env-name-invalid`. Neither refusal echoes the refused text. Because the
guard runs on decode, a record that holds a value cannot load, and no store or importer scans raw JSON a second time.

**`ProbeResult`** (B1) is `"ok"`, `{"failed": {"missing": [...]}}` or `{"error": "reason"}`. The signature
`run_probe(argv, expect, timeout) -> ProbeResult` is frozen; until #663 fills it, the stub answers `Error`, never `Ok`, so a
launch cannot pass a probe on a stub. The `Prober` trait and `SystemProber` let a test swap the runner. The runner (#663)
answers `ok` only when the program exited 0 and every `expect` string occurs in its stdout (as bytes, case-sensitive), and
`failed` when it exited 0 without some of them. A non-zero exit or an end by a signal is `error` whatever the output, and so
are the deadline passing and more than 1 MiB of stdout. The argv is run directly, never through a shell, and no reason
echoes an argv element or a byte of the output. The runner signals the probe's process group only while its leader is
unreaped, when the group's id (the leader's pid) cannot have been reused, so a `try_wait` error sends no signal and is
`error`. That path, a child that escapes the group and a missing `kill` binary are the documented exceptions to
section 12's "No verb leaves work running after it exits". Since #696 the probe is run by `holler-pane`'s one bounded
runner (`holler_pane::bounded`, section 5), which the adapters share; the contract above is unchanged.

**`GridPos`** (decision 7) is section 10.

### 2. Ratified: the ports

All ports are traits in `holler-pane` (`src/ports.rs`, `src/profile.rs`, `src/hub.rs`), **synchronous, blocking and `Send + Sync`**: async
code calls them from `spawn_blocking` or a thread, and every method returns within I5's bound (default 10 s) or with
`timeout`. Two methods are bounded otherwise, which also qualifies section 12's per-call bound (#663):
`ProfileScope::edit_spec` returns within the sum of its port calls (at most four) plus the verb's own act, which it can
neither bound nor cancel, and `Prober::run_probe` returns at its deadline plus at most 1 s to kill and reap the probe; a
follow-up amends the frozen trait docs to match. Through the wiring a third case can run past its bound: an OpenCode TUI
method whose pane the `tui_session` lookup resolves through the registry or Herdr (section 5, "Wiring as built
(#649)"). `Ports` bundles one `&dyn` of each, and a verb holds it.

| `ProfileScope` | `resolve(profile, pane?)`, `edit_spec(profile?, pane, edit, act)` | `holler-cli/src/pane/profile_scope.rs` (#663; #670 creates the empty file) |
| `HerdrPort` | `ensure_pane`, `send_text`, `send_keys`, `read`, `close`, `snapshot`, `version`, `observe_pane` (#832, section 14; required since #835) and the default-armed `observe_panes` (#832) | `holler-adapter-herdr` (#640) |

`HerdrPort`, and the data types it takes and returns, stay **provisional** until the spike #636 (Herdr) reports.
A pane Herdr reports carries its label (`HerdrPane.label`, an optional, observed value: `launch` and `relaunch` never write
one, and no comparison of a record with a snapshot entry looks at it). It is the join key from a pane name to a live Herdr
pane (#808, operator decision 2026-10-11).
`HarnessPort` is final: the spike #635 confirmed it unchanged and #642 built it (see "`HarnessPort` as built (#642)"
below). Amended again by #831 for a second harness (section 15). If a spike contradicts them, the contract and this ADR are amended first, in their own PR (the epic's amend-first
rule). `holler-pane-testkit` (#638) fakes every port and ships a conformance suite each real implementation runs against
itself. Both `HarnessPort` and `HostPort` are amended since, under that rule: `HarnessPort` by #645 (the prompt seam,
section 8) and by #802, and `HostPort` by #802 (see "The harness server as amended (#802)" below) and by #835, which adds
the required `foreground_commands` (section 13, "Decided (#835)"), and `Ports` by #839, which gains `HubPort` (section 11). #835 also made `HerdrPort::observe_pane` (#832)
required: both have no default, so the compiler finds every implementation, a wrapper port included, where a default
would answer silently in place of a port the wrapper did not forward. #647 part 2 adds two more required reads,
`HostPort::attached_clients` and `HarnessPort::agent_view` (section 12), for the same reason; #649's wrappers forward both.
**Amended by #831 (section 15, item 17):** `HostPort` gains the required, read-only `foreground_pids(name) -> Vec<u32>`, the
pids of the foreground process group of every live pane of the tmux session (every member of the group, not only its
leader), unique and ascending; pids only, never an argv (I7); `pane-not-found` for a missing session, as `ps` answers; and
all or nothing, never a partial list. tmux has each pane's tty (`#{pane_tty}`) but no format for its foreground process, so
the tmux adapter makes one `list-panes -s` listing of `#{pane_dead} #{pane_tty}` (a dead pane dropped, a tty checked to be
`/dev/` and a relative name of `[A-Za-z0-9._/-]` with no `..` segment and no leading `-`, or the answer is `unavailable`),
then, per live pane in tmux's order, `ps -t <tty> -o pid= -o pgid= -o tpgid=` with `LC_ALL=C` through the shared bounded
runner, under the call's one deadline; a process whose group id is the tty's `tpgid` is in the answer. A `ps` that exits
non-zero with no output is a tty with no process; any other failure is `unavailable` with its first stderr line. Every
subprocess of the host adapter is now `tmux`, `kill` or `ps`, each with its own binary seam (`with_ps_binary` beside
`with_kill_binary`). It has no default, so every implementation, a wrapper included, adds it; the import's adoption reads
it (section 15, item 17).

**The harness server as amended (#802).** The operator's decisions of 2026-10-11 (1 to 4), and three more decided in
review round 1 under the operator's rules (change signatures freely while in development; one source of truth; a wedged
process can always be killed with extreme prejudice):

1. **Decided (operator, 2026-10-11): the agent is applied as the OpenCode server's `default_agent`, set when the server
   starts**, not per prompt: per prompt would need a protocol field, a hub change and a `holler-body` change.
2. **Decided (operator, 2026-10-11): it reaches the port by changing the port**, not by an additive default-armed method.
   An omitted agent is a compile error at every call site, and every implementation is in this workspace.
3. **Decided (operator, 2026-10-11): `ServeSpec`**, a `#[non_exhaustive]` struct in `holler-pane`'s `ports.rs` that holds
   `agent: Option<AgentKey>` today. The model, the effort, the environment names and the context ceilings join it later
   with no signature change, and a new field of the pane's spec for its server goes there, never into a new parameter.
   Outside `holler-pane` it is built only from `ServeSpec::default()` and its builder (`with_agent`); the launch engine
   builds it with every field named, so a field added later is a compile error there until it is passed on.
4. **Decided (operator, 2026-10-11): the harness server runs inside the pane's tmux session, started through the host
   adapter.** `HostPort` (`run`, and `stop_owned`: TERM, a shared grace, then KILL) is the one place that starts and stops a
   pane's processes. So `HarnessPort::serve` became `serve_command(name, port, &ServeSpec) -> Argv`, which builds the
   server's argv and starts nothing (no process, no bound port, no file); the OpenCode adapter no longer spawns `opencode
   serve`; and `harness.pid` stops being a second source of truth: launch no longer writes it. This closes #695 (a wedged
   server could not be stopped). When the spec has an agent, some element of the argv contains the key's text; a harness
   that cannot apply it refuses `agent-unsupported` (an open code, exit 3: the harness understood the request and
   declines it, as `prompt-unsupported` does). The OpenCode adapter no longer answers it for every agent: since #642
   part 3 its argv carries the key as the server's `default_agent` ("`HarnessPort` as built (#642)", fact 7).
5. **Decided in review round 1: the agent check after start.** The required method `HarnessPort::verify_serving(port,
   &ServeSpec)` (no default: a harness that starts servers must say whether the running one honours the spec) is called
   by the engine after the health wait and before `create_session`. `Ok` only when the running server honours every field
   of the spec; otherwise a refusal with an open code the implementation owns, which the engine's rollback answers, and the
   rollback now stops the server, a process of the session. Since #642 part 3 the OpenCode adapter checks a spec with an
   agent on the running server and refuses one the server does not run with its own open code `agent-unusable` (fact 7
   below), after the act's health wait, and the rollback stops the server: for this adapter a refused agent is exit 3
   after acting and rolled back, as the act's second `port-in-use` check is, while `agent-unsupported` stays the
   plan-time refusal of a harness that cannot apply an agent at all. The method answers for the spec, not for whether
   the server is up: the health wait has just seen the server answer, and a server gone since then fails the engine's next
   call to it (the session of record's), which the same rollback answers. So an implementation sends a request only for
   what it must check on the server, and the OpenCode adapter answers a spec without an agent `Ok(())` with nothing sent:
   its argv applies no agent, so the server keeps its own default.
6. **Decided in review round 1: the server's working directory has one source, the pane's spec** (`plan.spec.host.cwd`).
   `HostPort::run` gains it, `run(name, cwd, argv)`, and the tmux adapter passes it as `new-window -c <cwd>` (escaped like
   every value the adapter did not write); a `cwd` that is empty, relative or missing is `usage`, before any window is made,
   since tmux would start the program in `$HOME`. The engine passes the spec's directory for both the spec's command and
   the server, so a session reused after a directory change no longer starts a program in the old one; the session keeps
   its own directory for its shell window only, and nothing relies on it. `OpenCodeConfig.workdir` is deleted.
7. **Decided in review round 1: every refusal stays in the plan.** `serve_command` is pure, so the engine calls it in the
   plan, first, keeps the argv, and the act passes exactly that argv to `host.run` after `ensure_session`. An
   `agent-unsupported` refusal is therefore exit 3 with nothing written, no rollback and no reconcile step, like
   `pane-exists` and `port-in-use`. The OpenCode adapter's `serve_command` refuses no agent since #642 part 3; what only
   the running server can show, an agent it does not run, is `verify_serving`'s `agent-unusable`, exit 3 after acting and
   rolled back (decision 5).

**The health wait moved into the engine** (`holler_pane::tx_launch::wait_healthy`): after it runs the server, the act asks
`health` every `TxOptions.boot_poll` (150 ms by default) until the server answers or the run's budget ends, and a server
that never answers ends the run as the budget's `timeout` (`pane.launch` or `pane.relaunch`; it was `unavailable`). The
wait has no deadline, budget or poll count of its own: it ends with the run's budget, whose end it checks before every
ask, the first one after the server's run included. So each `health` call is a live step with the budget checked before
it, no call starts once the budget has run out, and section 12's bound (the budget plus one port call's own bound plus the
rollback calls) holds for the wait too. The test kit's conformance suite and the OpenCode adapter's opt-in real tests wait
with the same function. Three things of the adapter's own wait are given up, each acceptable: its shorter bound per try
(`boot_try`, 500 ms; `health` always uses `Timeouts.health`, 2 s, and a try that hangs costs at most that, which is the one
port call's own bound of section 12 when the try starts just before the budget ends); its fast failure when the server
exits at once (now seen as the budget's `timeout` when the budget ends, with the same rollback); and its check that a
healthy answer came from the process it had started (never adopting a server now rests on the plan's `port-in-use` check
and the act's check again just before it runs the server).

What moves with the server: `stop_owned` stops the server's process group, not the shell commands OpenCode starts in
sessions of their own (`scripts/spikes/opencode-lib.sh`), which the deleted `kill_group` did not stop either. A provider
credential never goes on an argv (`ps` and tmux show it): under tmux the server inherits the tmux server's environment, not
the adapter's, so a credential reaches it only through the pane's tmux session. How production sets it there is the
cutover's (#654): the wiring (#649) passes `ProcessEnv::Inherit`, handles no credential and makes no `HostPort`
amendment, so `HostPort` still has no environment parameter (section 5, "Wiring as built (#649)"). tmux also limits a command's size
(tmux 3.7c refused a 20,000-byte `new-window` argument and took 15,000), so #642 part 3's `OPENCODE_CONFIG_CONTENT`
carries only `{"default_agent": KEY}`, never an agent's definition.

**`HarnessPort` as built (#642).** `holler-adapter-opencode` implements every method, over OpenCode's HTTP API on
`127.0.0.1` and, for a pane's TUI, over tmux:

1. SHOWN is read from the TUI's terminal title through tmux (`#{pane_title}` of the pane's tmux session, addressed by its
   exact name as `=<name>:`, which tmux resolves to the active pane of the session's current window), not through Herdr;
   the session of record is titled with its own id, so the title maps back to it. The precondition is that the session's
   current window is the TUI's. Since #802 every pane's session also holds its server's window, which `run` creates
   detached; a client that switches the session to that window moves `attach_tui` and `shown_session` onto the server's
   pane. A later change can address the TUI by its own window. Every tmux call the adapter makes passes `-u`, so the
   query's TAB-joined reply survives a process with no UTF-8 locale, where a tmux client prints each TAB as `_` (#844).
2. **The adapter starts no server** (#802, decision 4 above). `serve_command` builds `<env prefix> <opencode_bin> serve
   --port P --hostname 127.0.0.1 <serve_args>`, the prefix being the TUI's own (`env -u OPENCODE_DISABLE_TERMINAL_TITLE`,
   or `env -i` and the configured pairs), plus one pair for a spec with an agent (fact 7), and `HostPort::run` starts it
   in the pane's tmux session; `stop_owned` stops
   it. Never adopting a running server is the launch engine's: its plan refuses a port that already answers
   (`port-in-use`), and it asks again just before it runs the server. The adapter no longer checks the port itself. `FakeHarness`'s scenario method still restarts its own pane's server idempotently, where a
   second real server would fail to bind; no engine reaches that difference, since it never runs a server on a port that
   answers.
3. `shown_session` is `None` whenever it cannot tell: the home screen, a deleted session, a title that is not a whole id,
   no TUI; it never guesses.
4. One TUI per server is the caller's precondition (`select-session` reaches every TUI of a server); the registry gives
   each pane its own port.
5. `list_sessions` lists top-level sessions only; child (subagent) sessions are left out.
6. The adapter's one lookup, a pane's tmux session name, is supplied by wiring (#649) and must answer for a pane being
   launched, before its record exists; an unknown `PaneId` is the lookup's own error (`pane-not-found`), where
   `FakeHarness` answers `None` or `unavailable`. The server's directory is no lookup since #802: it comes from the pane
   spec, through `HostPort::run` (decision 6 above).
7. The pane's OpenCode agent (`Pane.opencode_agent`, #700) reaches the port in the `ServeSpec` (#802), and the OpenCode
   adapter applies it as the server's `default_agent`, once, when the server starts (#642 part 3); it no longer answers
   `agent-unsupported` for every agent. `opencode serve` has no agent option, so `serve_command` adds one pair to the
   server's `env` prefix, `OPENCODE_CONFIG_CONTENT={"default_agent":KEY}`: the key and nothing else (tmux refuses a
   command of about 20,000 bytes), on the server's argv only, never the TUI's, and after the prefix's own words, so it
   replaces a same-named configured pair and an inherited value. OpenCode starts healthy with any key, so `verify_serving`
   then asks the running server, within one call's bound: `GET /config` must name the key as its `default_agent` (the
   variable reached the server), and `GET /agent` must list the key with a `mode` other than `subagent` (`primary`, or
   `all`, what a config agent without a `mode` gets) and not hidden, OpenCode's own rule for a default agent. Anything
   else is the adapter's open code `agent-unusable` (exit 3), whose message names the key and the reason and quotes no
   reply; it comes after the act's health wait, and the engine's rollback stops the server (decision 5). A reply that is
   not the JSON a step needs is `unavailable`. A spec without an agent adds nothing to the argv and is answered `Ok(())`
   with nothing sent.

`Watch<T>` is the change stream of both stores: changes in order, each with a store-wide, strictly increasing `Cursor`.
`watch(Cursor(0))` first yields a put for every record held now; resuming from the last cursor seen neither repeats nor skips.
`next()` yields `Ok(Some(event))`, `Ok(None)` for idle within the bound (the stream stays usable), or an error that ends the
stream; `timeout` means a wedged store, never idle. An event is `PaneEvent { cursor, name, pane? }` or
`ProfileEvent { cursor, name, profile? }`, with no record meaning a deletion; a profile rename is a deletion of the old name
and a put of the new one.

### 3. Ratified: the verbs, the `--profile` classes and the spec flags

The pane verbs are `list`, `get`, `watch`, `launch`, `relaunch`, `switch`, `reset`, `park`, `unpark`, `close`, `doctor` and
`import`, under the `pane` subcommand group of the `holler` binary. The profile verbs are `create`, `delete`, `list`, `show` and
`apply` (REQUIRED, #664; `apply` refuses a pane of another profile unless `--take-over`, C3, and `--dry-run` prints the plan),
plus `rename`, `export` and `import` (#665). There is no `diff` verb: `profile show` reports where live panes differ
from their spec. One verb is one file and one owning story, including its clap `Args` struct (ruling 2); the shared flag groups
(`SpecFlags`, `ProfileOpt`, `SpecOnly`) and `--take-over` are declared once by #670.

`--profile P` has two classes and one exception:

- **Spec-editing** (`launch`, `relaunch`, `close`): edit P's spec for that pane and change the live pane as one transaction
  (I8, section 8). P must exist (`profile-not-found`). `--spec-only` (C2, requires `--profile`) edits the spec and changes
  nothing live. Without `--profile` these verbs never touch a profile.
- **Scoping** (`list`, `get`, `watch`, `doctor`, `switch`, `reset`, `park`, `unpark`, the `--pane` forms of `say`, `interrupt`
  and `answer`, and the roster): act on P's panes. A named pane outside P is `pane-not-in-profile`. The read verbs and
  `doctor`, `park` and `unpark` with no pane name mean every pane of P; `say`, `interrupt`, `answer`, `switch` and `reset`
  still need a pane name.
- **Neither**: `pane import` takes no `--profile`; a real run creates the profile `fleet` itself (#650).

**Park and unpark as built (#646).** `pane park [PANE] --reason TEXT --release-when WHEN` and `pane unpark [PANE]`
change only the pane record's `hold`, by one compare-and-swap per pane; they call no adapter and write no profile, so
they never move a pane in Herdr or touch its processes, and I3 reduces to plan and record. `park` sets `{"parked":
{reason, release_when, since}}` on a pane whose hold is `none` (`since` is the verb's clock); `unpark` sets `none` on a
parked pane. Both leave a pane already in that state, or `drained`, as it is and report it unchanged (exit 0). With
`--profile` and no pane name they take P's panes in name order and stop at the first failed write, whose message
names the panes changed before it and those not reached; the rerun is safe. The reason and the release condition are
one line each, hold no control character, are not blank and are at most 200 characters (`usage` otherwise). Which verbs and prompts read a parked pane
is decided by their stories (the watchdog); the prompt gate of #646 refuses a prompt to a parked pane's
session of record (see "The pane-state prompt gate as built (#646)", section 8). The roster (#648) lists a parked pane
like any other and shows no pane hold: its HOLD column is the hub's session hold, which a park does not set, and
`holler pane list` shows the park.

**Spec flags**, one per `ProfileSpec` field, used by `launch`, `relaunch` and the profile spec:

| Flag | Field |
|---|---|
| `--project DIR` | `host.cwd` |
| `--workspace W` | `herdr.workspace` |
| `--grid POS` | `herdr.grid` (any form `GridPos::parse` accepts) |
| `--model PROVIDER/ID` | `model.provider`, `model.model_id` |
| `--effort E` | `model.effort` |
| `--role agent\|orchestrator` | `role` |
| `--agent KEY` | `opencode_agent` (through `AgentKey`) |
| `--env NAME` (repeatable) | `env` (through `EnvVarName`) |
| `--ctx-soft N`, `--ctx-hard N` | `context.soft`, `context.hard` |
| `--port-policy P` | `harness.port_policy` |
| `--command-arg ARG` (repeatable) or `--command-json '[...]'` | `command` |
| `--check-arg ARG` (repeatable) or `--check-json '[...]'` | `check` |
| `--expect STR` (repeatable) | `expect` |

Giving both forms of `command` or of `check` is a usage error (exit 2). **`profile create --from-current`** copies, from the
`Pane` records in `PaneStore` (so it needs no Herdr call), each member's `herdr.workspace` and `herdr.grid`, `host.cwd`,
`harness.kind`, `model`, `opencode_agent`, `role`, `env`, `context`, `command`, `probe.check` and `probe.expect`, and sets
each member's `Pane.profile`; a pane already in another profile is `pane-in-other-profile`. The mapping lives in
`holler-pane/src/profile_snapshot.rs` (#662), which the migration (#650) reuses. `--from-current` writes `harness.port_policy`
as `fixed:<port>`, the port the pane's harness uses (#662, `profile_snapshot::fixed_port_policy`); `profile_diff` compares it
with `fixed:<port>` of the live port. `profile_diff` compares every field of a spec except `pane` (the name that pairs a spec
with its live pane), so `opencode_agent` too (#644), by equality: `profile show` lists a spec's agent and reports a live pane
whose agent differs from its spec's. In text an absent agent prints `(default)`, never `none`, which is a valid key. A
profile's **live panes** are the pane records whose `profile` names it (by slug).

**Profile files as built (#665).** `holler profile export NAME [--out FILE]` writes a profile as one JSON document,
`{"format": "holler-profile", "version": 1, "name", "panes": [...]}`, whose panes are the specs with `herdr.grid` as
`rRcC`; it holds no slug, generation, timestamp or log, and no environment value (a spec holds names). `holler profile
import FILE [--name NAME]` reads the same document, accepts a position in any form `GridPos::parse` accepts, and creates a
**detached** profile (no pane joins) at generation 1: a file with an environment value is `profile-secret-refused` (the
typed `EnvVarName` decode refuses it; no second scan), a command or check that is a string is `command-not-argv`, a taken
name or slug is `profile-exists`, and a file that is not a document of this format is `usage`. `profile-drift` (#665) is a
reconcile finding, raised for a pane whose record differs from its profile's spec on any field of `profile_diff`'s table:
the comparison `profile show` makes, so they agree; a spec with no pane and a member with no spec are not drift. One
finding per drifted pane per pass naming every differing field and no value, with no remedy; a pass keeps no memory
(section 8), so "once per episode" is once per pass. A pass reads `ProfileStore::list` once, and only when a pane in scope
names a profile; a failed read is an `observe-failed` finding.

### 5. Where verbs run, and the crate layout

**Decided (ruling 1): verbs run CLI-side, against the ports; the hub is the store only.** The hub holds the pane registry
and the profile registry and answers their store methods; it constructs no adapter and runs no verb. The adapters are
constructed in `holler-cli/src/pane/wiring.rs` (#670 creates it, #649 fills it). The hub's `pane_wiring.rs` (#669) is an empty
placeholder with no job under this ruling.

**Wiring as built (#649).** `Wiring::connect` builds the ports of a run, once per run, and every pane and profile verb runs
over them, as do `say`, `interrupt` and `answer` with `--pane`, whose pane resolution calls `connect` (`say_cmd.rs`), and
the roster (#648), which calls `connect` only after its hub call has answered and never with `--server`, and reads the
pane store or, with `--profile`, the profile scope, and no adapter.

- **`connect` needs the hub and nothing else.** It makes one `control/status` exchange (the control client's own 5 s), and
  any failure of it is `unavailable` naming the hub and its state dir, so with no hub every verb exits 1 having touched no
  adapter. It builds the two registries' clients, the Herdr adapter, the tmux host, the OpenCode harness, `SystemProber`, and
  `StoreScope` over the two clients as the `ProfileScope`. The Herdr adapter pings Herdr when it is built, so it is built on
  its first use and kept, a failed build included; building the host or the harness does no I/O. So `pane list`, `get` and
  `watch` and `profile list` and `show` run with no Herdr, tmux or OpenCode present.
- **The registries' clients** (`wiring/store.rs`) send each call as one control-socket request through the CLI's one dispatch
  point (`transport::call`), with the params of `holler_pane::reply` and a `PaneReply` back, within 10 s, or within the
  long-poll window plus 5 s for a `*/watch` request. A failed exchange of a read is `timeout` naming the store method when
  the hub took the request and did not answer within the bound, which is section 2's own rule, and `unavailable` naming the
  hub otherwise. A write whose reply is lost is `timeout`, since it may have landed (section 8, step 2). A JSON-RPC error is
  `unavailable` for a read and a write alike, nothing having been written, and a reply that does not decode is `unavailable`
  naming the method. A `watch` makes its first request when it is called and keeps that batch for its first `next()`, so a
  refused cursor or a missing hub is the answer of `watch` itself, before any item; each later batch is one request,
  resumed from the cursor of the reply before it.
- **The hub port (#839).** `connect` also builds `HubPort`, a client of the hub's control socket; it needs only the hub, as
  the registries' clients do.
- **The configuration** is the CLI process's environment. Herdr: the session `HOLLER_HERDR_SESSION` (Herdr's own
  `HERDR_SESSION` is not read), its socket `HOLLER_HERDR_SOCKET`, else `HERDR_SOCKET_PATH`, else
  `$XDG_CONFIG_HOME/herdr/sessions/<session>/herdr.sock`, and each workspace's rows by columns, `HOLLER_HERDR_WORKSPACES`
  (`label=RxC,...`). tmux, for the host and the harness both: `HOLLER_TMUX_SOCKET`, an absolute path, or tmux's default
  socket when it is unset. OpenCode: the binary `HOLLER_OPENCODE_BIN`, else `opencode` found on `PATH` (an absolute path
  either way, since tmux starts it), the serve arguments `HOLLER_OPENCODE_SERVE_ARGS` (a JSON array of strings), and
  `ProcessEnv::Inherit`. A missing or malformed value never fails `connect`: it is `usage` naming the variable (`unavailable`
  for an `opencode` that cannot be found), which each method of the port it configures answers at its first use, and a bad
  tmux socket never falls back to the default tmux server, the operator's live one. A value of a `HOLLER_*` variable or of
  `HERDR_SOCKET_PATH` that is not UTF-8 is read as the empty value, never as unset, so it takes no fallback: the empty value
  is malformed, but for `HOLLER_HERDR_WORKSPACES`, where it is no workspace and the Herdr adapter then refuses every launch.
- **The `tui_session` lookup** (section 2, fact 6) answers from, in order: the bindings of a launch in progress (the Herdr
  port keeps the pane id each `ensure_pane` returns, and the host port binds it to the name of the `ensure_session` that
  follows it, the launch engine's order, which a default-run test pins); the one pane record whose Herdr session and pane
  id are the pane's (Herdr numbers pane ids within a session, and two such records are `unavailable`, never a pick); and the
  pane's label in Herdr's snapshot (an imported pane's; launch writes none). Otherwise it is `pane-not-found`. **The third
  case beside section 2's two that are bounded otherwise:** the adapter asks the lookup after it has fixed its method's
  deadline, so an `attach_tui`, `select_session` or `shown_session` resolved through the registry (one `pane/list`) or Herdr
  (one snapshot, and on a first use the adapter's connect ping) can run past its own bound when the hub or Herdr is slow. A
  launch resolves its own pane from the bindings and nests no call. The case also qualifies the observation bound of
  `profile apply` (`tx_apply.rs`), whose `shown_session` calls resolve the panes they observe this way.
- **No new bound.** Each adapter and each registry request keeps its own 10 s bound (I5), and each verb its budget; there is
  no flag, option or variable for a bound.
- **What the wiring makes live.** Every profile write through the scope is logged under the one actor `holler pane`: a
  `--profile` edit of `launch`, `relaunch` or `close`, and the creates and relaunches of `profile apply`, so the profile log
  cannot tell those verbs apart. A per-verb actor needs a seam other than the argument-less `connect` (#825). Since #839
  the first message of `pane reset --first` goes through the hub's prompt path, so a parked, held or unhealthy pane refuses
  it (section 8, "Switch and reset as built").
- **Not done here.** No `HostPort` amendment and no credential handling: a provider credential reaches a harness server only
  through its tmux server's environment, and how production sets that is the cutover's (#654). `--herdr-session` is not
  defaulted from the configured session (section 8, "Launch and relaunch as built (#644)"). The pane's model, effort and
  environment still do not reach its server (#829).

**Decided: the crate dependency rules.**

- `holler-pane` holds types, traits and the pure transaction engines (`tx_launch.rs` #644, `tx_switch.rs` #645, `tx_apply.rs`
  #664, `reconcile.rs` and `findings.rs` #647, `profile_snapshot.rs` and `profile_diff.rs` #662, `import.rs` #650), which work
  only through the ports. It depends on `serde`, `serde_json` and `holler-proto`, and takes no async runtime. Its one direct
  side effect is the bounded subprocess runner (`holler_pane::bounded`, #696), which runs a process with the standard
  library under a deadline; beside it, the launch engine sleeps between the health polls of a server it started
  (`wait_healthy`, #802), which touches nothing. **Amended by #696, with no contract change:** that runner is the one
  runner of the probe (`run_probe`, #663) and of the host, OpenCode and Claude adapters, which call it instead of keeping
  private copies. Each consumer sets only where the copies differed (what is kept of stdout and stderr, the kill's reach
  and the poll) and maps its typed error to its own texts, so no consumer's behaviour, error text or `ProbeResult`
  changed; the host adapter keeps its own signals to the panes' process groups and its fake-`kill` seam, and since #831 its
  one `ps` call per pane of `HostPort::foreground_pids` (section 2), with a fake-`ps` seam beside it.
- Each adapter crate depends on `holler-pane` and implements one port. `holler-cli` depends on the adapter crates; `holler-hub`
  does not.
- `holler-pane-testkit` (empty today; #638 fills it) may depend on `holler-pane` and `serde_json`, and **must not depend on

- `holler-proto` knows only the method *names* (`PANE_METHODS`, `PROFILE_METHODS`); it cannot depend on `holler-pane`, which
  owns the params and the reply type.

**Decided: where the I8 transaction helper lives.** The trait `ProfileScope` is in `holler-pane/src/profile.rs` (frozen by
#637). The real implementation is in `holler-cli/src/pane/profile_scope.rs` (#663) and the fake is in `holler-pane-testkit`
(#638). The spec-editing verbs call `edit_spec` and do not write the profile themselves.

### 6. The hub control-socket methods and their replies

**Decided (ruling 6): `pane/*` and `profile/*` are hub control-socket methods, not v2 wire methods.** They sit outside the
closed 23-row catalog (`holler_proto::methods::CATALOG`; 22 rows until #839 added `session/rebind`, section 11), are not reserved in [protocol v2](../protocol/v2.md) §4, and a body
connection that sends one still gets `method_not_found`. The names are:

- `PANE_METHODS`: `pane/get`, `pane/list`, `pane/cas_put`, `pane/delete`, `pane/watch`.
- `PROFILE_METHODS`: `profile/get`, `profile/list`, `profile/cas_put`, `profile/delete`, `profile/watch`, `profile/log`,
  and `profile/rename` (#665).

The control server forwards them through `holler-hub/src/pane_dispatch.rs` to `panes::dispatch` (#639) and
`profile::dispatch` (#661, with `profile/rename` routed to `profile/rename.rs` for #665). Each dispatcher gets both
registries' state.

**Decided (ruling 3): the reply is a `PaneReply` carried as the JSON-RPC result.** Its form is
`{"ok": bool, "data": ..., "error": {"code", "message", "detail"?}}`. The merged type adds the optional `detail` (the payload
of the closed error variant, so the client can rebuild the exact `PaneError`) to the epic's `{code, message}`. It carries no
`schema_version` and is **not** the CLI's `--format=json` envelope (section 9): it is an internal hub-to-CLI encoding. Only a
request that never reaches a handler stays a JSON-RPC error: framing errors and a method in neither list. Every outcome of a
request that reaches a handler is a `PaneReply`, including params that do not decode (`decode_params`; a request with no
`params` decodes from `{}`). Parse-back (`into_result`): a closed code becomes its own variant, any other well-formed code
`Refused`, a malformed code or a reply whose `ok` and `error` disagree `unavailable`. A reply ignores unknown fields; the
records inside `data` do not.

**Decided: `*/watch` is long-poll.** One request, one reply, whose `data` is `WatchReply { events, cursor }`: the batch
collected after `since`, and the cursor to resume from. An idle window answers `{"events": [], "cursor": <head>}`; the head
equals `since` except for a watch from 0 over a registry whose records have all been deleted, and resuming from the head keeps
the `Watch` contract ("then every later change"), where answering 0 would let a pane created and deleted between two polls
never reach the watcher (see "Decisions taken", item 7). The window
stays under the control client's default timeout and within I5's bound; its value is #639's (its brief proposes 4 s).

**Decided: the `data` of each method** (which `reply.rs` leaves to this ADR):

| Method | `data` |
|---|---|
| `pane/get`, `profile/get` | the record, or `null` when there is none (the verb decides whether absence is an error) |
| `pane/list`, `profile/list` | an array of records (`pane/list` sorted by name) |
| `pane/cas_put`, `profile/cas_put` | the stored record, with its new generation |
| `pane/delete`, `profile/delete` | `null` |
| `pane/watch`, `profile/watch` | `WatchReply<PaneEvent>`, `WatchReply<ProfileEvent>` |
| `profile/log` | an array of `ProfileLogEntry`, oldest first |
| `profile/rename` | the renamed record |

### 7. Persistence on the hub

**Decided**, consistent with the brief of #639 (which proposes it for panes) and extended to profiles:

- The pane registry is `<state dir>/hub/panes.json` and the profile registry is `<state dir>/hub/profiles.json`, beside
  `holds.json`. Each is written at mode `0600` through `holler_proto::atomic_file::write_atomic` (a temporary file in the same
  directory, then a rename), the hub's one state-file writer. As with the hub's other state files there is no fsync.
- Each file is a versioned JSON document (`"version": 1`). Its exact layout belongs to the registry's story (#639, #661); both
  use the same generic load and save helpers. The profile change log is persisted in `profiles.json` with the records,
  never inside a `Profile`.
- **One lock per registry.** A single mutex guards each registry's whole table. A write runs under it in this order: the
  compare-and-swap check, building the next document, saving it, and only then committing to memory and publishing the
  event. A failed save therefore changes nothing (memory, file and cursor), and the call answers `unavailable`.
- **Lock order.** The pane registry never calls into the profile registry while it holds its own lock. A hub-side
  operation that needs both (only `profile/rename`, #665) takes the profile lock before the pane lock.
- **Fail closed.** A missing file is an empty registry. An unreadable file, a parse failure, an unknown version or a failed
  validation puts that registry in a failed state: every method, `watch` included, answers `store-corrupt`, naming the file
  and the problem but never quoting its content. The file is **left in place**, never moved aside or rewritten (unlike
  `holds.json`, which is moved aside and restarted empty): pane records gate every verb, so an empty registry would be a
  silent reset. The hub still starts, because its other functions do not depend on panes. The state clears on a restart
  after the operator repairs the file.
- The change feed's cursor head is persisted, so cursors never go backwards across a restart. A watcher that falls behind the
  retained window, or resumes across a restart, receives one event per record changed since its cursor (the latest state, or
  a deletion), so it can miss intermediate writes but never a final state or a deletion.
- `deny_unknown_fields` means that a file written by a newer build with a new field fails closed as `store-corrupt` on an
  older build. That is intended.

### 8. Generations, concurrent writers and the I8 write order

**Decided: how generations fence concurrent writers.**

- Every `Pane` and `Profile` carries `generation: u64`. A record that does not exist is at generation 0, so a create names
  `expected_generation: 0` and is stored at 1. Each applied write adds one. The store sets the generation; the one a client
  submits is ignored. The rule is `holler_pane::next_generation`, written once and used by every store and fake.
- A write whose expected generation is not the current one is `generation-conflict` and changes nothing. `delete` checks
  that the record exists first (`pane-not-found` or `profile-not-found`, whatever the generation) and the generation second.
- A verb takes its expected generation when it plans, and writes the record with it after the act. If another writer got in
  between, the verb's record write fails with `generation-conflict` **after** the live change: the verb fails loudly, exits 1,
  writes nothing more, and prints the reconcile step (the pane doctor command line; the profile-scoped or the bare form of
  step 6, which names no pane, for the reason given there). With `--profile` the record step runs inside the act, so a
  record conflict also restores P's specs (step 5) before the verb prints the reconcile step (#663, confirming the
  assumption of #638).
- **Generations fence records, not live acts.** Two verbs on the same pane can both act; only one records. The frozen
  `Pane` has no field to claim a pane before acting, so this ADR adds none; the reconcile pass (#647) is the safety net. A
  claim, if one is wanted, comes with the operation id (section 12).
- **Known gap:** a record deleted and then created again restarts at generation 1, so a writer still holding generation 1 of
  the old record can overwrite the new one. The contract fixes "0 for a new record", so this is recorded, not fixed.
- No store transaction spans the two registries except `profile/rename` (#665, below). The membership rule is enforced on `pane/cas_put`: setting `Pane.profile`
  to P when the stored pane already belongs to another profile is `pane-in-other-profile`, and P must exist. A spec that
  names a pane of another profile (a detached spec) is not refused.

**Decided (the epic's order, as the merged `ProfileScope::edit_spec` documents it): the I8 write order.** For a
spec-editing verb with `--profile P`:

1. **Plan.** Read P at generation `g` and the pane record; compute P with the edit (`SpecEdit::Set` or `SpecEdit::Remove`).
   A `Set` for a pane whose record belongs to another profile is refused here with `pane-in-other-profile`, before anything
   is written or moved, with or without `--spec-only` (the scope cannot see that an act is empty); a `Remove` is not (a
   detached spec stays removable), and the pane registry's check ("Decisions taken", item 2) stays the authority (#688).
2. **Profile CAS first.** `ProfileStore::cas_put(P_edited, g, actor)`. A conflict here comes before anything live changed:
   the verb exits 1 with `generation-conflict` and can be run again. A first write whose outcome is unknown (a `timeout`)
   may have landed, so the act does not run, and the answer is `timeout`, saying that P may hold the edit, with the
   reconcile step. The store client (#649) answers `timeout`, not `unavailable`, when it loses the reply to a write it
   sent. Any other error of this write is answered as it is (#663).
3. **Act** (skipped with `--spec-only`), then observe.
4. **Record.** Write the pane record with its own compare-and-swap (`cas_put`, or `delete` for `close`).
5. **If the act fails, nothing is recorded in P:** the pane record is not written, and the profile is put back by a
   compensating `cas_put` of its previous specs at `g + 1`. P's specs then equal what they were before the verb, and its
   log shows the edit and its reversal. If the compensating write fails other than by a conflict, the answer keeps that
   write's own code, and its message names P, the unrestored edit (after a `timeout`, the edit, which may not have been
   restored), the act's error and the reconcile step (#663).
6. **A conflict after the act fails loudly.** If the compensating write of step 5 conflicts (another writer moved P during
   the act), the verb exits 1 with `profile-conflict`, naming P, and prints the reconcile step: the exact pane doctor command
   line, and the profile show command for P. A pane-record conflict in step 4 is `generation-conflict`, handled the same way.
   The reconcile step is exactly `to reconcile, run holler pane doctor --profile '<P>' and then holler profile show '<P>'`,
   with P POSIX-single-quoted, and without `--profile` it is `to reconcile, run holler pane doctor`. `reconcile_step` in
   `holler-cli/src/pane/profile_scope.rs` builds both (`reconcile_step(None)` is the second) on
   `holler_pane::findings::doctor_command(None, false)`, the doctor command line's one builder (#701). The step names no
   pane on purpose: a pane-scoped doctor refuses a pane with no record or outside P (`pane-not-found` or
   `pane-not-in-profile`, in `holler-pane/src/reconcile.rs`), which is what a failed `launch` of a new pane leaves, so the
   step runs the doctor over every pane of P (or every pane) and `profile show` reports the spec that has no live pane.
   Three errors of the scope carry the step in their message: this `profile-conflict`, the restore failure of step 5 and
   the first-write `timeout` of step 2. A verb appends it only to an error that does not carry it (#663).

With `profile: None`, `edit_spec` runs only the act and touches no profile. This order deliberately makes the edit visible
in P before the live change, so a concurrent profile editor is refused before anything live moves. The cost is a second
profile write on a failed act; see "Decisions taken", item 1.

**Switch and reset as built (#645).** One engine, `holler_pane::tx_switch`, runs both verbs: switch moves a pane to a
session its harness server already has, and reset to one the run creates. Its plan reads the record (through the profile's
scope with `--profile`) and refuses before anything is written or moved: the orchestrator's pane unless the operator passes
`--as-operator`, a statement of intent and not authentication (`orchestrator-pane`); a harness server that does not answer
its health check, observed live and never read from `harness.health` (`server-unhealthy`, naming the relaunch remedy); for
reset of a pane that has a session of record, a conversation that `HarnessPort::session_activity` reports running a turn
(`session-busy`) or holding a question (`session-holds-question`), while a pane with none is not asked, since reset is
doctor's remedy for it; and, for switch, a target the pane's own server does not list (`session-not-found`) or that is
another pane's session of record (`session-of-other-pane`). The act is `select_session` in the pane's TUI, after
`create_session` for reset, and the observation is `shown_session`. The OpenCode adapter's `select_session` sends its
select request again after each check of the pane, within `settle`, while the title does not show the session (#845): a
TUI that has just started answers `true` before it takes a switch, and the request is idempotent. **A mismatch observed after the act is the closed
failure `unavailable`, exit 1:** I3 needs a failure, and an open code is a refusal (section 9). A mismatch records nothing.
Otherwise the record the plan read is written with exactly four fields set (`session_of_record` and `last_observed.shown` to
the target, `last_observed.at` to the run's clock, `harness.health` to healthy) in one compare-and-swap at the generation the
plan read, never retried; `last_observed.driven` is written in the same compare-and-swap, from the id the body
acknowledged (section 11), or `None` when no body drives the pane. Before the act, the plan reads the live attach sessions
through `HubPort::advertised` and finds the pane's driver (`holler_pane::driven::driver_of`); a driver that reports a turn
or a question is refused (`session-busy`, `session-holds-question`), and a driver that cannot be shown to be the pane's own
(ambiguous, or unproven on a listing shared with other panes) is refused `pane-not-driven` unless the pane's session of
record, its recorded DRIVEN or a switch's target names exactly one body, and a switch whose target another body already
advertises is refused `session-driven-elsewhere`, and for `reset --first TEXT` a pane no body drives, or whose body does not
advertise its session of record, is refused `pane-not-driven` and the hub's gate is asked, without sending, whether it
would admit the prompt (`HubPort::prompt` with `Check`), so a parked, held or unhealthy pane, or one whose SHOWN and DRIVEN
differ, is refused before anything moves: no session is created and the record is unchanged. After `shown_session` shows
the target, `HubPort::rebind` asks the body to drive it; a failure there is a failure after the act (the message ends with
the reconcile step). Then, only for `reset --first TEXT`, `HubPort::prompt` with `Send` queues `TEXT` through the hub's one
prompt path (`send_prompt`), accepted and returned (never waiting for the turn). A prompt that fails after the record, a
refusal in a race included, is that call's own error (a refusal is exit 3 with its code), and its message says the session
was created, shown and recorded but the first message did not land; it has no reconcile step, because the record is
correct. A single process's switch and reset (the next paragraph) ask the hub nothing. No step calls Herdr or the host (I4;
a single process's switch and reset are a relaunch, below), and a run makes at most thirteen port calls, each bounded by I5
(section 12). Neither verb checks the pane's park state itself; `reset --first` is refused for it by the prompt gate of
#646, asked before the act and applied at the send. A failure after the act and before the record is not compensated: the record still names the previous session,
and the message ends with the reconcile step, the pane doctor command line for the pane with `--fix`, which selects that
session again. That step follows every such failure once `select_session` has been called, a record conflict or a
`timeout` included; a failure before then has moved neither the TUI nor the record, and its message has no step.
Whether or not the verb ran with `--profile`, the step names the pane, unlike the two forms of step 6 that the generations
rule above gives. Those name no pane because a failed launch can leave a pane with no record, which a pane-scoped doctor
refuses. A switch or reset reads the pane's record before it acts, so a doctor run for that pane is not refused, and
`--fix` is the pane doctor's own remedy for a TUI that does not show the session of record, while a fix can repair it.
Neither verb edits P's specs, so no `profile show` is needed. A session that reset created and did not record stays on the
server, and the message names it. After a successful reset the previous session also stays on the server, and the pane
doctor reports it as a stray session: no port deletes a session. The session-of-other-pane check is a read in the verb, not
a rule of the registry, whose compare-and-swap enforces only the generation and the membership rule, so two concurrent
switches of two panes to one session can both pass it and both record that session.

**Switch and reset of a single process as built (#831, section 15 item 6).** A pane whose harness's shape is
`SingleProcess` (Claude Code) has no server to create a session on and no TUI to switch, so `tx_switch` keeps its plan and
replaces its act with a relaunch. The plan refuses as above (`orchestrator-pane`, `server-unhealthy` for a process that no
longer runs, and for switch `session-of-other-pane`), except that a switch also refuses a pane that is not idle, since a
relaunch drops the turn in flight (`session-busy`, `session-holds-question`, and `session-holds-permission` for a
permission prompt, which reset refuses too), and asks for no session list. Whether the target has a conversation is the
relaunch's plan's: `process_command` with the resume-only `SessionChoice::Resume` answers `session-not-found` for an id
with no transcript, before anything is stopped, so a switch to an unknown id starts and records nothing, as a server
pane's switch does. The act is then
`tx_launch::relaunch_recorded`, the one stop, run, wait, locate and record sequence (section 15 item 6): the pane's
processes stopped, its process run on the target (switch) or on a fresh session (reset), located idle, seen holding it, and
recorded with its new pid by the launch engine's own compare-and-swap. A relaunch calls Herdr and the host as a launch does,
and types nothing (I4). Since #839, `reset --first` on a single process is refused `pane-not-driven` in the plan, before
anything is stopped: no body drives a Claude Code pane until #850, and the hub's gate is the only path a first message
takes (section 11, point 6). A failure once the relaunch entered its act ends with the reconcile step, as a failure after
`select_session` does.

**The prompt and activity seam (#645 part 2, the operator's carve-out).** `HarnessPort` grows two default-armed methods,
the first amendment since #637 froze it (the second is #802's, section 2): `send_prompt(port, session, text)` and
`session_activity(port, session)`, which
answers the closed `Activity` (`Idle`, `Busy`, `HoldingQuestion`, and since #831 `WaitingPermission`; in `ports.rs`, never on
the wire). A default keeps every
impl that does not override it as it was: `session_activity` answers `Idle`, so nothing is refused where no port reports
activity, and `send_prompt` refuses with the open code `prompt-unsupported` (exit 3). That code departs from the
`not-implemented` the skeleton answers for unlanded methods on purpose: by the time `reset --first` sends the prompt the
reset itself has succeeded, so "understood and declined" (a refusal) is the honest class, not a runtime failure. The OpenCode
adapter replaces both defaults (#642 part 3), and the test kit's fake records them (#684). Its `send_prompt` asks `GET
/session/:id` first, as its `abort` does (an unknown session is `session-not-found` and nothing is posted), then posts
`{"parts":[{"type":"text","text":TEXT}]}`, naming no agent, to the bare `POST /session/:id/prompt_async`, the route and body
`holler-body` sends; it is `Ok` exactly on that route's `204`, and its message for any other reply names the route, the port
and the status and quotes no part of the reply, which could echo the prompt. Its `session_activity` is `HoldingQuestion`
while `GET /question` or `GET /permission` lists an item of the session or of a direct child (subagent) session of it, the
scope `holler-body` reads: a pending permission request, the session's own or a direct child's, reads as `HoldingQuestion`,
since the turn waits on an answer either way. A list that cannot be read holds nothing (a turn that waits on an answer still
runs, so its status reads `Busy`). Otherwise it is `Busy` while `GET /session/status` has an entry for the session whose
`type` is not `idle` (`busy`, `retry`, or none), else `Idle`; only a server whose status route answers no JSON object is read
from its last assistant message instead (`Busy` while it has no `time.completed`). Its `abort` reads that route the same
way, so an abort of a session OpenCode is retrying is not settled until the session's entry is gone or `idle`. One choice
differs from what this ADR had proposed for 645b, and #646 and #649 build on it: the activity read is of the pane's session
of record, which section 11 (#839) makes the session the hub drives. The first message does **not** go through
`HarnessPort::send_prompt` since #839: it goes through the hub's one prompt path (section 11, point 5).
`HarnessPort::send_prompt` remains the adapter's transport, with no verb or engine caller; a test fails if one appears. The
adapter's `send_prompt` stays pure transport: a
hold, a limit or a park belongs at the hub's choke point, not in an adapter.

**Launch and relaunch as built (#644).** `pane launch PANE --herdr-session NAME` and `pane relaunch PANE`, each with the
spec flags, `--profile` and `--spec-only`, run one engine over the ports, `holler_pane::tx_launch`, which `profile apply`
(#664) calls unchanged. Its plan writes nothing and moves nothing: the spec names the pane, a launched name has no record
(`pane-exists`), the port policy is the `fixed:<port>` form of section 3 (launch accepts no other), the harness builds the
server's argv from the in-flight spec's `ServeSpec` (`serve_command`, pure, the plan's first call since #802, so its
`agent-unsupported` is exit 3 with nothing written; that stays the plan-time refusal of a harness that cannot apply an agent
at all, while for the OpenCode adapter a refused agent is exit 3 after acting and rolled back, as the act's second
`port-in-use` check is: its `verify_serving` refuses `agent-unusable` after the health wait, #642 part 3), a check passes
when the spec has one (a failing result is not stored),
Herdr's version is supported, the target cell holds no Herdr pane (`grid-occupied`, judged by Herdr's snapshot alone,
recorded or not: a pane is never adopted) and no server answers on the port (`port-in-use`, never adopted). The act ensures
the Herdr pane and the tmux session, runs the spec's `command` in that session as an argv, checks the port again (a server
that took it since the plan is `port-in-use`, from the act), runs the planned server argv there (both runs through
`HostPort::run`, in the spec's directory), waits for the server's health within the run's budget, has the harness say
whether the server honours the spec (`verify_serving`), creates the session of record through the harness API (never a ping
session), attaches the TUI to it, and observes that the TUI shows it (SHOWN equal to `session_of_record`, which I2 makes the
session the hub drives) and that Herdr still lists the pane. A mismatch observed after the act is `unavailable`: a closed
failure code, since I3 asks for exit 1 and an open code is a refusal. Only then is the record written, by one
compare-and-swap, with no `harness.pid` (#802): `last_observed.shown` is that observation, and `driven` is never inferred
(launch writes none, relaunch keeps the stored one). The model, effort, environment names and ceilings are recorded, not
applied: no port carries them yet (#829; they will join the `ServeSpec`). A failed step rolls back what the run made
(it stops the tmux session's processes, the server among them since #802, and closes a Herdr pane the plan's snapshot did
not list); the tmux session and a created harness session stay, as no port call ends them, and a record write that conflicts
is not rolled back. Relaunch first stops only what the pane owns, its server among them (`stop_owned`: TERM, the grace, then
KILL), and fails loudly when the old server still answers after that, never adopting it; it keeps the pane's directory,
moves its cell only with `--grid` (both rules are the engine's own, so every
caller is held to them) and keeps the session of record the restarted server still lists (a new conversation is
`pane reset`'s). After a move it records the new pane before it closes the old one, so a close that fails leaves an extra
pane with no record, never a record naming the wrong pane; the run then exits 1 with `unavailable` and P keeps its edit.
Every failure once the act has started ends with the reconcile step of step 6, appended only when the message lacks it.
The pane's OpenCode agent travels in the `ServeSpec` (#644): the in-flight spec's `opencode_agent`, which is `--agent KEY`
or else the base spec's (so a relaunch without the flag keeps the recorded agent), and the record names it. Only the
running server can say which agents it has, so the verbs read no project file and add no check of their own: a server that
does not honour the spec's agent is `verify_serving`'s refusal, an open code the harness owns, which ends the run with exit
3, that code, and the harness's message followed once by the reconcile step; the rollback stops the server, no record is
written, and with `--profile` P's specs are put back (I8). A relaunch meets that refusal after its old server was stopped,
so the pane is left with no server and its record unchanged; `relaunch PANE` without `--agent` brings it back on the
recorded agent. A successful run reports the agent the record names: the text line gains `, agent KEY` after the harness
port (nothing for a pane with no agent; the key prints by the line's rule for stored strings, so a key `-` is quoted), and
the JSON `data` gains `agent` after `spec_only`, the record's `opencode_agent` or `null` (`null` with `--spec-only` too). A
run is bounded as section 12 records. `--herdr-session` is required by `launch`, and is needed by `pane import` and by
`profile apply` to create a pane, because the frozen `HerdrPort` cannot tell the engine its session. The wiring (#649) does
not default it from the Herdr adapter's one configured session, and no story is planned to: the cutover (#654) names the
session. What a failure or a
crash leaves is not all reported by the merged doctor: only a whole-fleet pass reports a Herdr pane no record names
(`unregistered-herdr-pane`, which no verb removes, so the next launch at that cell is `grid-occupied` until the operator
closes it in Herdr), and no pass sees a server or a tmux session that no record names. A rollback and a crash leave
different things (#802): a rollback stops the server it started, since the server is a process of the pane's session; a
crash runs no rollback, so its server stays, tagged, in the pane's tmux session, and the next launch of that name is
refused with `port-in-use`. With no record, neither `close` nor `relaunch` can stop that server, and no doctor pass sees
it.

**Close as built (#646).** `pane close PANE [--profile NAME] [--spec-only]` keeps its engine in its own file
(`holler-cli/src/pane/close.rs`). Its plan writes nothing and moves nothing: with `--profile P`, P is read
(`profile-not-found`) and must hold a spec for the pane (`pane-not-in-profile`). The key is spec presence, not membership,
and it is checked before `edit_spec`, whose no-op `Remove` of a missing spec would still write P and bump its generation;
a live close then reads the record (`pane-not-found`). The act is `HostPort::stop_owned`, `HerdrPort::close` on the recorded
pane id and `PaneStore::delete` at the generation the plan read, each only after the one before it succeeded, and no
`ensure_pane` or keystroke, so no pane moves in Herdr (I4). Since #802 the pane's harness server is a process of its tmux
session, so `close`'s `stop_owned` stops the server too; before, the server outlived the close. The close is its own
observation: no snapshot is read after it.
With `--profile` the act runs inside `edit_spec(P, pane, Remove, act)` (step 3: the record delete is inside the act), so
a failed act restores P's specs and P's generation moves by two; a successful close moves it once. `--spec-only` removes the
spec with no act and needs no record (a detached spec for a gone pane is what it cleans up). Without `--profile`, no profile
is read or written. A failure from `stop_owned` on names the pane and the step it reached (a delete that fails after the
close says the pane is closed and its record was not deleted) and ends with step 6's reconcile step for the run's profile,
built by `reconcile_step` and appended only when the message lacks it; a plan refusal and a first-write conflict carry none.
A Herdr pane already gone is not treated as closed: `close` answers Herdr's error, with the step.

**Apply as built (#664).** `holler profile apply NAME [--dry-run] [--take-over] [--herdr-session NAME]` runs one engine
over the ports, `holler_pane::tx_apply`, which calls `tx_launch` unchanged. **To adopt** a pane is to record that a pane
which already has a record, is healthy and matches its spec belongs to P, and to touch nothing live: its `Pane.profile`
becomes P by one compare-and-swap (the join), or under `--take-over` by two (the leave from its profile, then the join),
and nothing is written when it is in P already. That is the only adoption in this ADR, and it adopts a record, never a
process: a Herdr pane, a tmux session or a harness server that no record names is still never adopted (launch refuses
`grid-occupied` and `port-in-use`, and `pane import` (#650) is what records existing panes). Apply reads P and the
registry; without `--herdr-session`, a spec pane with no record (a create) is `usage` before any Herdr or harness call,
in a dry run too. It then observes every recorded spec pane at once, one thread per call: a pane is healthy when `health`
answers true, Herdr's snapshot lists the record's Herdr session and pane id (never the cell or the label), and its TUI
does not show a session other than its session of record (a shown session that cannot be read does not count against
it). Each spec pane, in creation order (a workspace's column 1 by row, then the rest by row and column; see "Apply's step order" below), takes the first row that matches: a record of another profile
without `--take-over` is refused (`pane-in-other-profile`); a spec pane with no record is created through launch; a
healthy one is adopted when it matches its spec and reported with its `profile_diff` row when it differs, never
rewritten, moved or killed; one that is not healthy is relaunched in place when it is an agent, and refused
(`orchestrator-not-relaunched`) when it is the orchestrator. A refusal from the launch transaction is a refused step
with its code (`usage` for the spec is `spec-not-launchable`); a failure-class answer, a failed `health` or snapshot call
included, is a failed step that stops the run, and the later steps are skipped. A take-over moves the pane to P before
the step's live change: if the relaunch then fails the pane stays in P, and if the join fails after the leave landed the
pane is left in no profile, as the step's error says, and no re-join is written. Each step re-reads its record and P
before it acts, so the spec it hands to launch or relaunch is P's at that moment. `--dry-run` chooses every step from
the same reads and observations and calls nothing else (no probe, no split, no write); its steps that would act are
`planned`. The exit codes are the doctor form (section 9): 0 for a dry run that does not fail, or a real run with no failed or refused step, which prints
its steps (`{"profile", "dry_run", "steps"}` in JSON, the plan for a dry run); 1 for a failed step, which prints only
`apply stopped at <pane> (<action>): <step error>; <N> later step(s) skipped`, for a dry run too, since an envelope
cannot carry data with a failure; and, since #853, **3 for a real run that has a `refused` step and no failed one**
(see "Apply's step order and its exit code" below). A step is the object `{pane, action, outcome, code, diff, detail}` in
`data.steps[]`, whose absent `code`, `diff` or `detail` prints `null`: its `action` is one of `create`, `adopt`,
`report`, `relaunch`, `refuse` (rows a and e, and a spec whose pane is not a pane name) and `observe` (a recorded pane
whose `health` or snapshot call failed); its `outcome` is one of `created`, `relaunched`, `adopted`, `reported`,
`refused` and `failed`, or `skipped` after a failed step, or `planned` for a dry run's step that would act; its
`detail` is the step's own line, inside `data`, so it does not conflict with section 9's "the envelope has no
`detail`"; and a step whose launch or relaunch had started its act before it was refused or failed (since #802 the act
can refuse: the port's re-check, `verify_serving`) carries step 6's reconcile step, a `refused` step at the end of its
`detail` and a `failed` step in that failure's message, as `pane launch` does; in a real run that exits 3 for a refused step, the
reconcile step travels in the one-line refusal (see "Apply's step order and its exit code"). There is no budget over the whole run
(decided 2026-10-11): each create or relaunch runs under launch's own budget, so a run is bounded per step, as the
module doc of `tx_apply.rs` records.

**Apply's step order and its exit code (#853).** A missing pane is created through `HerdrPort::ensure_pane`, one cell at a time, and the Herdr
adapter's split planner (section 10, #640) adds a new row only below a row of one pane. So the order of the steps decides
whether a grid can be built. A scratch run (2026-10-12, on `main` at `b76f4d2`) showed that the old order, workspace then row
then column, made `r1c1`, `r1c2`, then refused `r2c1` and `r2c2` as `grid-unreachable` on an empty 2-row-by-2-column
workspace, and that launching `r1c1` and `r2c1` first, then applying, built all four. **The order is now the planner's own:**
by workspace, then the workspace's column-1 cells by row, then every other cell by row and column, so the cells of a
2-by-2 profile run `r1c1`, `r2c1`, `r1c2`, `r2c2`. The key is `cell_key` in `tx_apply.rs`; the planner, the port, the step
shape and the refusal codes do not change, and nothing is added to a record, a spec or the wire. The order is the order of
`steps` in the output, a dry run's plan included, and it is stable: specs of one cell keep P's order. What does not change:
an empty workspace still starts at `r1c1`, a gap (`r1c3` without `r1c2`) is still refused, and **one limit stays**, because
Herdr makes every pane by splitting one: apply cannot add a row below a row that already holds two or more live panes, so
creating `r2c1` beside a live `r1c1` and `r1c2` is still a refused step (`grid-unreachable`, "place rows before columns").
Apply moves nothing live to get round it (decision 32).

**A refused step now exits 3 (#853, decision 33).** Before, a `refused` step left the exit code 0, so the spike's run (two
`grid-unreachable` refusals beside two creates) exited 0 and a script had to read `steps`. The rule is the doctor form's
third case, using the repo's one convention for a refusal ("Exit codes are the same in both formats": 0 ok, 1 runtime failure,
2 usage, 3 refusal; ADR 0003's exit 3, a request understood and declined, working as designed). After a real run, in this
order: a `failed` step stops the run and exits 1 (unchanged); otherwise **any `refused` step exits 3**; otherwise 0. A
`reported` step (a healthy pane that differs from its spec, left alone) still exits 0. Refusals still do not stop the
run, so every step runs as before: the panes created, adopted or relaunched around a refusal stay, and nothing is rolled
back. Because the shared envelope has no `data` on a failure (`ok` is exactly "exit 0", decision 6), the run then prints only
the failure, in the form of a failed step's: in JSON the failure envelope with `error.code` the **code of the first refused
step in step order** (a refusal code, so `class_of` agrees with exit 3) and the one-line message
`apply refused <N> step(s): <pane> (<code>), ...; <M> other step(s) ran`, naming every refused pane with its code; **and
for each refused step whose launch or relaunch had begun its act, its `detail` follows** (`; <pane>: <detail>`, in step order),
so step 6's reconcile step (which the verb already puts at the end of that detail, once) and the step's take-over note when it
has one ("left profile X and joined Y before the relaunch, and stays in Y") are not lost, as `pane launch` and apply's own
failure line keep them. A refused step that acted nothing adds nothing beyond its pane and code: a refusal of the plan (rows a
and e), or of a launch or relaunch before its act began (a failed health check, an occupied cell). So a relaunch refused
before its act after a take-over does not say that the pane moved; `pane list` and `profile show` show it in Y (the rule keys
on the act alone, decided at #853's implementation; the step shape is not changed). In text it is
one `error:` line on stderr and nothing on stdout. A script that needs the steps as data runs
`--dry-run` first (it exits 0 and prints them), or reads `pane list` and `profile show` after. **A `--dry-run` is not
changed:** the only verb whose dry run finds blockers, `pane import`, exits 0 on a dry run and refuses only its real run
(section 14), so a dry run of apply that plans a `refused` step still exits 0 and prints the plan, as before. The wire,
the records, the step shape, the refusal codes and `class_of` are not changed.

**Rename as built (#665).** `holler profile rename OLD NEW` sends `profile/rename` with the generation of OLD it read, and the
hub does the whole change as one transaction under the profile lock and then the pane lock (section 7). The checks come
first and write nothing, in this order: either registry failed to load (`store-corrupt`); OLD not found by slug
(`profile-not-found`); NEW equal to OLD's stored name (`usage`); NEW's slug filed under another live profile
(`profile-exists`, whatever the generation); a stale or ahead generation (`generation-conflict`). The change: the profile
record takes NEW's name and slug and generation + 1 and keeps its `created` and specs; every pane record that is a member
of OLD (by slug) and does not already name NEW takes `Pane.profile` = NEW and generation + 1, and nothing else of it
changes, so no pane is detached, relaunched or touched live. The logs are filed by slug: OLD's gets one `deleted` entry and
NEW's exactly one `renamed {from}` entry at the new generation, with the request's actor; no entry is copied or rewritten,
and a deleted profile's older log under NEW's slug goes on. The profile feed gets the deletion of OLD then the put of NEW
(one put when only the spelling changed), the pane feed one put per member. Both documents are saved, the panes' first;
both registries' memory, rings and cursors change only after both saves succeeded, and a failed second save saves the
first document back (`unavailable`, nothing changed). If that save back fails too, the hub logs one `error` event,
`profile_rename_restore_failed`, and `panes.json` holds the members' moves until the next pane write saves the registry
again. A crash between the saves leaves the members naming NEW while OLD stands at its generation, and running the same
rename again completes it. A pane join that names OLD, checked before the
rename and written after it, is the same check-then-write gap `profile delete` has. The reply is the renamed record. The
in-process `ProfileStore::rename` of a registry with no pane registry (the fakes, and `ProfileState` called as a port,
which no hub path does) renames the record only.

**Prompting a pane as built (#646).** `say`, `interrupt` and `answer` with `--pane NAME [--profile P]` address the pane's
session of record, resolved in `holler-cli/src/say_cmd.rs` (`resolve_pane_target`, called by `interrupt_cmd.rs` and
`answer_cmd.rs`; #670's `prompt_target::route` stays as frozen, unused by them). In order: the pane name (`usage`), with
`--profile` the scope (`ProfileScope::resolve`, so `profile-not-found` and `pane-not-in-profile` are the helper's), the record
(`pane-not-found`), its session of record (`session-not-found`, naming the pane), and then what the record says: `hold`
parked (`pane-parked`), `harness.health` unhealthy (`pane-unhealthy`, with the reason), or `last_observed.shown` and
`.driven` both present and differing (`pane-shown-driven-mismatch`). The record is the source, never a live probe. Each is a
refusal, exit 3, its code in the one-line message (these verbs have no envelope); `--profile` without `--pane` is `usage`.
The routed `say --queue` sends the prompt queued with the user's `--timeout` as the turn's bound but waits for the hub only
`QUEUE_ACCEPT_WAIT` (2 s): a read deadline after that is reported `queued <session>` (JSON `{"queued":true,"session":...}`),
exit 0, since a refusal answers at once; a reply inside the wait prints as the bare form's. Only over the local control
socket: with `--server` the remote client cannot tell a deadline from a dropped connection, so the reply is awaited. The bare
`say --queue SESSION` still waits for the reply (#190).

**The pane-state prompt gate as built (#646).** `circuit::dispatch::send_prompt`, the hub's one sender of
`session/prompt`, refuses a prompt to a session that any pane records as its session of record while that pane is parked,
unhealthy, or shows a session other than the one it drives, by the predicate the CLI checks (`pane_state_refusal`; the
two copies exist only because `holler-pane` is frozen and the hub cannot depend on the CLI). It matches the bare session
name being sent, after `holds.admit` (an operator or default hold refuses first, with its own kind), by one synchronous
`PaneState::list()` with no `await`, and fails closed across panes of different bodies that record the same name: any bad
one refuses, the first in name order is named. The refusal is `-32011 session_held` with `data.hold_kind = "pane"`
(`hold_kind` is now `operator`, `default` or `pane`) and `data.reason` the pane code, a message naming the pane and the
code, and no `data.since` (the park's is epoch milliseconds, not RFC 3339). `holler release SESSION` does not lift it: there is
no hold entry, and the remedy is `pane unpark` or `pane doctor`. `say` and `interrupt` print it as exit 3 with that remedy,
not as a hold (exit 4); `answer` sends no prompt and is not gated. A pane registry that cannot be read gates nothing, as a
holds file that cannot be read leaves no holds. The registry reaches the gate through two touches outside the issue's
named files: `serve.rs`'s `build_shared_state` loads `PaneDeps` before the live registry and attaches its pane `Arc` with
`Registry::with_panes`, and `circuit.rs`'s one `HoldGate` construction passes `Registry::panes()` (`HoldGate` is no longer
`Copy`).

### 9. Failure taxonomy, and the CLI output

**Decided: two casings, kept apart by channel.**

- The **v2 wire catalog's error codes** are the closed `holler_proto::Code` table: 17 codes, each a JSON-RPC number and a
  `snake_case` `data.code` string (`method_not_found`, `session_held`, ...), documented in [protocol v2](../protocol/v2.md) §8.
  They appear only in JSON-RPC error frames, on the body circuit and for framing errors and unknown methods on the control
  socket.
- The **pane and profile codes** are `kebab-case` (`^[a-z]+(-[a-z]+)*$`, checked by `holler_pane::error::is_valid_code`, the
  workspace's one validator). They appear only inside a `PaneReply` (a JSON-RPC result) and in the CLI envelope's
  `error.code`, never in a JSON-RPC error frame. Neither table imports the other: `holler-proto` cannot see `holler-pane`, and
  no pane code is added to `Code`. That `holler-pane` also has exactly 22 closed codes is a coincidence; they are unrelated
  to the 22 catalog rows.

**Decided: closed and open pane codes.** The closed set (`ALL_CODES`, one `PaneError` variant each) is: `not-implemented`,

**Decided (decision 6): the `--format=json` envelope.** Every pane and profile verb and the roster take
`--format=text|json` (default text). In JSON mode stdout carries exactly one envelope, and every diagnostic goes to stderr:

```json
{"schema_version": 1, "ok": true, "data": {}, "error": null}
{"schema_version": 1, "ok": false, "data": null, "error": {"code": "pane-not-found", "message": "pane not found: hj-c1r1"}}
```

- `error` is `null` exactly when `ok` is true. `error.code` is the `PaneError` code verbatim and `error.message` its one-line
  text; the envelope has no `detail`. Each verb supplies only its `data`. The types and `emit()`, `emit_stream()` and
  `emit_usage_error()` are in `holler-cli/src/output.rs` (#670 creates it, #660 completes it).
- `pane watch` in JSON mode writes NDJSON: one envelope per line, flushed per line.
- **Exit codes are the same in both formats (operator, 2026-10-09):** 0 ok, 1 runtime failure, 2 usage, 3 refusal. A
  refusal is a request the system understood and declined, working as designed, so nothing was wrong with the system
  (`pane-in-other-profile`, `profile-secret-refused` and the like); this is [ADR 0003](ADR-0003.md)'s exit 3, a fail-closed
  policy refusal, carried to the new verbs. A failure is something that went wrong while doing the work (a timeout, an
  unreachable hub or adapter, a conflict between writers). A usage error under the `pane` or `profile` subcommands in JSON
  mode is an envelope with code `usage` and exit 2. In JSON mode `ok` is false for exit 1, 2 and 3 alike. Which `PaneError`
  code is a refusal and which a failure is decided once, in one function in `holler-pane`, `holler_pane::error::class_of`
  ([#676](https://github.com/Performant-Labs/holler/issues/676); see "Decisions taken", item 5). The CLI's output module and
  the test kit (#638) call it, and `ErrorClass::exit_code` turns its class into the number; the table below is its
  classification. An open code is always a refusal (exit 3), so a verb that reports a runtime failure uses a closed
  failure code; a malformed code is a failure. This **amends the epic's output contract**, which said refusals exit 1.

- Grid positions in `data` serialize through `GridPos`.

### 10. Grid notation (decision 7)

`GridPos { row: u16, col: u16 }`, 1-based, defined once in `holler-pane/src/grid.rs`.

- **Accepted input:** `r<row>c<col>`, `c<col>r<row>` (labelled, either order) and a bare `<row>,<col>` (always row first,
  never column first). Upper case and surrounding ASCII whitespace are accepted; `R2C1`, `c1r2` and `2,1` are all row 2,
  column 1.
- **`grid-ambiguous`:** interior whitespace, a missing half (`r2`, `c1`), a repeated label or a mix (`r2c1c3`, `c1r2c3`), more
  than two numbers (`2,1,3`), unlabelled digits (`21`), the empty string, anything unreadable, and a JSON `pos` that
  disagrees with its `row` and `col`.
- **`grid-out-of-range`:** a zero (`r0c1`, `c0r1`, `0,1`, `r2c0`) or a number above 65535; or, from `HerdrPort::ensure_pane`,
  a cell outside its workspace's rows and columns (`r1c2` in a workspace of 2 rows by 1 column), which the `HerdrPort`
  conformance suite pins (#638 amendment 2026-10-08, grid; #683). Herdr has no grid, so a workspace's extent is the Herdr
  adapter's configuration: rows by columns per workspace label (`HerdrConfig.workspaces`, #640), which the wiring supplies
  from `HOLLER_HERDR_WORKSPACES` (#649). A cell inside the extent that no single right or down split reaches is the open
  code `grid-unreachable` (#640).
- **Output** is always row first: text `r2c1`; JSON `{"row": 2, "col": 1, "pos": "r2c1"}`, in that key order. On input `pos`
  is optional.
- The Herdr adapter (#640) is the only code that converts a `GridPos` to Herdr's own order and base. `HerdrPort::ensure_pane`
  reaches a position by right and down splits (B4, `plan_splits`, #640) or fails loudly, and never relocates a healthy pane.
  `relaunch` moves a pane only when `--grid` is given. A pane's position comes from Herdr's snapshot, never from its name:
  `hj-c1r2` sits at `r2c1`.
- A pane's name is not its position and not its identity in Herdr: the importer (#650) finds a pane's live Herdr pane by
  `HerdrPane.label == name`. A pane with no cell has no place in the snapshot and is a finding of the importer, never
  recorded.
- **Decided (#650): the import's join.** It looks only in the Herdr session `--herdr-session` names (the snapshot filtered
  by `session`, as launch's occupancy check is), so a pane of the same label in another Herdr session is no candidate. No
  pane with the label is the problem `pane-unlabelled`, and two or more the problem `pane-label-ambiguous` (naming their
  ids): either way the pane gets no record, since guessing which pane is which re-creates the incident. The record takes
  the entry's cell and the entry itself with its label cleared (a label is observed, never recorded). A name `hj-<cell>`
  that spells another cell than Herdr's is the information finding `name-cell-differs`; the name never chooses a position.
- Herdr API versions (B5): the Herdr adapter checks Herdr's protocol when it connects, so no adapter exists for an unknown
  one, and `HerdrPort::version()` checks it again on every call; the other methods trust the check made at connect (#640).
  An unknown version is `herdr-version-unsupported`, and the message names the supported ones (#640, from #636's list). The
  string `version()` returns is recorded as `host.herdr_api_version` by a verb, never by the adapter (decided, operator, 2026-10-11:
  #644's launch and relaunch record it, so a pane's recorded version is the one seen at its last launch), and `doctor`
  shows it (#647).

### 11. How attach mode (ADR 0014) relates

[ADR 0014](ADR-0014.md) stays in force, extended by points 1 and 2 below (#839: the hub also resolves a session's harness
id as an address, and may ask the body to re-point); its teardown rule (point 3) and its rule against typing into a PTY
(point 4) apply as they are. What changes is **who chooses the session**. For a pane in the registry,
Holler creates the session of record: the pane verbs start the harness server (the argv `HarnessPort::serve_command`
builds, which `HostPort::run` starts in the pane's tmux session, #802), create the session over its API (`create_session`)
and attach the TUI to it (`attach_tui`). The body that drives that session is still not its
parent, so ADR 0014's teardown rule (point 3) and its rule against typing into a PTY (point 4, which I4 restates for pane
verbs) apply as they are. The difference is that the session id comes from `session_of_record`, which a verb writes after it
observes the session. It is no longer pasted by an operator or guessed by a repair. That answers ADR 0014's open "automatic
discovery of attachable sessions (e.g. from a Herdr pane)" for registered panes: there is no discovery; the registry names
the session. Attach mode with an operator-written `endpoint` and `session_id` stays for sessions Holler does not own (a
session with no pane record). The setup wizard (#803) builds registry panes only: it starts no backend, creates no session
and attaches no TUI, and runs one body on the hub's machine whose attach rows take their `endpoint` and `session_id` from
the registry. It no longer builds a session with no pane record.

`HerdrPort::send_text` and `send_keys` exist in the provisional port. Under I4 no verb may use them to change which
session a pane shows or what it is doing; #640 uses them only in its tests, which type into panes they created in a scratch
Herdr session, #646 names the permitted uses, and #645's tests fail on any keystroke.

**DRIVEN as built (#839).** The session the hub drives for a pane is the harness session that a live attach-mode body
advertises (`SessionAd.harness_session_id`, ADR 0014 point 6), and the hub joins it to the pane by that id. Decided under
the operator's standing rules (2026-10-11). Each point names what it rejected.

1. **The address is the advertised `harness_session_id`.** At the hub, `say`, `interrupt` and `answer` resolve a target
   that is a valid name (ADR 0005) by name, as before, and any other target as a harness session id, against the live
   attach sessions: no match is unknown, a match on an offline body is not connected, two matches are ambiguous. The hub
   marks the offline answer, `-32004 not_connected`, with an optional `data.reason` of `offline`; that is how a `--pane`
   verb tells a pane that no body drives from a prompt the body did not answer in time, which is the same code without the
   reason and keeps its text and its exit 1. A name is never an id (the name grammar refuses `_`, which every OpenCode id
   has); an id that happens to be a valid name is resolved as a name and is not routable by id. The id is an address for `--pane` resolution and the pane gate, not a form
   a person types: the `holler` CLI refuses a `SESSION` positional that is not a valid name (`holler say ses_… TEXT` is
   `unknown session`, as before) and sends an id only for `--pane`. This extends ADR 0005 section 3, ADR 0003's Addressing
   line and ADR 0014 point 5 and its Consequences; the name is still the identity. The pane gate (`pane-parked`,
   `pane-unhealthy`, `pane-shown-driven-mismatch`) is keyed on the advertised id of the session being prompted, however the
   prompt addressed that session, and selects the panes whose session of record or recorded DRIVEN it is; it is no longer
   keyed on the session's name, so a bare `say` to a body session that drives a parked pane's session of record is refused
   too. One predicate, `holler_pane::gate::prompt_refusal`, decides the three refusals for the hub's gate and for `--pane`;
   their messages stay where they are. Rejected: joining on the pane's name (nothing makes a body's session name its
   pane's name, and the join would be a naming rule imposed on a fleet); a new field of `Pane` naming the body session (a
   second source of truth beside the advertisement, and a change of the stored record); a new request to ask a body which
   session it drives (presence already carries it); keeping the name match beside the id match (two keys, and only test
   fixtures match the old); keying the gate on the session of record alone (a body that is behind would not be gated);
   letting a bare id work as a typed SESSION (a second typed address, and a stale id would reach a body).
2. **A body is re-pointed, not restarted: `session/rebind`.** A new additive request, hub to body, `{session,
   harness_session_id}` answered `{session, harness_session_id}` (protocol v2 section 4; the catalog has 23 rows). The body
   re-points one of its own attach sessions to another harness session on the same endpoint, after the existence check
   `attach` makes (never `session/new`), and only when the session is idle: a session that is not an attach session is
   `invalid_params`, an unknown name `unknown_session`, a busy session or one holding a question `session_busy`, an id the
   endpoint does not have `invalid_params` with the old binding kept, an endpoint that does not answer within 5 s
   `not_connected` with the old binding kept (an attach that finishes after the deadline is dropped, never swapped in). The
   session's name does not change, so its address and its hold key do not (point 4); ADR 0005 section 3 says the name is
   the identity and the locator changes. The session task's own configuration is the one source of the id a body attaches
   to: the rebind writes the new id there once the new driver has attached, so the re-attach after a turn that ended in
   error and the attach retry follow it, and presence and `query/support` read it from there. The hub sends the request
   through its own `LiveHandle::rebind`, not through the generic request forward, whose allowlist is unchanged, so
   `control/query_remote` and `admin/query` cannot carry it. `control/rebind`, a method of the local control socket only
   (there is no `admin/rebind`), is bounded by 8 s (the CLI waits 10 s) and, before it replies, updates the hub's cached presence and the
   body's roster rows, so a read after the reply sees the new id. One forwarded request is in flight on a connection at a
   time: the circuit has one reply slot, shared by `session/answer`, `query/*` and the rebind, and the hub serialises the
   three. Only the HTTP attach driver implements it; a body for another harness implements it in its own driver. Rejected:
   restarting the body with a new configuration (not bounded by I5, and the CLI would supervise a process and rewrite a
   file the wizard owns); a new body session for each harness session (a new name is a new hold key, so `--join-held`
   would default-hold every reset); the hub or the CLI posting the prompt to the pane's server (an adapter in the hub, and
   a second way to deliver a prompt); leaving it to the cutover (the first message of `reset --first` could not be
   delivered, and the gate would refuse everything as `pane-shown-driven-mismatch`); allowlisting the request on the
   generic forward (`control/query_remote` and `admin/query` would carry it without the cache update); persisting the
   binding across a body restart (state for a window the cutover does not need).
3. **DRIVEN is observed, never inferred, and the hub does not write it (I6).** The pure function
   `holler_pane::driven::driver_of` finds the body that drives a pane, and accepts a body only on positive evidence. A
   body that advertises another pane's session of record, or another pane's recorded DRIVEN, is that pane's and is never
   a candidate for any rule below, the fallback included. The exception is a body that also advertises this pane's own
   session of record or recorded DRIVEN: this pane's evidence is checked first, so a stale DRIVEN on another pane never
   takes a pane's own body. Of the bodies that remain, those that advertise the pane's session of record are its drivers; else those that advertise its recorded
   DRIVEN (the record's own memory, which finds a body whose session the pane's server no longer lists); else, for a
   switch, those that advertise the session being switched to. One match is the driver and more than one is ambiguous.
   With no evidence a body counts
   only if the pane's server lists no other pane's session of record (servers that share a data directory list each
   other's sessions, so a listed id proves nothing there), lists the body's id, and the body is the only such one;
   where the listing is shared, a listed body is unproven. Ambiguous and unproven bodies are refused alike. The port
   `HubPort` (`advertised`, `rebind`, `prompt`) reads the hub through its control socket. A switch or reset writes
   `last_observed.driven` in the same compare-and-swap as the record, from the id the body acknowledged to `rebind`
   (`None` when no body drives the pane; a body already on the target is not asked); reconcile reads `advertised` once
   per pass and records what it found with `shown`. `shown-driven-mismatch` is also reported when an observed DRIVEN
   is neither SHOWN nor the session of record; `--fix` repairs only the TUI side, and a body that is behind is
   `not-fixable` with the finding's own remedy `holler pane switch PANE SESSION` for the session of record, which is
   idempotent. The order of a switch or reset is: plan (the refusals of section 8, then the driver, then for `--first`
   the gate's answer), act, observe, rebind, record, first message. A switch whose target another body, not the pane's
   driver, already advertises is refused in the plan, before anything moves (two bodies would drive one harness
   session, which ADR 0014 leaves undefined; a body the rule above removed counts as one that advertises it). The rebind comes after the observation so that a failed `select_session`
   leaves the body where it was and `doctor --fix` restores the rest. If the record's write fails after the rebind,
   the body is ahead of the record: `doctor` reports it and `pane switch` re-points it back; nothing is compensated
   (section 8). A body restart reverts a re-pointed body to the session in its configuration (the binding is not
   persisted). When the pane's server lists only its own sessions, `doctor` finds the body, reports it the same way,
   the same remedy re-points it, and the gate refuses prompts to it once its id is recorded as the pane's DRIVEN. When
   servers share a data directory, a reverted body's configured id is nobody's session of record and nobody's recorded
   DRIVEN, so nothing proves whose body it is: the verbs refuse `pane-not-driven`, naming each listed body, and the
   operator makes the pairing explicit by switching the pane to the session its own body drives, then to the session
   of record. `launch` and `relaunch` keep the stored DRIVEN and never infer it, so a relaunch onto a new session (the
   restarted server no longer lists the old one) leaves the body on the old session; the body advertises the stored
   DRIVEN, so `doctor` finds it, reports the mismatch and `pane switch` re-points it. If no DRIVEN was ever recorded
   for the pane, nothing finds that body and it must be restarted with the new session in its configuration. The
   window that remains: a body that is behind and that no pass or verb has yet observed is not refused by the gate.
   Rejected: the hub writing DRIVEN (the hub is the store only, ruling 1); recording the session of record as DRIVEN
   without observing it (inference); driving before the act (a failed select would leave the body moved, with no
   repair); choosing among ambiguous bodies by order (a wrong pairing, silently); taking a body to be a pane's because
   the pane's server lists its id (shared listings); joining on the body's attach endpoint (a `query/status` per body
   per pass, and endpoint strings to compare).
4. **Hold keys.** A hold is keyed `<label>/<session>` by the body session's name, which a rebind does not change, so an
   operator or default hold carries across a switch or reset, and `--join-held` (which holds a name on first sight) does not
   fire again. A hold stops prompts, not a rebind.
5. **`reset --first` goes through the hub's gate: asked before the act, sent after the record.** Before anything moves, the
   plan asks the hub whether it would admit the prompt (`control/say` with `check_only`, which resolves the id and runs the hold
   and the pane gate, the same functions `send_prompt` calls, and sends and logs nothing), so a refusal creates no session and
   leaves the session of record, SHOWN and DRIVEN as they were. After the record, the prompt is queued through
   `send_prompt`, accepted and returned within the accept wait (2 s) and never waiting for the turn (I5). `send_prompt` stays the
   only authority: a pane parked, held or made unhealthy between the question and the send is refused there, and then the
   reset has completed and the first message did not land (section 8). Rejected: rolling the switch back on a refusal (no port
   deletes a session, so the created session would stay as a stray and nothing would be "unchanged", and undoing the TUI is a
   second act that can fail); no question before the act (the record would change and only the message be refused); a plan-time
   check without the hub (a third copy of the predicate, blind to holds). `HarnessPort::send_prompt` stays as the adapter's
   transport and no verb or engine calls it.
6. **A pane no body drives.** DRIVEN is then `None`; a switch or reset works as before without the rebind; `say`,
   `interrupt` and `answer` with `--pane` answer `pane-not-driven` (they were `unknown session`); `reset --first` is refused
   `pane-not-driven` before anything moves, as it is when the body does not advertise the pane's session of record, and when
   more than one body could drive the pane, or none can be shown to be its own, and the call names none of them (point 3). Only an OpenCode attach body exists
   today. A Claude Code pane (#831) is in this case until a body can drive it (#850), and its switch and reset, which are a relaunch, ask the hub nothing; the join is a string comparison of the
   advertised id with the session of record, so its session id joins the same way once a body advertises it, and that body
   implements `session/rebind` in its own driver.

### 12. Long-running work and the operation id (I5)

**Decided:** the hub runs no adapters (ruling 1), so it executes no long work. The CLI process that runs a verb executes
every step, and every port call is bounded by I5 (default 10 s) or ends in `timeout`. A verb that times out stops,
compensates as section 8 says, exits 1 with `timeout`, and prints the reconcile step. A crash between steps leaves state that
the next pane doctor run finds and reports (#644's acceptance). No verb leaves work running after it exits, except in the
probe runner's three documented cases, which section 1 records: a `try_wait` error, a child that escapes the probe's
process group and a missing `kill` binary (#663).

**Decided (operator, 2026-10-09): the operation id is deferred to #644, with an amendment to the contract first.** It needs two things the frozen contract
does not have: an executor that outlives the CLI process, and a place to record an operation's progress. `Pane` refuses
unknown fields and has no operation field, and `PANE_METHODS` has no operation methods. Two options are on record for #644 to choose from, after the OpenCode and Herdr spikes show real launch times:
(a) the verb starts a detached worker process of the same binary and returns an id, the worker records progress in a new
hub-held operation store (new control-socket methods beside `pane/*`), and the hub still runs no adapter; or (b) a hub-side
executor for long work only, which narrows ruling 1. Until one is chosen, I5 is satisfied by the per-call bound and the
loud `timeout`, not by an operation id.

**Decided (operator, 2026-10-11; proposed by #644): no operation id yet.** Neither option is built: both need frozen
files outside #644's reach (the `Pane` record or `PANE_METHODS`, and the hub), and the spikes show that a launch is short.
The OpenCode server is healthy 630-740 ms after it is started, a TUI shows its session in about 1.6-1.7 s and a restarted
server is healthy in about 645 ms, so a launch takes about 3 s of the 10 s bound. `pane launch` and `pane relaunch` meet
I5 with a budget for the whole run (10 s from when the engine starts, checked before every live step; once it has run out
the run rolls back and exits 1 with `timeout`, whose op is `pane.launch` or `pane.relaunch`), each port call's own bound and
the reconcile step. A run takes at most the budget plus one port call's own bound plus its rollback calls. If a measured
launch later exceeds the budget, options (a) and (b) stay on record and a new decision reopens this section.

**Decided (#647): no hub timer.** Under ruling 1 the hub runs no adapters, so it cannot reconcile: the periodic pass is the
CLI verb itself, which a scheduler runs as `holler pane doctor --format=json` (without `--fix`) as often as wanted, each run
recording `last_observed` and `harness.health` where they changed. The engine (`holler_pane::reconcile::reconcile`) takes
only the ports and a request, so a later daemon or `--every` loop can call it unchanged. None is built now: a pass keeps no
memory between runs, so every tick would report every standing finding again, and suppressing them needs stored state that
a later story may add.

**Decided (#647, part 2): `unattached` and `agent-cannot-dispatch`, each from one new read-only port method.** Reconcile
reads the world only through the ports (I6), and no port could observe either finding. The operator allowed the contract
change on 2026-10-11 (decisions taken, below). Both methods are **required**, with no default, for the reason in section
2 (#835): a default answers silently in place of a port a wrapper did not forward, and the compiler finds a wrapper that
left one out. #649's wrappers forward both, and a test per wrapper pins it.

- **`HostPort::attached_clients(name) -> Result<u32, PaneError>`**: the number of tmux clients attached to the session
  `name`, as tmux counts them (`#{session_attached}`). A fresh session made by `ensure_session` has none. A missing
  session is `pane-not-found`, as `ps` answers. A count only: never a client's name, tty or process (I7).
- **`HarnessPort::agent_view(at, session, max_turns) -> Result<AgentView, PaneError>`** (`at` is the pane's
  `HarnessEndpoint`, #831): what the harness server says about the agents of `session`, in one call. `HarnessRouter`
  routes it by endpoint, and a single-process harness answers an empty view for a process endpoint and, as section 15
  item 5 has it for every step of the other shape, `server-unsupported` for a port, so a misrouted call is loud.
  `AgentView` is `#[non_exhaustive]`, with builders and an empty default, as `PaneObservation` is.
  - `turns`: for each of the last `max_turns` user turns of `session`, oldest first, a
    `TurnAgent { agent, can_dispatch }`. `agent` is the key the server recorded for the turn, `None` when it recorded
    none or a name that is not an `AgentKey`. `can_dispatch` is `Some(false)` only when the server's permission rules
    for that agent deny the `task` permission for every subagent (OpenCode: the last rule whose permission is `task` or
    `*` and whose pattern is `*` is `deny`, and no later rule whose permission is `task` or `*` allows another pattern
    or asks for it), `Some(true)` when they do not, and `None` when the server does not say, the agent is not in its
    list, or the rules have a shape the adapter does not know.
  - `dispatchers`: the agents the server lists that a pane could run as its default (not a subagent and not hidden: the
    rule `verify_serving` applies), that are not the harness's own (OpenCode: `native` is false), and whose
    `can_dispatch` is `Some(true)`. Sorted by key, without duplicates; a name that is not an `AgentKey` is left out.
  - An implementation that cannot tell answers an empty view, never a guess. A session the server does not have is
    `session-not-found`; a reply of the wrong shape is `unavailable`. The OpenCode adapter reads
    `GET /session/:id/message` and `GET /agent`, and never a file.
- **`unattached`** is raised when `host.ps` answered for the pane (the session exists) and `attached_clients` is `0`.
  The rule is "no tmux client at all", not "a client in the Herdr pane the record names": telling which Herdr pane
  displays a tmux session needs Herdr's `pane.process_info`, whose answer is whole command lines (I7; section 13 refuses
  it), so a client attached in some other terminal hides the finding. `HerdrSnapshot` and `HerdrPane` do not change. The
  finding names no command: no Holler verb attaches a tmux client to a Herdr pane (`launch` and `relaunch` attach the
  TUI inside the tmux session; `launch` refuses a registered pane), and its message says so.
- **`agent-cannot-dispatch`** is raised when all of these hold: the record names no agent (`opencode_agent` is absent; a
  pane whose record names one chose it, `build` included); the pane's harness is OpenCode; its server is healthy and
  lists the session of record; `agent_view(at, session_of_record, 3)` answers at least one turn and every turn has
  `can_dispatch` `Some(false)`; and `dispatchers` is not empty, which is what "the project ships an orchestrator" means.
  "Recent hub-delivered turns" are the recent turns of the session of record, which I2 makes the session the hub drives:
  OpenCode records a turn's agent, not who sent it. The remedy is `holler pane relaunch PANE --agent=KEY` when
  `dispatchers` holds exactly one KEY; with several there is no remedy and the message lists up to three. `--fix` does
  nothing for either finding.
- **Reads and writes.** A server's chain makes at most nine port calls, each bounded by I5 (`attached_clients` and
  `agent_view` are the two new ones), and a single process's chain gains `attached_clients`. The OpenCode adapter's
  `agent_view` reads the session's whole message list: OpenCode 1.19.0's `limit` counts every message, not user turns,
  so no limit promises the last three turns. A reply past the adapter's 64 MiB cap, or one not read within the call's
  bound, is `observe-failed` naming `harness.agent_view`, and nothing is concluded. Neither finding writes the record,
  and each is raised once per pass.

### 13. Migration from the launcher's files

Each file below is replaced by registry state:

| File | What it held | Replaced by |
|---|---|---|
| `sessions.toml` | the session the launcher recorded for each pane | `Pane.session_of_record` |
| `last-session` | the last session a pane used | `Pane.session_of_record`, with `last_observed` for what was seen |
| `owned-sessions` | the sessions the launcher created for a pane | `session_of_record`; any other session on the pane's server is a stray-session finding from reconcile (#647) |
| `pane.env` | a pane's model, effort and environment | `Pane.model`, `Pane.env` (names only; values stay in the operator's own environment), `Pane.context`, and the spec |
| the launcher's port and directory table | each pane's port, directory and launch command | `harness.port`, `host.cwd`, `command` (an argv; a shell-string command is a finding and is imported without a command) |

The hub's own registration, the fifth record of the incident, is replaced by `session_of_record` once a body is re-pointed
to it (#839, section 11); the cutover (#654) starts one attach body for each pane.

**Decided (#650): the launcher table's shape.** The repository held no sample of the launcher's port and directory table, so
the import defines it, as one TOML file (`<state-root>/launcher.toml` unless `--launcher FILE` names another): one table per
pane, keyed by the pane's name, with `port` (an integer from 1 to 65535), `cwd` (an absolute path) and `command` (an array of
strings, an argv; a string is a shell command, the `command-not-argv` finding, and the pane is imported without one). No other
key is accepted, and the port is never derived from the name. A file that is not TOML or not this shape is `source-unreadable`
for every pane, naming the file and the line and column of the error, never the parser's text (it quotes the file). A pane
with no entry, or an entry without its `port` or `cwd`, is `source-missing`. If the live fleet's table has another shape, the
cutover's dry run says so, and the fix is a one-file export, not a code change.

**Decided (#835): a pane that runs Claude Code is left alone.** Some fleet panes run a Claude Code CLI session, not an
OpenCode server, and the launcher's files cannot tell them apart. So the import reads one more thing per pane, after `ps` has
answered and on the pane's own thread: the command names of the pane's tmux session, through the required
`HostPort::foreground_commands(name)` (section 2). It answers the command name of the foreground process of each live pane of
the session, in tmux's order (`[]` for a session with no process; `pane-not-found` for a missing session, as `ps` answers).
The tmux adapter reads it as `#{pane_current_command}` from the `list-panes` listing `ps` makes, with a parser as strict as
`ps`'s. Names only: never an argv, a command line or Claude Code's configuration directory (I7), and never Herdr's
`pane.process_info`, which returns whole command lines.

- **The rule.** A pane is left alone when a live pane of its tmux session has the command name `claude`, exactly. It gets
  one finding, `harness-claude-code`, and nothing else: no record, no harness call, and it blocks nothing. The finding's
  level is `info` and the row's action `skipped`, where `harness-not-opencode`'s level is `skipped`: a deliberate
  difference, since `--adopt-claude-code` adopts these panes (#831, section 15, item 17). A
  whole-fleet `pane doctor` then reports the pane as `unregistered-herdr-pane`, as expected. Any other answer is imported as
  OpenCode, as before: `bash` (the old launcher's OpenCode panes run its `oc-holler` script under bash), `opencode`, or a
  session with no process. So a pane whose OpenCode server is merely down is still recorded and flagged `server-down`. Only
  `claude` is classified, in one place: `holler_pane::pane::CLAUDE_CODE_COMMAND` and its predicate `is_claude_code_command`,
  which #831 can reuse. The name is a process name, not the protocol's harness id `claude`, though the two are spelled alike.
- **Never recorded on a guess.** These are each the problem `harness-unreadable`, so the pane gets no record and a real run
  is refused (`import-blocked`): a read of `ps` or of the names that fails with anything but `pane-not-found`, and a pane
  whose check did not finish. A `pane-not-found` from either read is `tmux-session-missing`, as before. A pane is recorded
  as OpenCode only when its names were read and none is `claude`. Under #650 a failed `ps` was an `observe-failed` warning
  and its pane was recorded; this reverses that.
- **The rule's limits.** tmux names a pane's foreground process by its `argv[0]`, where the old launcher looks for `claude`
  among every argument. So a Claude Code pane is imported as OpenCode when its `claude` has exited (the pane shows its
  shell), is not in the foreground (a wrapper script that stays in the foreground runs it, so tmux names the script's
  interpreter; or it is suspended, so its shell has the foreground) or was started under another `argv[0]` (a wrapper
  that `exec`s it under another name, or `node` running Claude Code's script). The rule is a default for the first real
  import, not a proof of what a pane runs, and the dry run of that import is the check.
- **The switch.** `--adopt-claude-code` adopts these panes too (#831, section 15, item 17 "As built"). #835 made it a
  refused argument (`usage`, naming #831) until the adoption was built; #831 replaced that one refusal. Without the switch
  the rule above is unchanged, and its finding now says "pass --adopt-claude-code to adopt it, otherwise the import leaves
  the pane alone".
- **Not the registry's rule.** The question is what a pane's process is, not whether a record names it. The rule of
  `holler_pane::unmanaged` (a pane that no record names, section 14) holds for every import candidate, since the import
  skips a pane that already has a record. So it cannot tell a Claude Code pane from an OpenCode one, and the import does
  not use it.

The order:

1. `pane import --from <state-root> --herdr-session NAME --dry-run` (#650) reports every disagreement between these files and
   what Herdr, tmux and the harness show, and writes nothing.
2. The real run writes one record per pane, or nothing at all. It sets `session_of_record` only where the sources agree and
   the pane's healthy server has the session; where the files agree and the server does not have it, or cannot say, the record
   has none and the report has a finding. **Narrowed (#650, operator decision 4):** files that name different sessions are the
   problem `sources-disagree` and give the pane no record, and a real run is refused (`import-blocked`) while any pane has a
   problem, until the operator fixes the drift with the old tools. It takes each position from Herdr's snapshot, never from the
   name. It records model, effort, env names and ceilings (C1), creates the profile `fleet` with one spec per imported pane, and
   sets each pane's `profile` to `fleet`. It deletes nothing from the source files.
3. The operator cuts over (#654): from then on only pane verbs change panes, and the launcher's files are no longer read.
   Retiring the launcher's writers is pfleet's follow-up (#653), not Holler's. After seven days on the live fleet (#654) the
   operator recreates the Herdr workspace from the stored profiles (#666) and watches it for 24 hours (C4).

### 14. Unmanaged panes (#832, epic decision 9)

**Amended 2026-10-11.** A Herdr pane that no record names (today a Claude Code session set up by hand; since #831 every
`HarnessKind` is one Holler drives, so having no record is the only way a pane is one Holler does not drive), is invisible to
the registry: it is on no roster and in no `doctor` report. One night an orchestrator read
the same unchanged screen of such a pane about 25 times over four hours and called it working each time. The pane is now
**visible as `unmanaged`**:

- **`unmanaged` is observed, never stored** (decision 2: the registry stays the only record of a pane). It is a state a verb
  shows, not a hold and not a record field. A pane is unmanaged when `HerdrPort::snapshot` lists it and no record names its
  `(session, pane_id)`: the rule `unregistered-herdr-pane` uses. It is **one public rule**, `holler_pane::unmanaged::unregistered`
  (and `is_unmanaged` for one pane), that every caller uses instead of writing its own. The other half of "a pane Holler cannot
  drive", a record whose harness kind is not drivable, has no case: #831's second kind, Claude Code, is drivable (section 15),
  and the import tells a pane that runs Claude Code by its foreground command (`is_claude_code_command`, section 15 item 2), not
  by this rule.
- **`HerdrPort::observe_pane(pane) -> PaneObservation { cwd?, last_screen_change? }`** is the one new port method. It has a
  contract, not a default, since #835: every implementation answers it, a wrapper port by forwarding it, and one that leaves it
  out does not compile. (#832 gave it a default, `Ok` with both `None`, which would answer silently in place of a wrapper that
  did not forward it; #649's wrappers forward it.) An implementation that cannot tell answers `Ok` with both `None`;
  `pane-not-found` for a pane Herdr does not have. `observe_panes(&[PaneId])`, which keeps its default, is the same
  for several panes at once (an empty observation for a pane that cannot be observed), so a list of many unmanaged panes costs
  one call: the Herdr adapter reads every `cwd` from the `PaneInfo` of **one** `session.snapshot` (any tab, grid cell or not).
- **The time of the last screen change is whatever Herdr reports, and Herdr reports none.** Herdr 0.8.2 (protocol 20) has no
  such field: `PaneInfo.revision` stayed 0 while a pane printed, and `state_change_seq` moves only for agent reports (scratch
  run, #832). So the real adapter answers `last_screen_change: None`, and `idle_seconds` is `None` with it. Nothing here guesses
  a time from an earlier read or a file (I6). **The operator decided this** (2026-10-11): the port carries the field and the
  value stays unknown until a source exists (a Herdr that reports it, or a resident watcher with its own exception to
  decision 2), tracked in #837. Until then `unmanaged-stalled` cannot fire against real Herdr; every other part of the
  story works, and the test kit's `seed_unmanaged_pane` reports a time.
- **Where it shows.**
  - `pane list` (the whole registry only; a pane or `--profile` scope is a question about records): the JSON data gains
    `"unmanaged": [PANE, ...]` (left out when there is none), each PANE
    `{"state": "unmanaged", "pane_id", "session", "workspace", "pos", "label", "cwd", "last_screen_change" (ms since the Unix
    epoch), "idle_seconds"}` with `null` for what Herdr did not report. The text view adds a second table after a blank line
    (`PANE-ID LABEL POS PROJECT STATE IDLE`). If Herdr or the pane store cannot be read, the managed rows are still listed, JSON
    carries `"unmanaged_unavailable": "<code>"`, and text prints one `warning:` line on stderr: the gap is said, never hidden.
  - `pane get NAME-OR-ID`: when no record answers, a label or Herdr pane id of an unmanaged pane shows it (`state`, `pane-id`,
    `label`, `session`, `workspace`, `pos`, `project`, `last-screen-change` in UTC, `idle`); JSON data is the same object. Anything
    else is `pane-not-found`, as before (an unknown Herdr pane id too, not `usage`); a bad name that is not id-shaped stays `usage`.
  - The roster (#648) is not changed here: that story is in flight, and its columns can read `holler_pane::unmanaged::observe`.
- **No verb that acts on a pane accepts one** (`pane-unmanaged`, an open code, exit 3): `relaunch`, `switch`, `reset`, `park`,
  `unpark` and `close` refuse a label or Herdr pane id that names an unmanaged pane, where they would otherwise say
  `pane-not-found`. They look at Herdr only on that missing-record path, so a pane that has a record costs no extra read. An
  argument that is **not a valid pane name** (a Herdr pane id such as `w1:p3`, or a label, which Herdr allows to be any text:
  `Claude Code`, upper case, over 32 characters) would be `usage` before any lookup, so the dispatcher checks it first; `usage`
  stands only when no unmanaged pane answers to it. That is one read of Herdr and of the pane store on a bad name, never a write
  or a call that acts.
  `launch` and `import` create or adopt and are not acting verbs; the `say`/`interrupt`/`answer --pane` routes keep their own
  lookups and are not changed here.
- **`pane doctor --unmanaged-stalled-after SECONDS`** reports each unmanaged pane whose `idle_seconds` is at least the threshold
  as the finding `unmanaged-stalled` (message: pane id, label, idle time, threshold; no remedy, since no verb adopts a pane).
  There is no default: the threshold is the operator's, and without it nothing is reported. Whole-fleet runs only, as
  `unregistered-herdr-pane` is. A pane whose idle time is unknown is never stalled.
- **Limits.** The snapshot lists only panes in a workspace's grid tab, so an unmanaged pane in another tab is not listed (a pane
  with no cell stays out of the snapshot, as section 2 records). A failed `observe_pane` of one pane leaves its `cwd` and time
  empty; the pane is still listed.

### 15. A second harness: Claude Code (#831, epic decision 9)

**Amended 2026-10-11.** This is the contract amendment the amend-first rule puts before any code of story #831. It is
decided from the spike's note ([`docs/research/claude-code-pane-spike.md`](../research/claude-code-pane-spike.md), #830, PR
#833), whose findings are not repeated here. The words below win over the note where they differ. **A Claude Code pane is one
process, not a server and a TUI**: the interactive `claude` process is the harness, the TUI and the session holder at once,
and the pane's tmux session runs it (section 2, #802, decision 4).

**The abort decision (operator, 2026-10-11).** The spike asked whether one Esc keypress through `HerdrPort::send_keys` may be
an in-place interrupt. **The answer is no.** Abort for a Claude Code pane is **stop and relaunch with `--resume <session of
record>`**: it loses only the turn in flight and keeps the session. `AbortStyle` has the relaunch style first; an `InPlace`
style for Claude Code is not built, and nothing types into a pane (I4). The optional `PreToolUse` hook gate ("stop after this
step") stays a later, separate option. The research note's "Decisions" section records the same answer.

**Decided, in the order of the work.**

1. **The kind.** `HarnessKind` gains `Claude` (serde `claude`). `holler_proto::vocab::HARNESS_IDS` already lists `claude`, so
   no id is added and the test that pins every `HarnessKind` serde name to that list covers the new variant. The id has two
   uses that do not meet: a **pane** harness `claude` is the interactive CLI and is read only by the pane engine; a **body**
   harness `claude` (ADR 0012) is the ACP bridge and is read only by `holler-body`. The doc comment of `HARNESS_IDS` says so.
   `HarnessKind` gets two pure methods, the only place these facts live (a port method could be contradicted by a fake, and
   one source of truth is the epic's rule): `shape()`, `Shape::ServerAndTui` for `opencode` and `Shape::SingleProcess` for
   `claude`; and `abort_style()`, `AbortStyle::InPlace` for `opencode` and `AbortStyle::Relaunch` for `claude`.
2. **One command name.** `pub const CLAUDE_CODE_COMMAND: &str = "claude"` and `pub fn is_claude_code_command(name)` in
   `holler-pane/src/pane.rs`, beside `HarnessKind`, are the one place the name is written and the one rule that compares a
   foreground command name with it (#835's import, a Claude launch's `process-in-use`, #832's unmanaged panes). **One signal:** the read-only `HostPort::foreground_commands(name) ->
   Result<Vec<String>, PaneError>` that #835's amendment decides (required, no default, tmux's `#{pane_current_command}`, names
   only). This story adds no second signal and no second constant. **Order:** whichever of #835 and #831 lands second adopts
   the other's constant and method. If #835 has not merged when this story reaches its adoption step (item 17), this story
   builds the method and the constant to #835's brief, exactly (signature, required, `FakeHost`, conformance case, the forwards
   of the wiring's decorators), and #835 adopts them. **As built:** #835 had not merged when this story's F ran, so it copied
   #835's committed code and tests for exactly those (its branch at `9bd101b` and `36b0de8`: the constant and the rule, the
   required method, `TmuxHost`'s and `FakeHost`'s implementations, the host suite's case 10, the decorators' forwards). The
   API and the host-side code are #835's, unchanged: the constant's value, the rule, the method's signature, the
   implementations, case 10 and the forwards are the same on both branches (compared with #835's branch at `f1d1bd0`). The
   doc comments are not: #835 has since reworded those of `CLAUDE_CODE_COMMAND` and `is_claude_code_command` (and the module
   doc of `claude_code_rule_test.rs`), this story's doc of `HostPort::foreground_commands` also names the launch's
   `process-in-use`, and the constant sits after `impl HarnessKind`, which this story adds. So whichever of the two lands
   second keeps the other's API and code, and resolves a conflict in those doc comments of `pane.rs` and `ports.rs`, keeping
   the words that name both stories' uses. `HerdrPort::observe_pane`'s loss of its default, also on #835's branch, is #835's
   and is not copied.
3. **The endpoint.** A Claude Code process has no port. `holler_pane::ports` gains
   `enum HarnessEndpoint { Port(u16), Process { pane: PaneName, pid: u32 } }`, and **every `HarnessPort` method keyed by
   `port: u16` is keyed by `&HarnessEndpoint` instead** (`verify_serving`, `health`, `create_session`, `list_sessions`,
   `abort`, `send_prompt`, `session_activity`; `attach_tui` and `shown_session` gain it too, `shown_session(pane, endpoint)`,
   since a single process is read through its endpoint and not through a TUI). This changes the port rather than adding
   default-armed twins, as #802 decided (decision 2 there): a call site that forgets the endpoint is a compile error, and
   every implementation is in this workspace. `HarnessInfo.port` becomes `Option<u16>` (`#[serde(default,
   skip_serializing_if = "Option::is_none")]`), so every stored `opencode` record reads and writes the same bytes. A record
   is valid only when `opencode` has a `port`, and `claude` has no `port` and a `pid`; anything else does not load
   (`deny_unknown_fields` and the fail-closed registry, section 7). `HarnessInfo::endpoint(&self, pane: &PaneName)` is the
   one place a record becomes an endpoint.
4. **One router, `Ports` unchanged.** `Ports` keeps its single `harness: &dyn HarnessPort`. The wiring builds a router that
   implements the port and sends a call to the OpenCode adapter for `HarnessEndpoint::Port` and to the Claude adapter for
   `HarnessEndpoint::Process` (calls that carry only a kind, `serve_command` and `process_command`, are routed by the kind the
   spec names). The test kit's `FakeHarnesses` is the same router over `FakeHarness` and the new `FakeClaude`. So a grid that
   mixes the two harnesses needs no new field in `Ports` and no rig outside the harness fakes changes shape. **As built (plan
   review W5):** the router is one type, `holler_pane::HarnessRouter<S, P>` (`ports/router.rs`), since the test kit can name
   neither the wiring nor the wiring the test kit. A `ServeSpec` carries no kind, so the table routes by call: every method
   keyed by an endpoint by the endpoint's variant; `serve_command` and `select_session` to the server harness; the four process
   methods to the single-process harness. The wiring builds `HarnessRouter<WiredHarness, WiredHarness>` over the two adapters
   (each misconfiguration kept for its own first use), and `FakeHarnesses` wraps `HarnessRouter<FakeHarness, FakeClaude>` and is
   also the linker a rig's host calls (`start` of either fake's argv, `stop` of both fakes' processes of a pane): every rig
   that runs a `FakeClaude` links it through `FakeHarnesses`, and the three older rigs that run only `FakeHarness` keep their
   own linking.
5. **New methods, for a `SingleProcess` kind only.** Default-armed, each refusing `process-unsupported` (an open code, exit 3,
   in the style of `prompt-unsupported`), because the engines call them only for a kind whose shape is `SingleProcess`, and
   the OpenCode adapter never answers them:
   - `process_command(name, spec, session) -> Argv`, pure like `serve_command`: the argv that starts the process holding
     `session`. The adapter chooses `--resume <session>` when the conversation's transcript file exists (existence only; the
     contents are never read) and `--session-id <session>` when it does not, the verified rule of the note. Other flags are
     those of the note's argv: `--settings` with inline JSON carrying `crossSessionInbound: accept` and a `SessionStart` hook,
     `--model` and `--effort` from the spec's model, and `--disallowed-tools AskUserQuestion` always (see 11). The argv is an
     argv array (B2), carries no secret, and starts under `env -u` for each variable that changes the login (see 10).
   - `new_session_id() -> String`: a fresh id for a launch or a reset. The randomness is the adapter's (the engine takes none);
     the fake counts.
   - `locate_process(name, session) -> Option<u32>`: the pid of the running process that holds `session`,
     from `claude agents --json`, matched by session id, which Claude Code makes unique (`session-in-use`). Launch and relaunch
     call it to learn the pid they record; afterwards the pid is the identity (it survives a person's `/clear`).
   - `login_status() -> LoginStatus` (`Ok`, `Missing`): see 10.

   **As built (plan review W1, W9 and W10):** `process_command(name, spec, choice: &SessionChoice)`, where
   `SessionChoice::{Fresh, Keep, Resume}` carries the verb's intent: `Fresh` (launch, reset) is `--session-id`; `Keep`
   (relaunch, interrupt, doctor's repair) is `--resume` when the transcript exists and `--session-id` when it does not;
   `Resume` (switch) is `--resume`, or `session-not-found` when there is no transcript, so a switch keeps its refusal of an
   unknown target. `login_status`'s default refuses `process-unsupported` like the other three, never a silent answer, so a
   wrapper that forgot the forward fails loudly; `LoginStatus` has no `NotApplicable`, since the login is asked only of the
   Claude harness, through the router. `ServeSpec` gains `model: Option<ModelSpec>` and `cwd: Option<String>` (with
   `with_model` and `with_cwd`), which the launch engine sets only for a single process: an OpenCode server keeps `None` for
   both until #829, so `serve_command`'s rule holds for it unchanged. `HarnessEndpoint::port()` and `process()` are the one
   conversion each shape makes: a server harness answers a process endpoint `process-unsupported`, and a single-process
   harness answers a port, or a server's or a TUI's step, `server-unsupported`.
6. **Launch, relaunch, switch, reset and doctor's repair for a `SingleProcess` kind are relaunches.** The engines
   (`tx_launch`, `tx_switch`, reconcile's repair) skip `health` of a server, `create_session`, `list_sessions`, `attach_tui`
   and in-place `select_session`, and run this order: plan (every refusal of the plan: port policy, agent, login variables,
   `pane-exists`, grid), then `ensure_pane`, `ensure_session`, `stop_owned` (relaunch, switch, reset only), `process_command`
   and `HostPort::run`, a bounded wait that `locate_process` finds the session and the entry is `idle` (the wait ends with the
   run's budget, like `wait_healthy`; a `waiting` entry whose reason is `dialog open` is the refusal `harness-dialog-open`,
   rolled back), the record write with the pid. **Launch** chooses a fresh id; **relaunch** keeps the session of record;
   **switch** relaunches on the other session; **reset** on a fresh id. The session shown can then never differ from the
   session of record except by a person's `/clear` or `/resume`, which `shown_session` (the entry's `sessionId`) shows, and
   which `doctor --fix` repairs by relaunching on the session of record. A relaunch loses the turn in flight and keeps the
   session; `reset` and `switch` still refuse a pane that is not idle (`Activity`, below), so they lose none. Rollback after
   `run` is `stop_owned`, as for OpenCode.

   **As built (plan review W2, W3, W4, W10 and W11):**
   - **One sequence.** `tx_launch::relaunch_on(ports, request, &ProcessSession)` is `relaunch` with the session a single
     process starts on (`Keep`, `Resume(id)`, `Fresh`), and `relaunch_recorded(ports, record, session, options)` runs it for a
     pane relaunched as recorded (its own spec through `spec_from_pane`, its cell, its profile). `switch`, `reset`,
     `interrupt` and doctor's repair all go through it; a server pane's relaunch takes `Keep` alone (anything else is
     `usage`).
   - **The plan.** The port policy (`port_for`), the login variables and then `process_command`, first among the reads, so
     their refusals write nothing; a launch (never a relaunch, which stops what the pane owns first) refuses a tmux session
     that already runs Claude Code, `process-in-use`, through `HostPort::foreground_commands` and `is_claude_code_command`
     (a session that does not exist yet runs nothing). The fresh id is the harness's (`new_session_id`).
   - **The act.** A relaunch's B1 and B2 stop what the pane owns and check, through the old record's endpoint, that the old
     process no longer runs. Then `run`, and the wait: `tx_launch::wait_until`, the engine's one deadline-checked loop (which
     `wait_healthy` and `wait_located` also use), until `locate_process` finds the session and `session_activity` reports it
     idle, within the run's budget. The process is then seen holding the session (`shown_session` through its endpoint), Herdr
     must still list the pane, and the record is written with the pid and no port. `harness-dialog-open` is the adapter's
     answer to `session_activity` for a process held by a dialog, so the wait fails and the run rolls back.
   - **Doctor's repair (W2, W3).** Reconcile's chain of a single process is `ps`, `health` at its endpoint (`server-down`
     for a process that no longer runs, with no wedge check, no screen read and no mismatch beside it), `shown_session` and,
     while it runs, `session_activity` (`pane-waiting`); the rules that need a server's list are skipped. The one mismatch is
     fixable only while the process is idle, and `--fix` then relaunches it on the session of record through the caller's
     relaunch (`reconcile_with(ports, request, relaunch)`: `holler pane doctor` passes `relaunch_recorded` with `Keep`), so
     reconcile never imports `tx_launch`, which reads its `shown_differs`. A pane that works or waits is `not-fixable`, with
     the relaunch remedy, and is never relaunched. After a relaunch the chain writes no record of its own: the relaunch
     stored it (or, failed, rolled the process back).
7. **Delivery.** `send_prompt(endpoint, session, text)` writes one line, `{"type":"user","message":{"role":"user","content":
   TEXT}}`, to the process's inbox socket, never a keypress (I4). The socket path is learned from the `SessionStart` hook the
   launch argv carries: the hook writes `CLAUDE_CODE_MESSAGING_SOCKET` to a file the adapter owns (directory mode `0700`, file
   `0600`, outside the repository and outside Claude Code's configuration directory, a path the adapter's configuration sets);
   the adapter never reads `<config dir>/sessions/*.json` (the note's decision 4). A `session` that is not the process's
   current session is refused `session-mismatch`. The call is bounded by I5. If the entry turns `waiting` within a short
   window after the write and was not `waiting` before it, the message was held behind a dialog and the call is refused
   `inbound-held`. The frame is **Read**, not documented: the conformance probe (item 15) is its guard, and the model sees a
   hub order as a peer session's message (less authority than a typed prompt; by design, not removable).

   **As built (plan review W8):** the hook's command is fixed text, with nothing of a pane, a session or a path in it; its data
   comes through the environment: the socket's path from Claude Code (`CLAUDE_CODE_MESSAGING_SOCKET`) and the directory it
   writes to from the launch argv's one assignment, `HOLLER_CLAUDE_SOCKET_DIR=<dir>` (a directory, never a secret). Under
   `umask 077` it writes the path to `<dir>/<pid>`, the pid of the process that runs it (its `$PPID`), through a temporary
   file renamed into place, so every `SessionStart`, a person's `/clear` included, rewrites the same file. The directory is
   `<Holler state dir>/claude-inbox/` (the wiring's; `HOLLER_STATE_DIR`, else `$HOME/.holler`). The reader fails closed: the
   directory and the file must be the user's alone (no group or other bits), not links, and the file one absolute path;
   anything else, a missing file included, is `unavailable`, and the adapter trusts the file only for a process
   `claude agents --json` lists now. The held window is 600 ms (`Timeouts::held_window`), ended early when the entry turns
   `busy`.
8. **Activity.** `Activity` gains `WaitingPermission`. `session_activity(endpoint, session)` maps `agents --json`:
   `idle` to `Idle`, `busy` to `Busy`, `waiting` with `waitingFor` `permission prompt` (or `sandbox request`, `worker
   request`) to `WaitingPermission`, `waiting` with `input needed` to `HoldingQuestion`. `reset` and `switch` refuse any
   non-idle pane as they do today, and the roster can say which wait it is. A permission prompt is not answered by Holler in
   this story (the hook that could answer one is later). **As built:** a `waiting` entry with any other reason is
   `WaitingPermission` too (a wait a person answers, never idle); `waiting` on `dialog open` is the refusal
   `harness-dialog-open`; a status the adapter does not know is `unavailable`. A process holds one session, so its activity is
   the process's: the session named is not compared.
9. **Abort and interrupt.** `abort(endpoint, session)` for a kind whose `abort_style()` is `Relaunch` is refused
   `abort-unsupported` (open, exit 3): there is no in-place abort, and a signal is not one (SIGINT ends the process). `holler
   interrupt --pane NAME` for such a pane does not go to the hub (it has no body, item 18): after the same pane-state gates
   `resolve_pane_target` applies today (parked, unhealthy, shown and driven apart), the CLI relaunches the pane on its
   session of record through the pane engine. `interrupt` with replacement text on such a pane is refused
   `interrupt-text-unsupported` in this story. `answer --pane` on a Claude pane is refused `answer-unsupported` (nothing but a
   keypress answers a question; the launch removes the question tool, 11). **As built:**
   `interrupt_cmd::interrupt_pane(ports, pane, profile, text) -> PaneInterrupt::{Hub { session }, Relaunched { session }}` by
   the kind's `abort_style()` (a busy pane is relaunched too: that is the interrupt), and
   `answer_cmd::answer_pane_target(ports, pane, profile)`, both after `say_cmd::resolve_pane_record`, the pane gates of
   `resolve_pane_target` returning the record. `holler interrupt --pane NAME` prints `interrupted NAME: relaunched on its
   session of record "<session>"` for such a pane, exit 0.
10. **The login (I7).** A subscription login is never read, copied, stored or printed: only environment variable **names**
    appear in any record, spec, argv, message or file. The process needs `HOME` and `PATH` and nothing else for the login. The
    names that silently change it, `ANTHROPIC_API_KEY`, `CLAUDE_CODE_OAUTH_TOKEN`, `ANTHROPIC_AUTH_TOKEN`,
    `CLAUDE_CONFIG_DIR`, `CLAUDE_CODE_USE_BEDROCK`, `CLAUDE_CODE_USE_VERTEX` and `CLAUDE_CODE_USE_FOUNDRY`, are (a) unset in the
    launch argv with `env -u NAME` for each, and (b) refused in a spec's `env` at the plan as `claude-login-env-refused` (open,
    exit 3; the message names the variable name, never a value). `login_status()` runs `claude auth status` and reads the
    `authMethod` field only: `claude.ai` is `Ok`, anything else `Missing`. Nothing else of its output is kept or shown.
    **As built:** the names are a fact of the kind, `HarnessKind::login_variables()` (`CLAUDE_LOGIN_VARIABLES` in `pane.rs`),
    which the adapter's `env -u` list and the engine's plan both read, so the refusal `claude-login-env-refused` is the launch
    engine's, raised in its plan before any port call, not the adapter's. The adapter's own `claude agents --json` and `claude
    auth status` runs remove the same names from their environment, so the login they report is the one the panes use; an
    answer with no `authMethod` is `unavailable`, quoting none of it, never `Ok`.
11. **Spec fields and launch defaults in this story.** No new field of `Pane` or `ProfileSpec`. A Claude pane's `model` becomes
    `--model model_id` and `--effort effort` (the provider is recorded and not passed). `--disallowed-tools AskUserQuestion` is
    in every Claude launch (the one wait the hub cannot answer); a spec field that turns it off, a permission-mode field and an
    allowed-tools list are a later story, so a pane launches in Claude Code's default permission mode and the hub never chooses
    to bypass permission prompts. `--agent KEY` on a Claude pane is refused `agent-unsupported` (plan time): Claude's `--agent`
    exists, and applying and checking it is a later story. `ServeSpec` stays the carrier (its doc: a new field of the spec for a
    server goes there), and `process_command` takes it.
12. **The flag and the policy.** `--harness opencode|claude` is declared once in `SpecFlags` (`cli.rs`), on `launch` and
    `relaunch` and in the profile spec edits, as `harness.kind` of the spec. A new spec without it is `opencode`; an existing
    spec keeps its own; a `relaunch` that names a different harness from the record is refused `harness-change-refused`
    (open, exit 3: close the pane and launch it anew). `--port-policy` for `claude` is the word `none` (the policy grammar
    gains it; `fixed_port_policy` of a claude record is `none`, so a spec round-trips), and any other policy, or `none` for
    `opencode`, is `port-policy-unsupported` (open, exit 3, plan time). `profile show` and `profile apply` compare
    `harness.kind` like any field (`profile_diff` already lists it) and never rewrite a live pane's harness. **As built (plan
    review W13):** `--harness` is declared in `SpecFlags` (`holler-cli/src/pane/args.rs`, not `cli.rs`), typed by `validate`
    (anything but `opencode` or `claude` is `usage`, and the text is never echoed), and absent unless given. The one policy
    rule is `tx_launch::port_for(kind, policy)`: outside the grammar is `usage`, a policy the kind does not take is
    `port-policy-unsupported`; `pane launch`'s check of its flags reports only the first. A record's snapshot names its policy
    through `profile_snapshot::port_policy_of` (`none`, `NO_PORT_POLICY`, for a harness with no port). `profile apply` refuses
    a recorded pane whose spec names another harness, `harness-change-refused`, before it judges the pane's health, and
    `HarnessInfo` checks its fields against its kind through `#[serde(try_from = "RawHarnessInfo")]`, as `Profile` checks its
    slug.
13. **Doctor.** `FindingKind` gains `claude-login-missing` (a problem; `login_status` is `Missing`, reported once per run when
    any recorded pane is `claude`, and its remedy names the login, never a command that reads one) and `pane-waiting` (a
    warning; the entry is `waiting`, with the reason `waitingFor` gives). `server-down` is reused for "no `agents --json` entry

## Why

One registry, written only by compare-and-swap and read by every verb, removes the condition behind every 2026-10-07
incident: several records that each claimed to know the session. Running the verbs CLI-side keeps the hub a store that never
blocks on Herdr, tmux or a harness, and lets every story code against traits and fakes in parallel. Kebab-case codes in a
result, not wire error frames, keep protocol v2's closed catalog and golden files unchanged. Failing closed on a corrupt
registry, rather than starting empty, follows from records that gate every verb: an empty registry would look like a fleet
with no panes.

## Consequences

- Protocol v2 is unchanged: no row is added to §4, no error to §8, and no golden file changes. [Protocol v2](../protocol/v2.md)
  §11 notes, without rules, that the `pane/*` and `profile/*` control-socket methods exist and are specified here.
- The control socket has two refusal conventions: `control/*` methods answer a refusal with a JSON-RPC error and a
  `data.reason`, and `pane/*` and `profile/*` answer with a `PaneReply` result. A client must tell them apart by method family.
- `holler-cli` takes on the adapter dependencies (#649). The tests that drive the CLI in the default run use the test kit's
  fakes, never a real Herdr, tmux or OpenCode; the opt-in scenarios (#649, and #667 for `profile apply`) run only on
  scratch Herdr, tmux and OpenCode instances they start themselves, and refuse real session names.
- The CLI's JSON output for pane and profile verbs becomes a versioned contract (`schema_version`); a change to its shape is
  a breaking change under ADR 0003.
- Two hub state files are added (`panes.json`, `profiles.json`). Their corruption stops the pane and profile verbs until the
  operator repairs the file, and nothing else in the hub.
