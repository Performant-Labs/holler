## Context

On 2026-10-07 five records each claimed to say which session a pane was on (the TUI, the hub's registration, and the
fleet launcher's `sessions.toml`, `last-session` and `owned-sessions`), and nothing kept them in step. Orders ran in a session
the pane did not show, a repair re-registered the old session by guessing, a wedged harness server went unnoticed for three
days, and every launch left a stray session behind. Epic #633 makes Holler the only thing that changes a pane. This ADR
ratifies the contract the epic fixed and the code that already implements part of it, and decides the questions the epic
left open.

**Sources, in order of precedence.** The merged code wins over the epic's prose wherever they differ, and this ADR says so
at each difference. The code is `crates/holler-pane/` (#637), `crates/holler-proto/src/methods.rs` (#637), and
`crates/holler-hub/src/{pane_dispatch.rs,panes/mod.rs,profile/mod.rs,profile/rename.rs}` (#669). Files that a later story
creates are named with the story that creates them; they do not exist on `main` yet.

## Decision

### 1. Ratified: the records

The records live in `holler-pane` (`src/pane.rs`, `src/profile.rs`). Every stored record and every params struct refuses
unknown fields (`deny_unknown_fields`): a peer that does not know a field cannot read, change and write back a record and
drop that field silently. Optional fields are left out when absent and read back as absent. Every timestamp is `i64`
milliseconds since the Unix epoch.

**`Pane`**, one per pane, keyed by `name`:

| Field | Type (merged) | Notes |
|---|---|---|
| `name` | `PaneName` | A newtype over `holler_proto::vocab::SessionName`, so a pane name obeys the [ADR 0005](ADR-0005.md) grammar. It is also the tmux session name. Names such as `hj-c1r2` are names, not positions. |
| `generation` | `u64` | See section 8. |
| `herdr` | `HerdrPane { session, workspace, pane_id, grid: GridPos }` | `pane_id` is Herdr's opaque id (`PaneId`). |
| `host` | `HostInfo { name, tmux, cwd, herdr_api_version? }` | `herdr_api_version` is the string `HerdrPort::version()` reports, recorded by a verb, never by the Herdr adapter, which writes no record (section 10). |
| `harness` | `HarnessInfo { kind, port, pid?, health }` | `kind` is the closed enum `HarnessKind` (only `opencode`); `health` is `"healthy"`, `{"unhealthy": reason}` or `"unknown"`. |
| `session_of_record` | `Option<String>` | THE session: the TUI shows it and the hub drives it. The epic wrote `Option<SessionId>`; the merged type is a plain string. |
| `role` | `PaneRole` | `agent` or `orchestrator`. |
| `hold` | `Hold` | `"none"`, `{"parked": {reason, release_when, since}}` or `"drained"`. This is the park state of a pane, **not** the prompt hold of the hold and release verbs (`holler_proto::SessionHold`). |
| `last_observed` | `LastObserved { shown?, driven?, at }` | Written by reconcile, never inferred (I6). |
| `profile` | `Option<ProfileName>` | The profile the pane belongs to, at most one (C5). Membership is this field only. |
| `model` | `ModelSpec { provider, model_id, effort }` | Recorded by launch, relaunch (#644) and import (#650) (C1). |
| `env` | `Vec<EnvVarName>` | Names only (I7). |
| `context` | `ContextCeilings { soft, hard }` | `u32` each; the ceilings a watchdog reads. |
| `command` | `Option<Argv>` | B2. |
| `probe` | `PaneProbe { check?: Argv, expect: Vec<String>, last?: ProbeResult }` | B1. |

**`Profile`**: `name: ProfileName`, `slug`, `generation`, `panes: Vec<ProfileSpec>`, `created`, `updated`. On read the
stored `slug` must equal the slug derived from the name, or the record does not load. **There is no `log` field** (ruling 8;
the epic listed one): the append-only change log is read only through `ProfileStore::log`, so `cas_put` cannot rewrite
history. A log entry is `ProfileLogEntry { at, generation, actor, change }`, `change` being `created`, `{"updated": {summary}}`,
`{"renamed": {from}}` or `deleted`.

**`ProfileName`** is a display name (spaces allowed). Parsing trims it and refuses a name that is empty, longer than 64
characters, has a control character, or has no ASCII letter or digit (all `usage`). `slug()` is the one slug rule: ASCII
letters and digits lower-cased, each run of anything else one `-`, no leading or trailing `-`. Two names with the same slug
are the same profile for uniqueness. **`Actor`** (who made a profile write) is a trimmed, non-empty name of at most 64
characters with no control character.

**`ProfileSpec`**, one pane of a profile, names and non-secret values only (I7): `pane: String`, `herdr { workspace, grid }`,
`host { cwd }`, `harness { kind, port_policy }`, `model`, `role`, `env`, `context`, `command?`, `check?`, `expect`. `pane` is
plain text, not a `PaneName`, because a spec may name a pane that does not exist or belongs to another profile (a *detached
spec*, for example after `profile create --from`).

**`Argv`** (B2) is a JSON array of strings. Nothing in Holler passes a stored command through a shell. A bare string, or an
array with a non-string element, is `command-not-argv`. `Argv::from_json` reads the text of the `--command-json` and
`--check-json` flags (text that is not JSON is `usage`).

**`EnvVarName`** (I7) is the one guard for environment entries (ruling 7): a `=` anywhere is `profile-secret-refused`; an empty
name, or one with whitespace or a control character, is `env-name-invalid`. Neither refusal echoes the refused text. Because the
guard runs on decode, a record that holds a value cannot load, and no store or importer scans raw JSON a second time.

**`ProbeResult`** (B1) is `"ok"`, `{"failed": {"missing": [...]}}` or `{"error": "reason"}`. The signature
`run_probe(argv, expect, timeout) -> ProbeResult` is frozen; until #663 fills it, the stub answers `Error`, never `Ok`, so a
launch cannot pass a probe on a stub. The `Prober` trait and `SystemProber` let a test swap the runner. The runner (#663)
answers `ok` only when the program exited 0 and every `expect` string occurs in its stdout (as bytes, case-sensitive), and
`failed` when it exited 0 without some of them. A non-zero exit or an end by a signal is `error` whatever the output, and so
are the deadline passing and more than 1 MiB of stdout. The argv is run directly, never through a shell, and no reason
echoes an argv element or a byte of the output. The runner signals the probe's process group only while its leader is
unreaped, when the group's id (the leader's pid) cannot have been reused, so a `try_wait` error sends no signal and is
`error`. That path, a child that escapes the group and a missing `kill` binary are the documented exceptions to
section 12's "No verb leaves work running after it exits".

**`GridPos`** (decision 7) is section 10.

### 2. Ratified: the ports

All ports are traits in `holler-pane` (`src/ports.rs`, `src/profile.rs`), **synchronous, blocking and `Send + Sync`**: async
code calls them from `spawn_blocking` or a thread, and every method returns within I5's bound (default 10 s) or with
`timeout`. Two methods are bounded otherwise, which also qualifies section 12's per-call bound (#663):
`ProfileScope::edit_spec` returns within the sum of its port calls (at most four) plus the verb's own act, which it can
neither bound nor cancel, and `Prober::run_probe` returns at its deadline plus at most 1 s to kill and reap the probe; a
follow-up amends the frozen trait docs to match. `Ports` bundles one `&dyn` of each, and a verb holds it.

| Port | Methods (merged) | Implemented by |
|---|---|---|
| `PaneStore` | `get`, `list`, `cas_put(pane, expected_generation)`, `delete(name, expected_generation)`, `watch(since)` | the hub (#639); `delete` was added by ruling 9 |
| `ProfileStore` | `get`, `list`, `cas_put(profile, expected_generation, actor)`, `delete(name, expected_generation, actor)`, `watch(since)`, `log(name)`, and **PROPOSED** `rename(from, to, expected_generation, actor)` | the hub (#661); `rename` answers `not-implemented` until #665 is confirmed |
| `ProfileScope` | `resolve(profile, pane?)`, `edit_spec(profile?, pane, edit, act)` | `holler-cli/src/pane/profile_scope.rs` (#663; #670 creates the empty file) |
| `HerdrPort` | `ensure_pane`, `send_text`, `send_keys`, `read`, `close`, `snapshot`, `version` | `holler-adapter-herdr` (#640) |
| `HostPort` | `ensure_session`, `run`, `stop_owned`, `ps` | `holler-adapter-host` (#641) |
| `HarnessPort` | `serve`, `health`, `create_session`, `list_sessions`, `abort`, `attach_tui`, `select_session`, `shown_session` | `holler-adapter-opencode` (#642) |
| `Prober` | `run_probe(argv, expect, timeout)` | `SystemProber` (the free `run_probe`, #663) |

`HerdrPort` and `HarnessPort`, and the data types they take and return, stay **provisional** until the spikes #636 (Herdr)
and #635 (OpenCode) report. If a spike contradicts them, the contract and this ADR are amended first, in their own PR (the
epic's amend-first rule). `holler-pane-testkit` (#638) fakes every port and ships a conformance suite each real
implementation runs against itself.

`Watch<T>` is the change stream of both stores: changes in order, each with a store-wide, strictly increasing `Cursor`.
`watch(Cursor(0))` first yields a put for every record held now; resuming from the last cursor seen neither repeats nor skips.
`next()` yields `Ok(Some(event))`, `Ok(None)` for idle within the bound (the stream stays usable), or an error that ends the
stream; `timeout` means a wedged store, never idle. An event is `PaneEvent { cursor, name, pane? }` or
`ProfileEvent { cursor, name, profile? }`, with no record meaning a deletion; a profile rename is a deletion of the old name
and a put of the new one.

### 3. Ratified: the verbs, the `--profile` classes and the spec flags

The pane verbs are `list`, `get`, `watch`, `launch`, `relaunch`, `switch`, `reset`, `park`, `unpark`, `close`, `doctor` and
`import`, under the `pane` subcommand group of the `holler` binary. The profile verbs are `create`, `delete`, `list`, `show` and
`apply` (REQUIRED, #664; `apply` refuses a pane of another profile unless `--take-over`, C3, and `--dry-run` prints the plan),
plus **PROPOSED** `rename`, `export` and `import` (#665). There is no `diff` verb: `profile show` reports where live panes differ
from their spec. One verb is one file and one owning story, including its clap `Args` struct (ruling 2); the shared flag groups
(`SpecFlags`, `ProfileOpt`, `SpecOnly`) and `--take-over` are declared once by #670.

`--profile P` has two classes and one exception:

- **Spec-editing** (`launch`, `relaunch`, `close`): edit P's spec for that pane and change the live pane as one transaction
  (I8, section 8). P must exist (`profile-not-found`). `--spec-only` (C2, requires `--profile`) edits the spec and changes
  nothing live. Without `--profile` these verbs never touch a profile.
- **Scoping** (`list`, `get`, `watch`, `doctor`, `switch`, `reset`, `park`, `unpark`, the `--pane` forms of `say`, `interrupt`
  and `answer`, and the roster): act on P's panes. A named pane outside P is `pane-not-in-profile`. The read verbs and
  `doctor`, `park` and `unpark` with no pane name mean every pane of P; `say`, `interrupt`, `answer`, `switch` and `reset`
  still need a pane name.
- **Neither**: `pane import` takes no `--profile`; a real run creates the profile `fleet` itself (#650).

**Park and unpark as built (#646).** `pane park [PANE] --reason TEXT --release-when WHEN` and `pane unpark [PANE]`
change only the pane record's `hold`, by one compare-and-swap per pane; they call no adapter and write no profile, so
they never move a pane in Herdr or touch its processes, and I3 reduces to plan and record. `park` sets `{"parked":
{reason, release_when, since}}` on a pane whose hold is `none` (`since` is the verb's clock); `unpark` sets `none` on a
parked pane. Both leave a pane already in that state, or `drained`, as it is and report it unchanged (exit 0). With
`--profile` and no pane name they take P's panes in name order and stop at the first failed write, whose message
names the panes changed before it and those not reached; the rerun is safe. The reason and the release condition are
one line each, hold no control character, are not blank and are at most 200 characters (`usage` otherwise). Which verbs and prompts read a parked pane
is decided by their stories (the watchdog, the roster #648, the prompt gate of #646).

**Spec flags**, one per `ProfileSpec` field, used by `launch`, `relaunch` and the profile spec:

| Flag | Field |
|---|---|
| `--project DIR` | `host.cwd` |
| `--workspace W` | `herdr.workspace` |
| `--grid POS` | `herdr.grid` (any form `GridPos::parse` accepts) |
| `--model PROVIDER/ID` | `model.provider`, `model.model_id` |
| `--effort E` | `model.effort` |
| `--role agent\|orchestrator` | `role` |
| `--env NAME` (repeatable) | `env` (through `EnvVarName`) |
| `--ctx-soft N`, `--ctx-hard N` | `context.soft`, `context.hard` |
| `--port-policy P` | `harness.port_policy` |
| `--command-arg ARG` (repeatable) or `--command-json '[...]'` | `command` |
| `--check-arg ARG` (repeatable) or `--check-json '[...]'` | `check` |
| `--expect STR` (repeatable) | `expect` |

Giving both forms of `command` or of `check` is a usage error (exit 2). **`profile create --from-current`** copies, from the
`Pane` records in `PaneStore` (so it needs no Herdr call), each member's `herdr.workspace` and `herdr.grid`, `host.cwd`,
`harness.kind`, `model`, `role`, `env`, `context`, `command`, `probe.check` and `probe.expect`, and sets each member's
`Pane.profile`; a pane already in another profile is `pane-in-other-profile`. The mapping lives in
`holler-pane/src/profile_snapshot.rs` (#662), which the migration (#650) reuses. `--from-current` writes `harness.port_policy`
as `fixed:<port>`, the port the pane's harness uses (#662, `profile_snapshot::fixed_port_policy`); `profile_diff` compares it
with `fixed:<port>` of the live port. A profile's **live panes** are the pane records whose `profile` names it (by slug).

### 4. Ratified: the invariants, each with a test idea

| | Invariant | One-line test idea |
|---|---|---|
| I1 | Only pane verbs change a pane or its registration. | Every adapter call in a scenario is made from a verb's code path: the fakes record their caller, and the hub's `pane/*` handlers hold no adapter (no adapter crate in `holler-hub`'s manifest). |
| I2 | `session_of_record` is the only session a pane's TUI shows and the hub drives. | After each of launch, relaunch, switch and reset on the fakes, the fake TUI's shown session, the driven session and `session_of_record` are equal. |
| I3 | Every verb is plan, act, observe, record; a mismatch fails loudly and records nothing. | Make the fake TUI show a different session after `act`: the verb exits 1 with a code, and the stored record and its generation are unchanged. |
| I4 | No verb changes a session by typing into a TUI. | The fake Herdr records every `send_text`/`send_keys`; the switch and reset tests fail if any keystroke was sent (#645). |
| I5 | A verb returns in bounded time (default 10 s); long work returns an operation id. | A wedged fake port makes the verb exit with `timeout` within the bound plus a margin; the operation-id half waits for section 12. |
| I6 | State is observed from Herdr, tmux and the harness, never inferred from files. | Give the importer and reconcile a stale registration file that names session A while the fake harness shows B: no record gets A as observed state. |
| I7 | A profile holds names and non-secret values, never a secret. | A `ProfileSpec` or `Pane` JSON with `"env": ["TOKEN=x"]` fails to decode with `profile-secret-refused`, and the refusal text does not contain `x`. |
| I8 | An edit through `--profile` and the live change are one transaction. | Fail `act` in `edit_spec` on the fake: P's specs are equal to before and no pane record changed; succeed it: P holds the edit and the pane record names P. |

### 5. Where verbs run, and the crate layout

**Decided (ruling 1): verbs run CLI-side, against the ports; the hub is the store only.** The hub holds the pane registry
and the profile registry and answers their store methods; it constructs no adapter and runs no verb. The adapters are
constructed in `holler-cli/src/pane/wiring.rs` (#670 creates it, #649 fills it). The hub's `pane_wiring.rs` (#669) is an empty
placeholder with no job under this ruling.

**Decided: the crate dependency rules.**

- `holler-pane` holds types, traits and the pure transaction engines (`tx_launch.rs` #644, `tx_switch.rs` #645, `tx_apply.rs`
  #664, `reconcile.rs` and `findings.rs` #647, `profile_snapshot.rs` and `profile_diff.rs` #662, `import.rs` #650), which work
  only through the ports. It depends on `serde`, `serde_json` and `holler-proto`, and takes no async runtime. Its one direct
  side effect is the probe runner (`run_probe`, #663), which runs a process with the standard library.
- Each adapter crate depends on `holler-pane` and implements one port. `holler-cli` depends on the adapter crates; `holler-hub`
  does not.
- `holler-pane-testkit` (empty today; #638 fills it) may depend on `holler-pane` and `serde_json`, and **must not depend on
  `holler-cli`**: it is a dev-dependency of both the hub and the CLI, so a normal dependency back would make a cycle. Its
  envelope conformance helper (#638) parses the CLI envelope with `serde_json` alone.
- `holler-proto` knows only the method *names* (`PANE_METHODS`, `PROFILE_METHODS`); it cannot depend on `holler-pane`, which
  owns the params and the reply type.

**Decided: where the I8 transaction helper lives.** The trait `ProfileScope` is in `holler-pane/src/profile.rs` (frozen by
#637). The real implementation is in `holler-cli/src/pane/profile_scope.rs` (#663) and the fake is in `holler-pane-testkit`
(#638). The spec-editing verbs call `edit_spec` and do not write the profile themselves.

### 6. The hub control-socket methods and their replies

**Decided (ruling 6): `pane/*` and `profile/*` are hub control-socket methods, not v2 wire methods.** They sit outside the
closed 22-row catalog (`holler_proto::methods::CATALOG`), are not reserved in [protocol v2](../protocol/v2.md) §4, and a body
connection that sends one still gets `method_not_found`. The names are:

- `PANE_METHODS`: `pane/get`, `pane/list`, `pane/cas_put`, `pane/delete`, `pane/watch`.
- `PROFILE_METHODS`: `profile/get`, `profile/list`, `profile/cas_put`, `profile/delete`, `profile/watch`, `profile/log`,
  and **PROPOSED** `profile/rename`.

The control server forwards them through `holler-hub/src/pane_dispatch.rs` to `panes::dispatch` (#639) and
`profile::dispatch` (#661, with `profile/rename` routed to `profile/rename.rs` for #665). Each dispatcher gets both
registries' state.

**Decided (ruling 3): the reply is a `PaneReply` carried as the JSON-RPC result.** Its form is
`{"ok": bool, "data": ..., "error": {"code", "message", "detail"?}}`. The merged type adds the optional `detail` (the payload
of the closed error variant, so the client can rebuild the exact `PaneError`) to the epic's `{code, message}`. It carries no
`schema_version` and is **not** the CLI's `--format=json` envelope (section 9): it is an internal hub-to-CLI encoding. Only a
request that never reaches a handler stays a JSON-RPC error: framing errors and a method in neither list. Every outcome of a
request that reaches a handler is a `PaneReply`, including params that do not decode (`decode_params`; a request with no
`params` decodes from `{}`). Parse-back (`into_result`): a closed code becomes its own variant, any other well-formed code
`Refused`, a malformed code or a reply whose `ok` and `error` disagree `unavailable`. A reply ignores unknown fields; the
records inside `data` do not.

**Decided: `*/watch` is long-poll.** One request, one reply, whose `data` is `WatchReply { events, cursor }`: the batch
collected after `since`, and the cursor to resume from. An idle window answers `{"events": [], "cursor": <head>}`; the head
equals `since` except for a watch from 0 over a registry whose records have all been deleted, and resuming from the head keeps
the `Watch` contract ("then every later change"), where answering 0 would let a pane created and deleted between two polls
never reach the watcher (see "Decisions taken", item 7). The window
stays under the control client's default timeout and within I5's bound; its value is #639's (its brief proposes 4 s).

**Decided: the `data` of each method** (which `reply.rs` leaves to this ADR):

| Method | `data` |
|---|---|
| `pane/get`, `profile/get` | the record, or `null` when there is none (the verb decides whether absence is an error) |
| `pane/list`, `profile/list` | an array of records (`pane/list` sorted by name) |
| `pane/cas_put`, `profile/cas_put` | the stored record, with its new generation |
| `pane/delete`, `profile/delete` | `null` |
| `pane/watch`, `profile/watch` | `WatchReply<PaneEvent>`, `WatchReply<ProfileEvent>` |
| `profile/log` | an array of `ProfileLogEntry`, oldest first |
| `profile/rename` (PROPOSED) | the renamed record |

### 7. Persistence on the hub

**Decided**, consistent with the brief of #639 (which proposes it for panes) and extended to profiles:

- The pane registry is `<state dir>/hub/panes.json` and the profile registry is `<state dir>/hub/profiles.json`, beside
  `holds.json`. Each is written at mode `0600` through `holler_proto::atomic_file::write_atomic` (a temporary file in the same
  directory, then a rename), the hub's one state-file writer. As with the hub's other state files there is no fsync.
- Each file is a versioned JSON document (`"version": 1`). Its exact layout belongs to the registry's story (#639, #661); both
  use the same generic load and save helpers. The profile change log is persisted in `profiles.json` with the records,
  never inside a `Profile`.
- **One lock per registry.** A single mutex guards each registry's whole table. A write runs under it in this order: the
  compare-and-swap check, building the next document, saving it, and only then committing to memory and publishing the
  event. A failed save therefore changes nothing (memory, file and cursor), and the call answers `unavailable`.
- **Lock order.** The pane registry never calls into the profile registry while it holds its own lock. A hub-side
  operation that needs both (only the PROPOSED `profile/rename`) takes the profile lock before the pane lock.
- **Fail closed.** A missing file is an empty registry. An unreadable file, a parse failure, an unknown version or a failed
  validation puts that registry in a failed state: every method, `watch` included, answers `store-corrupt`, naming the file
  and the problem but never quoting its content. The file is **left in place**, never moved aside or rewritten (unlike
  `holds.json`, which is moved aside and restarted empty): pane records gate every verb, so an empty registry would be a
  silent reset. The hub still starts, because its other functions do not depend on panes. The state clears on a restart
  after the operator repairs the file.
- The change feed's cursor head is persisted, so cursors never go backwards across a restart. A watcher that falls behind the
  retained window, or resumes across a restart, receives one event per record changed since its cursor (the latest state, or
  a deletion), so it can miss intermediate writes but never a final state or a deletion.
- `deny_unknown_fields` means that a file written by a newer build with a new field fails closed as `store-corrupt` on an
  older build. That is intended.

### 8. Generations, concurrent writers and the I8 write order

**Decided: how generations fence concurrent writers.**

- Every `Pane` and `Profile` carries `generation: u64`. A record that does not exist is at generation 0, so a create names
  `expected_generation: 0` and is stored at 1. Each applied write adds one. The store sets the generation; the one a client
  submits is ignored. The rule is `holler_pane::next_generation`, written once and used by every store and fake.
- A write whose expected generation is not the current one is `generation-conflict` and changes nothing. `delete` checks
  that the record exists first (`pane-not-found` or `profile-not-found`, whatever the generation) and the generation second.
- A verb takes its expected generation when it plans, and writes the record with it after the act. If another writer got in
  between, the verb's record write fails with `generation-conflict` **after** the live change: the verb fails loudly, exits 1,
  writes nothing more, and prints the reconcile step (the pane doctor command line; the profile-scoped or the bare form of
  step 6, which names no pane, for the reason given there). With `--profile` the record step runs inside the act, so a
  record conflict also restores P's specs (step 5) before the verb prints the reconcile step (#663, confirming the
  assumption of #638).
- **Generations fence records, not live acts.** Two verbs on the same pane can both act; only one records. The frozen
  `Pane` has no field to claim a pane before acting, so this ADR adds none; the reconcile pass (#647) is the safety net. A
  claim, if one is wanted, comes with the operation id (section 12).
- **Known gap:** a record deleted and then created again restarts at generation 1, so a writer still holding generation 1 of
  the old record can overwrite the new one. The contract fixes "0 for a new record", so this is recorded, not fixed.
- No store transaction spans the two registries. The membership rule is enforced on `pane/cas_put`: setting `Pane.profile`
  to P when the stored pane already belongs to another profile is `pane-in-other-profile`, and P must exist. A spec that
  names a pane of another profile (a detached spec) is not refused.

**Decided (the epic's order, as the merged `ProfileScope::edit_spec` documents it): the I8 write order.** For a
spec-editing verb with `--profile P`:

1. **Plan.** Read P at generation `g` and the pane record; compute P with the edit (`SpecEdit::Set` or `SpecEdit::Remove`).
   A `Set` for a pane whose record belongs to another profile is refused here with `pane-in-other-profile`, before anything
   is written or moved, with or without `--spec-only` (the scope cannot see that an act is empty); a `Remove` is not (a
   detached spec stays removable), and the pane registry's check ("Decisions taken", item 2) stays the authority (#688).
2. **Profile CAS first.** `ProfileStore::cas_put(P_edited, g, actor)`. A conflict here comes before anything live changed:
   the verb exits 1 with `generation-conflict` and can be run again. A first write whose outcome is unknown (a `timeout`)
   may have landed, so the act does not run, and the answer is `timeout`, saying that P may hold the edit, with the
   reconcile step. The store client (#649) answers `timeout`, not `unavailable`, when it loses the reply to a write it
   sent. Any other error of this write is answered as it is (#663).
3. **Act** (skipped with `--spec-only`), then observe.
4. **Record.** Write the pane record with its own compare-and-swap (`cas_put`, or `delete` for `close`).
5. **If the act fails, nothing is recorded in P:** the pane record is not written, and the profile is put back by a
   compensating `cas_put` of its previous specs at `g + 1`. P's specs then equal what they were before the verb, and its
   log shows the edit and its reversal. If the compensating write fails other than by a conflict, the answer keeps that
   write's own code, and its message names P, the unrestored edit (after a `timeout`, the edit, which may not have been
   restored), the act's error and the reconcile step (#663).
6. **A conflict after the act fails loudly.** If the compensating write of step 5 conflicts (another writer moved P during
   the act), the verb exits 1 with `profile-conflict`, naming P, and prints the reconcile step: the exact pane doctor command
   line, and the profile show command for P. A pane-record conflict in step 4 is `generation-conflict`, handled the same way.
   The reconcile step is exactly `to reconcile, run holler pane doctor --profile '<P>' and then holler profile show '<P>'`,
   with P POSIX-single-quoted, and without `--profile` it is `to reconcile, run holler pane doctor`. `reconcile_step` in
   `holler-cli/src/pane/profile_scope.rs` builds both (`reconcile_step(None)` is the second) on
   `holler_pane::findings::doctor_command(None, false)`, the doctor command line's one builder (#701). The step names no
   pane on purpose: a pane-scoped doctor refuses a pane with no record or outside P (`pane-not-found` or
   `pane-not-in-profile`, in `holler-pane/src/reconcile.rs`), which is what a failed `launch` of a new pane leaves, so the
   step runs the doctor over every pane of P (or every pane) and `profile show` reports the spec that has no live pane.
   Three errors of the scope carry the step in their message: this `profile-conflict`, the restore failure of step 5 and
   the first-write `timeout` of step 2. A verb appends it only to an error that does not carry it (#663).

With `profile: None`, `edit_spec` runs only the act and touches no profile. This order deliberately makes the edit visible
in P before the live change, so a concurrent profile editor is refused before anything live moves. The cost is a second
profile write on a failed act; see "Decisions taken", item 1.

**Launch and relaunch as built (#644).** `pane launch PANE --herdr-session NAME` and `pane relaunch PANE`, each with the
spec flags, `--profile` and `--spec-only`, run one engine over the ports, `holler_pane::tx_launch`, which `profile apply`
(#664) calls unchanged. Its plan writes nothing and moves nothing: the spec names the pane, a launched name has no record
(`pane-exists`), the port policy is the `fixed:<port>` form of section 3 (launch accepts no other), a check passes when the
spec has one (a failing result is not stored), Herdr's version is supported, the target cell holds no Herdr pane
(`grid-occupied`, judged by Herdr's snapshot alone, recorded or not: a pane is never adopted) and no server answers on the
port (`port-in-use`, never adopted). The act ensures the Herdr pane and the tmux session, runs the spec's `command` in that
session as an argv (only `HarnessPort::serve` starts the server), starts and checks the server, creates the session of
record through the harness API (never a ping session), attaches the TUI to it, and observes that the TUI shows it
(SHOWN equal to `session_of_record`, which I2 makes the session the hub drives) and that Herdr still lists the pane. A
mismatch observed after the act is `unavailable`: a closed failure code, since I3 asks for exit 1 and an open code is a
refusal. Only then is the record written, by one compare-and-swap: `last_observed.shown` is that observation, and
`driven` is never inferred (launch writes none, relaunch keeps the stored one). The model, effort, environment names and
ceilings are recorded, not applied: no port carries them yet (#642, #649). A failed step rolls back what the run made (it
stops the tmux session's processes and closes a Herdr pane the plan's snapshot did not list); the tmux session and a
created harness session stay, as no port call ends them, and a record write that conflicts is not rolled back. Relaunch
first stops only what the pane owns and fails loudly when the old server still answers (until #695 stops it by its
recorded pid); it keeps the pane's directory, moves its cell only with `--grid` (both rules are the engine's own, so every
caller is held to them) and keeps the session of record the restarted server still lists (a new conversation is
`pane reset`'s). After a move it records the new pane before it closes the old one, so a close that fails leaves an extra
pane with no record, never a record naming the wrong pane; the run then exits 1 with `unavailable` and P keeps its edit.
Every failure once the act has started ends with the reconcile step of step 6, appended only when the message lacks it. A
run is bounded as section 12 records. `--herdr-session` is required because the frozen `HerdrPort` cannot tell the
engine its session; the wiring (#649) defaults it from the Herdr adapter's one configured session. What a failure or a
crash leaves is not all reported by the merged doctor: only a whole-fleet pass reports a Herdr pane no record names
(`unregistered-herdr-pane`, which no verb removes, so the next launch at that cell is `grid-occupied` until the operator
closes it in Herdr), no pass sees a server or a tmux session that no record names, and a crashed launch's server keeps its
port (`port-in-use`) until #695.

### 9. Failure taxonomy, and the CLI output

**Decided: two casings, kept apart by channel.**

- The **v2 wire catalog's error codes** are the closed `holler_proto::Code` table: 17 codes, each a JSON-RPC number and a
  `snake_case` `data.code` string (`method_not_found`, `session_held`, ...), documented in [protocol v2](../protocol/v2.md) §8.
  They appear only in JSON-RPC error frames, on the body circuit and for framing errors and unknown methods on the control
  socket.
- The **pane and profile codes** are `kebab-case` (`^[a-z]+(-[a-z]+)*$`, checked by `holler_pane::error::is_valid_code`, the
  workspace's one validator). They appear only inside a `PaneReply` (a JSON-RPC result) and in the CLI envelope's
  `error.code`, never in a JSON-RPC error frame. Neither table imports the other: `holler-proto` cannot see `holler-pane`, and
  no pane code is added to `Code`. That `holler-pane` also has exactly 22 closed codes is a coincidence; they are unrelated
  to the 22 catalog rows.

**Decided: closed and open pane codes.** The closed set (`ALL_CODES`, one `PaneError` variant each) is: `not-implemented`,
`usage`, `grid-ambiguous`, `grid-out-of-range`, `command-not-argv`, `env-name-invalid`, `generation-conflict`, `probe-failed`,
`profile-conflict`, `profile-not-found`, `profile-exists`, `profile-has-live-panes`, `pane-not-in-profile`,
`pane-in-other-profile`, `profile-secret-refused`, `herdr-version-unsupported`, `timeout`, `pane-not-found`,
`session-not-found`, `store-corrupt`, `unavailable`, and `profile-drift` (a reconcile finding kind, listed for convenience; it
is not an error a port returns). No story edits that list (ruling 3). A verb or adapter declares any other code it owns as a
constant in its own file through `RefusalCode::from_static`, which refuses a malformed or closed code at build time, and
raises it as `PaneError::Refused`. **Stable** means a code is never renamed or reused for another meaning once it has
merged; a code whose condition disappears is retired, not recycled. Every message is one line and never echoes a secret.

**Failure modes by verb.** Every verb can also answer `usage`, `unavailable`, `timeout`, `store-corrupt` and, until its
story lands, `not-implemented`. "Open (#N)" means codes that story declares as its own constants.

| Verb | Codes beyond the common ones |

**Decided (decision 6): the `--format=json` envelope.** Every pane and profile verb and the roster take
`--format=text|json` (default text). In JSON mode stdout carries exactly one envelope, and every diagnostic goes to stderr:

```json
{"schema_version": 1, "ok": true, "data": {}, "error": null}
{"schema_version": 1, "ok": false, "data": null, "error": {"code": "pane-not-found", "message": "pane not found: hj-c1r1"}}
```

- `error` is `null` exactly when `ok` is true. `error.code` is the `PaneError` code verbatim and `error.message` its one-line
  text; the envelope has no `detail`. Each verb supplies only its `data`. The types and `emit()`, `emit_stream()` and
  `emit_usage_error()` are in `holler-cli/src/output.rs` (#670 creates it, #660 completes it).
- `pane watch` in JSON mode writes NDJSON: one envelope per line, flushed per line.
- **Exit codes are the same in both formats (operator, 2026-10-09):** 0 ok, 1 runtime failure, 2 usage, 3 refusal. A
  refusal is a request the system understood and declined, working as designed, so nothing was wrong with the system
  (`pane-in-other-profile`, `profile-secret-refused` and the like); this is [ADR 0003](ADR-0003.md)'s exit 3, a fail-closed
  policy refusal, carried to the new verbs. A failure is something that went wrong while doing the work (a timeout, an
  unreachable hub or adapter, a conflict between writers). A usage error under the `pane` or `profile` subcommands in JSON
  mode is an envelope with code `usage` and exit 2. In JSON mode `ok` is false for exit 1, 2 and 3 alike. Which `PaneError`
  code is a refusal and which a failure is decided once, in one function in `holler-pane`, `holler_pane::error::class_of`
  ([#676](https://github.com/Performant-Labs/holler/issues/676); see "Decisions taken", item 5). The CLI's output module and
  the test kit (#638) call it, and `ErrorClass::exit_code` turns its class into the number; the table below is its
  classification. An open code is always a refusal (exit 3), so a verb that reports a runtime failure uses a closed
  failure code; a malformed code is a failure. This **amends the epic's output contract**, which said refusals exit 1.

  | Code | Class (exit) | Reason |
  |---|---|---|
  | `usage` | Usage (2) | The request is malformed; ADR 0003's exit 2. |
  | `grid-ambiguous` | Refusal (3) | The `GridPos` guard declined text it cannot read one way. |
  | `grid-out-of-range` | Refusal (3) | The `GridPos` guard declined a row or column outside its bounds, or the Herdr port declined a cell outside the workspace. |
  | `command-not-argv` | Refusal (3) | Policy: a stored command is an argv array, never a shell string. |
  | `env-name-invalid` | Refusal (3) | The `EnvVarName` guard declined a blank or whitespace name. |
  | `profile-secret-refused` | Refusal (3) | Policy I7: a profile holds names, never values. |
  | `profile-exists` | Refusal (3) | The name is taken; nothing went wrong. |
  | `profile-has-live-panes` | Refusal (3) | Delete is declined while panes of the profile are live. |
  | `pane-not-in-profile` | Refusal (3) | The `--profile` scope check declined a pane outside the profile. |
  | `pane-in-other-profile` | Refusal (3) | Ownership policy: a pane belongs to at most one profile (C3). |
  | `probe-failed` | Refusal (3) | The health gate declined to launch or relaunch, working as designed. |
  | `herdr-version-unsupported` | Refusal (3) | A fail-closed version gate, like ADR 0003's exit 3. |
  | `profile-not-found` | Refusal (3) | The named profile does not exist; the request was understood and declined. |
  | `pane-not-found` | Refusal (3) | The named pane does not exist. |
  | `session-not-found` | Refusal (3) | The named harness session does not exist. |
  | `generation-conflict` | Failure (1) | A race between writers; running the verb again can succeed. |
  | `profile-conflict` | Failure (1) | The profile moved after the live change (the I8 write order); a race. |
  | `timeout` | Failure (1) | The I5 bound ran out while doing the work. Its `op` names the port method that ran out, as `<port>.<method>` (`herdr.ensure_pane`, `harness.health`), in every implementation and fake; an adapter's own wire steps do not appear in it. |
  | `unavailable` | Failure (1) | The hub, the Herdr socket or a harness cannot be reached (also a garbled reply), or the live state a verb needs is not there after its act (#644). |
  | `store-corrupt` | Failure (1) | Stored state cannot be read back; the store fails closed. |
  | `not-implemented` | Failure (1) | The verb cannot do the work yet; every stub exits 1. |
  | `profile-drift` | Failure (1) | A finding kind, not an error a port returns; if one surfaces, live state disagrees with its spec. |
  | any other well-formed code (open, raised as `Refused`) | Refusal (3) | `Refused` is the channel for the codes a verb or adapter owns; the open codes so far (#640's `grid-unreachable`, merged; #645's and #646's, planned) are all refusals. |
  | a malformed code | Failure (1) | It cannot be trusted: the same rule turns a garbled wire reply into `unavailable`. |

  Close calls the operator may move (one arm of `class_of` and one row of its test): the three not-found codes (the legacy
  `hold` and `release` exit 1 for an unknown session), `probe-failed` and `herdr-version-unsupported` (their cause is often
  the environment), `not-implemented` (as a refusal it would move every stub to exit 3) and `profile-drift` (never an error
  today).
- `--json` on these verbs means `--format=json`, and `--json --format=text` is a usage error (#670).
- `schema_version` is an integer and is 1 now. Adding a field to the envelope or to a verb's `data` does not change it.
  Removing, renaming or retyping one does, and is a breaking change under ADR 0003's versioning (the JSON shape).
- Grid positions in `data` serialize through `GridPos`.
- **Deferred to #648:** how `roster`'s existing `--json` output and the envelope coexist (#670's format resolver reports
  whether `--format=json` was given explicitly).

### 10. Grid notation (decision 7)

`GridPos { row: u16, col: u16 }`, 1-based, defined once in `holler-pane/src/grid.rs`.

- **Accepted input:** `r<row>c<col>`, `c<col>r<row>` (labelled, either order) and a bare `<row>,<col>` (always row first,
  never column first). Upper case and surrounding ASCII whitespace are accepted; `R2C1`, `c1r2` and `2,1` are all row 2,
  column 1.
- **`grid-ambiguous`:** interior whitespace, a missing half (`r2`, `c1`), a repeated label or a mix (`r2c1c3`, `c1r2c3`), more
  than two numbers (`2,1,3`), unlabelled digits (`21`), the empty string, anything unreadable, and a JSON `pos` that
  disagrees with its `row` and `col`.
- **`grid-out-of-range`:** a zero (`r0c1`, `c0r1`, `0,1`, `r2c0`) or a number above 65535; or, from `HerdrPort::ensure_pane`,
  a cell outside its workspace's rows and columns (`r1c2` in a workspace of 2 rows by 1 column), which the `HerdrPort`
  conformance suite pins (#638 amendment 2026-10-08, grid; #683). Herdr has no grid, so a workspace's extent is the Herdr
  adapter's configuration: rows by columns per workspace label (`HerdrConfig.workspaces`, #640), which the wiring supplies
  (#649). A cell inside the extent that no single right or down split reaches is the open code `grid-unreachable` (#640).
- **Output** is always row first: text `r2c1`; JSON `{"row": 2, "col": 1, "pos": "r2c1"}`, in that key order. On input `pos`
  is optional.
- The Herdr adapter (#640) is the only code that converts a `GridPos` to Herdr's own order and base. `HerdrPort::ensure_pane`
  reaches a position by right and down splits (B4, `plan_splits`, #640) or fails loudly, and never relocates a healthy pane.
  `relaunch` moves a pane only when `--grid` is given. A pane's position comes from Herdr's snapshot, never from its name:
  `hj-c1r2` sits at `r2c1`.
- Herdr API versions (B5): the Herdr adapter checks Herdr's protocol when it connects, so no adapter exists for an unknown
  one, and `HerdrPort::version()` checks it again on every call; the other methods trust the check made at connect (#640).
  An unknown version is `herdr-version-unsupported`, and the message names the supported ones (#640, from #636's list). The
  string `version()` returns is recorded as `host.herdr_api_version` by a verb, never by the adapter (**PROPOSED**: #644's
  launch and relaunch record it), and `doctor` shows it (#647).

### 11. How attach mode (ADR 0014) relates

[ADR 0014](ADR-0014.md) stays in force, unchanged. What changes is **who chooses the session**. For a pane in the registry,
Holler creates the session of record: the pane verbs start the harness server (`HarnessPort::serve`), create the session over
its API (`create_session`) and attach the TUI to it (`attach_tui`). The body that drives that session is still not its
parent, so ADR 0014's teardown rule (point 3) and its rule against typing into a PTY (point 4, which I4 restates for pane
verbs) apply as they are. The difference is that the session id comes from `session_of_record`, which a verb writes after it
observes the session. It is no longer pasted by an operator or guessed by a repair. That answers ADR 0014's open "automatic
discovery of attachable sessions (e.g. from a Herdr pane)" for registered panes: there is no discovery; the registry names
the session. Attach mode with an operator-written `endpoint` and `session_id` stays for sessions Holler does not own (a
session with no pane record).

`HerdrPort::send_text` and `send_keys` exist in the provisional port. Under I4 no verb may use them to change which
session a pane shows or what it is doing; #640 uses them only in its tests, which type into panes they created in a scratch
Herdr session, #646 names the permitted uses, and #645's tests fail on any keystroke.

**Deferred to #649 (wiring) and #654 (cutover):** how the hub's DRIVEN session is pointed at `session_of_record` for each
registered pane, and when it moves after a switch or reset.
Until #649 wires DRIVEN, reconcile (#647) compares SHOWN with `session_of_record`, which I2 makes the session the hub
drives, and leaves `last_observed.driven` as stored.

### 12. Long-running work and the operation id (I5)

**Decided:** the hub runs no adapters (ruling 1), so it executes no long work. The CLI process that runs a verb executes
every step, and every port call is bounded by I5 (default 10 s) or ends in `timeout`. A verb that times out stops,
compensates as section 8 says, exits 1 with `timeout`, and prints the reconcile step. A crash between steps leaves state that
the next pane doctor run finds and reports (#644's acceptance). No verb leaves work running after it exits, except in the
probe runner's three documented cases, which section 1 records: a `try_wait` error, a child that escapes the probe's
process group and a missing `kill` binary (#663).

**Decided (operator, 2026-10-09): the operation id is deferred to #644, with an amendment to the contract first.** It needs two things the frozen contract
does not have: an executor that outlives the CLI process, and a place to record an operation's progress. `Pane` refuses
unknown fields and has no operation field, and `PANE_METHODS` has no operation methods. Two options are on record for #644 to choose from, after the OpenCode and Herdr spikes show real launch times:
(a) the verb starts a detached worker process of the same binary and returns an id, the worker records progress in a new
hub-held operation store (new control-socket methods beside `pane/*`), and the hub still runs no adapter; or (b) a hub-side
executor for long work only, which narrows ruling 1. Until one is chosen, I5 is satisfied by the per-call bound and the
loud `timeout`, not by an operation id.

**PROPOSED (#644, pending the operator's confirmation): no operation id yet.** Neither option is built: both need frozen
files outside #644's reach (the `Pane` record or `PANE_METHODS`, and the hub), and the spikes show that a launch is short.
The OpenCode server is healthy 630-740 ms after it is started, a TUI shows its session in about 1.6-1.7 s and a restarted
server is healthy in about 645 ms, so a launch takes about 3 s of the 10 s bound. `pane launch` and `pane relaunch` meet
I5 with a budget for the whole run (10 s from when the engine starts, checked before every live step; once it has run out
the run rolls back and exits 1 with `timeout`, whose op is `pane.launch` or `pane.relaunch`), each port call's own bound and
the reconcile step. A run takes at most the budget plus one port call's own bound plus its rollback calls. Nothing in the
code depends on the answer: on a yes a one-line edit marks this decided and drops the "Deferred" bullet, and if a measured
launch later exceeds the budget, options (a) and (b) stay on record.

**Decided (#647): no hub timer.** Under ruling 1 the hub runs no adapters, so it cannot reconcile: the periodic pass is the
CLI verb itself, which a scheduler runs as `holler pane doctor --format=json` (without `--fix`) as often as wanted, each run
recording `last_observed` and `harness.health` where they changed. The engine (`holler_pane::reconcile::reconcile`) takes
only the ports and a request, so a later daemon or `--every` loop can call it unchanged. None is built now: a pass keeps no
memory between runs, so every tick would report every standing finding again, and suppressing them needs stored state that
a later story may add.

### 13. Migration from the launcher's files

Each file below is replaced by registry state:

| File | What it held | Replaced by |
|---|---|---|
| `sessions.toml` | the session the launcher recorded for each pane | `Pane.session_of_record` |
| `last-session` | the last session a pane used | `Pane.session_of_record`, with `last_observed` for what was seen |
| `owned-sessions` | the sessions the launcher created for a pane | `session_of_record`; any other session on the pane's server is a stray-session finding from reconcile (#647) |
| `pane.env` | a pane's model, effort and environment | `Pane.model`, `Pane.env` (names only; values stay in the operator's own environment), `Pane.context`, and the spec |
| the launcher's port and directory table | each pane's port, directory and launch command | `harness.port`, `host.cwd`, `command` (an argv; a shell-string command is a finding and is imported without a command) |

The hub's own registration, the fifth record of the incident, is replaced by `session_of_record` through the wiring of #649.

The order:

1. `pane import --from <state-root> --dry-run` (#650) reports every disagreement between these files and what Herdr, tmux
   and the harness show, and writes nothing.
2. The real run writes one record per pane. It sets `session_of_record` only where the sources agree and the session exists;
   otherwise the record has none and the report has a finding. It takes each position from Herdr's snapshot, never from the
   name. It records model, effort, env names and ceilings (C1), creates the profile `fleet` with one spec per imported pane, and
   sets each pane's `profile` to `fleet`. It deletes nothing from the source files.
3. The operator cuts over (#654): from then on only pane verbs change panes, and the launcher's files are no longer read.
   Retiring the launcher's writers is pfleet's follow-up (#653), not Holler's. After seven days on the live fleet (#654) the
   operator recreates the Herdr workspace from the stored profiles (#666) and watches it for 24 hours (C4).

## Why

One registry, written only by compare-and-swap and read by every verb, removes the condition behind every 2026-10-07
incident: several records that each claimed to know the session. Running the verbs CLI-side keeps the hub a store that never
blocks on Herdr, tmux or a harness, and lets every story code against traits and fakes in parallel. Kebab-case codes in a
result, not wire error frames, keep protocol v2's closed catalog and golden files unchanged. Failing closed on a corrupt
registry, rather than starting empty, follows from records that gate every verb: an empty registry would look like a fleet
with no panes.

## Consequences

- Protocol v2 is unchanged: no row is added to §4, no error to §8, and no golden file changes. [Protocol v2](../protocol/v2.md)
  §11 notes, without rules, that the `pane/*` and `profile/*` control-socket methods exist and are specified here.
- The control socket has two refusal conventions: `control/*` methods answer a refusal with a JSON-RPC error and a
  `data.reason`, and `pane/*` and `profile/*` answer with a `PaneReply` result. A client must tell them apart by method family.
- `holler-cli` takes on the adapter dependencies, so tests that drive the CLI use the test kit's fakes, never a real Herdr,
  tmux or OpenCode, and refuse real session names.
- The CLI's JSON output for pane and profile verbs becomes a versioned contract (`schema_version`); a change to its shape is
  a breaking change under ADR 0003.
- Two hub state files are added (`panes.json`, `profiles.json`). Their corruption stops the pane and profile verbs until the
  operator repairs the file, and nothing else in the hub.

## Decisions taken

Taken by the operator on 2026-10-09, one at a time, after this ADR was drafted.

1. **The I8 compensation (section 8): the epic's order stays.** The profile is written first. A failed act restores the
   profile's specs by a second write, so the specs equal what they were but the generation has moved by two and the log
   shows the edit and its reversal. The acceptance of #663 and the conformance case in #638 are amended from "generation
   equal" to "specs equal".
2. **`pane-in-other-profile` runs inside the pane registry's compare-and-swap (section 8).** It needs only the stored pane
   record, so it runs under the pane lock where that record is at hand, and no writer can slip in between the check and the
   write. `check_membership` (#669) keeps the check that the named profile exists. #661 makes this one-line change in the
   registry code #639 creates, and #661's blast radius is widened to allow it.
3. **The operation id is deferred to #644 (section 12).** Until then I5 is satisfied by the per-call bound and the loud
   `timeout`.
4. **`profile rename`, `export`, `import`, the `profile/rename` method, `ProfileStore::rename` and the `profile-drift`
   finding (#665) stay PROPOSED** until wave 4. Nothing required depends on them.
5. **Refusals exit 3 (section 9), not 1.** This amends the epic's output contract. #670 is not merged yet and its output
   module maps every error to exit 1, so a change follows it (done in
   [#676](https://github.com/Performant-Labs/holler/issues/676)); the epic, #638's envelope helper (it checks `ok` against
   the exit code) and every verb story that asserts exit codes are amended to match.
6. **Issue #22**, the slot reserved for this ADR, is retitled to match it after this ADR merges.
7. **The idle `pane/watch` cursor is the head** (operator, 2026-10-09, #639). Section 6 is amended to match.

Items still open and owned by a named story are listed under "Deferred to named stories" above.
