# ADR 0004 — Holler protocol v2 is JSON-RPC 2.0 over WebSocket

**Status:** accepted
**Issue:** [#5](https://github.com/Performant-Labs/holler/issues/5)
**Date:** 2026-09-07
**Depends on:** [ADR 0001](ADR-0001.md)
**Supersedes:** server ADR-0009 (envelope), server ADR-0015 (join frame)
**Executes:** [holler-server#319](https://github.com/Performant-Labs/holler-server/issues/319)

## Decision

Holler protocol v2 is **JSON-RPC 2.0 over WebSocket text frames**. Both hops in the herd — the **circuit** (body ↔ hub) and the **body** (hub ↔ local agent) — speak the same JSON-RPC shape, mirroring [ACP](https://agentclientprotocol.com/), which is already JSON-RPC 2.0 over stdio/WebSocket. This keeps the two hops grammatically identical so the hub can act as a pass-through bridge, and it retires the bespoke v1 envelope `{v, type, id, ts, from, body}`.

The rules below are **normative**; the concrete method catalog, frame examples, and the error-code table live in `docs/protocol/v2.md`, which is the canonical protocol document and **matches this ADR exactly**.

### Transport and framing

- **WebSocket text frames only.** One JSON-RPC 2.0 **message per text frame** — a request, a response, or a notification. No binary frames, no multi-message batching.
- **No batches in v2.** A JSON **array** at the top level (a JSON-RPC batch) is **rejected with `-32600` Invalid Request** and the socket is closed. Batching is deferred; if it is ever needed it lands as a protocol **version bump**, not a v2 addition.
- **Codec ownership.** `holler-proto` owns the codec: it is the single place that parses a frame into a typed `JsonRpc` message and serializes one back. The wire selftest and the codec tests **reject anything that is not exactly one JSON-RPC 2.0 object per frame**.

### Peers, ids, and correlation

- **Both peers are clients and servers on the same socket** (as in ACP): each side issues requests and each side answers them. A single WebSocket carries interleaved requests and responses in both directions.
- **Requests carry an `id`; notifications carry none.** This is the JSON-RPC discriminator — the presence/absence of `id` is what separates a request (expects a response) from a notification (fire-and-forget).
- **`id` is a string ULID.** Ids are minted with a directional prefix so they never collide: **`h-<ULID>`** when minted by the **hub**, **`b-<ULID>`** when minted by the **body**. (ULIDs are already time-ordered and random per the JSON-RPC 2.0 id rules; the prefix is Holler's add-on for direction and debuggability.)
- **Request/response correlation replaces v1's `id` reuse.** v1 identified a message by reusing an `id` field across unrelated frame types; v2 correlates strictly by JSON-RPC `id`. A response's `id` equals the `id` of the request it answers.

### Field migrations from v1

- **`ts` moves into `params.ts`.** v1's top-level `ts` becomes an **optional** field on the request's `params` object. It records **emission time** and is **RFC 3339**. It is not a correlation token — correlation is `id`.
- **v1's `from` is dropped.** There is no sender field on the v2 wire. **Identity is the authenticated connection**: the hub already knows which body a socket belongs to (join + credential), so a `from` field was redundant and is removed.

### Version negotiation

- The **`circuit/hello`** request's params carry `protocol: 2` plus `protocol_min` and `protocol_max` — the **same three fields v1's hello carried**.
- A peer that cannot speak v2 (its accepted range excludes 2) gets error **`-32000` `unsupported_version`** and the **socket is closed**.
- **No silent downgrade.** The hub never falls back to v1 on a live connection; an incompatible peer is refused and disconnected, not quietly bridged onto the old envelope.

### Streaming and cancellation (the ACP shape, verbatim)

- A **`session/prompt`** request produces **zero or more `session/update` notifications** and then **exactly one response** — `{stopReason}` — when the turn ends. This is ACP's streaming shape carried over unchanged.
- **Cancellation** is a **`session/cancel`** request. It is answered by a **response when the cancellation is applied** — and **that response is the acknowledgement** the interruption path wanted (the ack that was pending under ADR-0005/#59). Interrupt remains **control, not a message**: it does not add a turn, and the session survives.

### Errors

- **JSON-RPC error objects**, in the response's `error` member: `{code, message, data?}`.
- **Standard JSON-RPC codes** are used for framing and protocol-shape failures: `-32700` Parse error, `-32600` Invalid Request, `-32601` Method not found, `-32602` Invalid params, `-32603` Internal error.
- **Application codes** are reserved **`-32000`..`-32099`**. Each carries the **Holler string** in `error.data.code` (e.g. `-32000` → `unsupported_version`). The full code↔string table lives in `docs/protocol/v2.md`; this ADR fixes the range and the convention, not the individual rows.

## Relationship to A2A and ACP (normative)

The v2 object model is not invented here — it is **reused verbatim** from the two protocols it sits between.

- **A2A 1.0** (https://a2a-protocol.org/latest/specification/) is the **guiding semantic document**, pinned to **A2A v1.0.1** (tag `v1.0.1`, published 2026-05-28; v1.0.0 was 2026-03-12). That pin is recorded in `docs/protocol/README.md`. Holler v2 reuses A2A's object model **on the inward wire**:
  - `Message { role, parts, metadata? }`
  - `Part` — **member-name discriminated**: `text` \| `raw` \| `url` \| `data`, each optionally carrying `metadata`
  - A2A's **task-state vocabulary** wherever a state is exposed: `working`, `input-required`, `completed`, `canceled`, `failed`, `rejected`.
  - Holler **adds `idle`** for a session with no active task, because A2A states are **per task** whereas Holler presence is **per session**. A session between turns is `idle`, not `completed`.
- **ACP v2** is the **body hop**. Inward method names **mirror ACP** — `session/prompt`, `session/update`, `session/cancel` — because the body's driver maps them **1:1**. **ACP's `stopReason` is the source of truth**; the **A2A terminal state is derived from it at the body**, so the bridge is a **pass-through**:
  | ACP `stopReason` | → A2A terminal state |
  |---|---|
  | `end_turn` | `completed` |
  | `cancelled` | `canceled` |
  | `error` | `failed` |
  | `refusal` | `rejected` |
  | `max_tokens` \| `max_turn_requests` | `failed` (with a reason) |
  | `limit` | `failed` |
- **What Holler does *not* take from A2A:** the HTTP client→server transport, one reachable endpoint per agent, push-notification webhooks, and agent cards on the inward wire. Those assume **reachability the body does not have** — a body sits behind NAT, not on a public endpoint. Those A2A conveniences live **only at the hub's outward face** (ADR 0017), never on the inward body wire.
- **Consequence:** a body **never learns a vocabulary of its own**. A `Part` on the body wire is **byte-identical** to the `Part` an A2A client receives from the hub. The body speaks ACP in and A2A-compatible objects out, with no translation layer of its own.

## Why

Every neighbouring hop is **JSON-RPC** — ACP on the body, A2A at the bridge, MCP nearby. A bespoke envelope **taxed every boundary**: each hop needed its own serializer, its own correlation, its own notion of "this is a reply and not a new message," and its own error shape. By adopting JSON-RPC 2.0, **correlation, notification-vs-request, and error objects come specified** — not reinvented. And because the body hop is ACP and the bridge is A2A, both already JSON-RPC, **the A2A bridge becomes method mapping, not envelope transcoding**: the hub forwards A2A-shaped messages to a body that speaks the same grammar, instead of converting between two private formats.

## Consequences

- **`holler-proto` owns the codec.** It is the single parse/serialize boundary; no other crate hand-rolls frame handling.
- **`docs/protocol/v2.md` is canonical**; **`docs/protocol/v1.md` is not ported**. v1 is retired, not migrated — the v2 spec is written fresh against this ADR.
- **The wire selftest and the codec tests** reject any frame that is not exactly one JSON-RPC 2.0 object (batch arrays included), so the framing rule is enforced at the codec, not just documented.
- **Prior art, not borrowed code.** NATS **leaf nodes** and **CI runner agents** are cited (from [holler-server#319](https://github.com/Performant-Labs/holler-server/issues/319)) as prior art for the **outbound-worker pattern** — a hub that dials out to workers rather than waiting to be reached. Their relevance is conceptual (the pattern); **no code is borrowed** from either.
