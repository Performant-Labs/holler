# ADR 0009 — Interrupt is `session/cancel`; the session survives; the response is the ack

**Status:** accepted
**Issue:** [#10](https://github.com/Performant-Labs/holler/issues/10)
**Date:** 2026-09-09
**Depends on:** [ADR 0004](ADR-0004.md), [ADR 0005](ADR-0005.md)
**Supersedes:** `holler-server` ADR-0005 (interrupt is a control frame; the session survives)
**Executes:** [#150](https://github.com/Performant-Labs/holler/issues/150) (busy-turn policy, landed) · [#191](https://github.com/Performant-Labs/holler/issues/191) (interrupt implementation, in progress concurrently with this ADR)

## Decision

`holler interrupt` is still not a prompt — that half of `holler-server` ADR-0005 survives unchanged: the session stays, only the in-flight turn stops, and a later `session/prompt` to the same session must succeed. What this ADR adds, on top of the v2 JSON-RPC wire (ADR 0004), is the piece v1 never had: **the response to the cancel request is itself the acknowledgement**, and a `say` against a busy session fails closed instead of queueing silently.

1. **`session/cancel` is a JSON-RPC request, not a notification.** It is answered by a response — `{applied: true}` — sent **only after** the body's driver has observed the turn actually stop (ACP `stopReason: cancelled`, or a force-kill). Cancelling an already-idle session responds `{applied: true}` immediately as a no-op, never an error. This *is* the "applied-ack" the old fire-and-forget control frame never carried: v1 sent interrupt and hoped; v2 waits for confirmation that the turn is actually gone before telling the operator it worked.
2. **Priority path.** The connection task keeps a separate high-priority outbound channel for `session/cancel`, so a cancel is never stuck behind a large `session/update` flush or another queued prompt. Interrupt has to win a race against exactly the kind of traffic it exists to cut off.
3. **RTT-scaled ack timeout, distinct from liveness.** The hub waits for `{applied: true}` for `max(2s, 10 × last measured circuit/ping RTT)`. Timing out does not mean the body is dead — heartbeats are a separate signal (ADR 0010) — it means `interrupt sent but not confirmed within Ns (body may be stalled); the session is still on the roster`, exit 1. A confirmed cancel prints `interrupted <session>`, exit 0.
4. **`say` refuses a busy session; it does not queue by default.** v1's busy-turn policy silently queued a `say` behind whatever turn was already running, and the caller learned nothing until a 600s timeout. v2 fails closed instead: `say SESSION TEXT` against a `working` or `stalled` session (the roster's derived display state, ADR 0010) returns error `-32009 session_busy` with `data: {state, turn_age_ms, last_update_age_ms}`, unless the caller opts in with `--queue`. An orchestrator cannot see a silent queue the way a human typing follow-ups can tolerate one; refusing with the turn's age is the actionable signal, not a bare "busy."
5. **`interrupt SESSION TEXT` is the atomic redirect.** This is the one new verb form: cancel, await `{applied: true}` **and** the in-flight prompt's own response (`stopReason: cancelled`), then send `session/prompt {session, message: TEXT, replace: true}` and stream its reply exactly as a plain `say` does — one atomic operator action, so a redirect can never be lost behind a stuck turn waiting on a second round-trip. `interrupt SESSION` with no `TEXT` is just the cancel from point 1; the sibling `say` that was in flight for that session (if any) receives `stopReason: cancelled` and exits 1 with `prompt was interrupted before it completed` — its own hub connection is untouched, and any concurrent `say` to a different session is unaffected.

## Why

The failure this ADR closes is concrete, not hypothetical: an orchestrator redirected a stuck session with `say`, and v0.1.0's busy-turn policy queued the new prompt behind the stuck one without telling the caller anything until the full timeout elapsed. The fix keeps `holler-server` ADR-0005's original insight — interrupt is control, not SSH `SIGINT`, and the session must remain promptable afterward — but adds what a JSON-RPC request/response pair gives for free that a bare control frame never could: a caller-visible confirmation that the cancel was *applied*, not merely *sent*. Refusing a busy `say` by default, rather than queueing, follows the same logic: a human tolerates a queue because they can see it; an orchestrator issuing commands programmatically cannot, and a model mid-turn will not remember to interrupt-then-say on its own.

## Consequences

- `crates/holler-proto` carries error `-32009 session_busy` in the application range ADR 0004 reserves, plus `turn_started_at`/`last_update_at` on presence so the roster and the busy error can both report turn age without a separate query.
- The hub's connection task (`crates/holler-hub/src/circuit.rs`) keeps `session/cancel` on a dedicated priority channel, verified by a test that a cancel confirms in under a second even behind a multi-thousand-chunk `session/update` flush.
- `crates/holler-cli`'s `say` checks the roster before sending and fails closed on `working`/`stalled` unless `--queue` is passed; `interrupt SESSION TEXT` is implemented as the atomic sequence in point 5, not as two separate CLI invocations glued together by the operator.
- `docs/protocol/talk.md` carries the request/response sequence diagram for both the plain cancel and the redirect form.

## Not decided here

- The roster's `stalled` display state and the periodic presence that drives turn-age visibility — [ADR 0010](ADR-0010.md).
- Session addressing (`SESSION` resolution, ambiguity handling) — [ADR 0005](ADR-0005.md).
- `answer SESSION CHOICE` for resolving a held `input-required` prompt — a separate wire vocabulary (issue [#151](https://github.com/Performant-Labs/holler/issues/151)), not part of this ADR.
