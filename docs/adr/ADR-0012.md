# ADR 0012 — Bodies are config + a subprocess (or an attached endpoint), never plugins

**Status:** accepted
**Issue:** [#13](https://github.com/Performant-Labs/holler/issues/13)
**Date:** 2026-09-09
**Depends on:** [ADR 0001](ADR-0001.md), [ADR 0013](ADR-0013.md)
**Supersedes:** `holler-server` ADR-0011 (new harnesses are config, not Holler releases), `holler-client` ADR-0002 (bodies are config + ACP subprocess, not plugins)

## Decision

Adding a new coding-agent harness to Holler is a **config row**, never an in-process plugin and never a reason to cut a release. This repo does not implement a plugin API (no `dlopen`, no Go-style plugins, no npm-style dynamic `require`), and it does not vendor a harness-specific SDK per harness. Both legacy repos already reached this decision on their own halves of the split (`holler-server` for the circuit, `holler-client` for the subprocess); this ADR restates it as one rule for the single binary, and extends it to cover the second body transport this repo now has.

1. **A body config row now has two shapes, not one.** v1's only shape was **spawn**: a config row names a harness id, a `command` argv, and an optional interrupt override, and the body execs that command as an ACP subprocess (ADR 0013) it fully owns. This repo adds **attach**: a config row instead names an `endpoint` and an existing `session_id`, and the body drives that already-running session over its control surface without ever spawning or `session/new`-ing it. Both shapes are still config, not code — see [ADR 0014](ADR-0014.md) for attach's own rules (ownership, teardown, the presence fields it adds).
2. **`holler body support <id>` answers "can this box run the configured command / reach the configured endpoint," never "did we compile this harness in."** There is no compiled-in enum of supported harnesses; an unrecognized harness id is legal on the wire and in config, and support is a runtime probe (PATH lookup for spawn, a reachability check for attach), not a lookup against a fixed list.
3. **Out-of-tree adapters remain the escape hatch for a harness that does not speak ACP.** If a harness needs translation, that translation is someone else's binary on `command` (or behind an attach `endpoint`) — a separate repo with its own release cadence — never code `dlopen`ed into the Holler process. Holler only ever `exec`s a command or dials an HTTP endpoint; it never loads a harness's code into its own address space.
4. **Adding a harness that already speaks ACP costs zero Holler code changes and zero Holler releases.** A user adds a `[[session]]` block naming the new command (spawn) or endpoint (attach); nothing in `holler-body` or `holler-cli` changes.

## Why

The alternative approaches all cost a solo-maintained project more than the harness landscape is worth chasing: releasing on every vendor CLI drift means owning every vendor's compatibility forever; an in-process plugin API means owning a public ABI and other people's crashes inside your own process; a server-side (hub-side) adapter would mean the hub knows about bodies, which ADR 0001 already forbids. ACP is already the extension point every harness that matters is converging on, so treating "speaks ACP" as the only requirement for a config row — rather than building a second extension mechanism on top of it — keeps the one extension point that already exists as the only one. Attach exists for the same underlying reason spawn does — "config, not code" — applied to the case where the harness process is already running under something else (a terminal multiplexer, an operator's own session) and Holler should drive it, not own it.

## Consequences

- `SessionConfig` (in whichever crate owns body configuration) carries a `mode` discriminating spawn vs attach, with `command` meaningful only under spawn and `endpoint`/`session_id` meaningful only under attach; the two shapes share the harness id and interrupt-override fields.
- `holler-body`'s harness ids remain plain strings end to end — no `enum Harness { OpenCode, Claude, … }` anywhere in the wire or config types — because a compiled-in enum is exactly the "Holler release per harness" cost this ADR refuses to pay.
- Checking a harness off as supported is a docs/gate exercise (a config snippet exists, `holler body support <id>` returns true, the relevant gate test was run), never a version bump.
- Convenience tooling that *writes* a config row for a harness found on `PATH` (e.g. a future `holler body add <harness>`) is sugar over this same config surface, not a second mechanism.

## Not decided here

- The body protocol itself (ACP version, SDK, why Rust) — [ADR 0013](ADR-0013.md).
- Attach mode's specific rules — who owns teardown, what presence carries, what "attach" means for `detach`/exit — [ADR 0014](ADR-0014.md).
- Any future harness-discovery or registry mechanism; v1 config is an argv or an endpoint URL, not a fetch from a registry.
