**Verdict:** PASS

## Summary

PASS. The plan builds the registry inside `panes/**` from objects that already exist:

- `write_atomic` writes the file.
- `next_generation` is the CAS.
- `decode_params` and the `reply.rs` params structs decode requests.
- `PaneReply` goes out through `reply_line`.
- The store code is synchronous behind `spawn_blocking`, and a `JoinError` fails closed, as in `token.rs:721-799`.

The plan departs from the analogous `holds.rs` in three ways: it fails closed instead of moving the file aside, it refuses a write it cannot save instead of keeping it in memory, and it holds one lock across the save. The brief justifies each one in writing (D3, D4, D1), and the draft ADR-0021 §7 ratifies them. They are deliberate decisions, not drift. There are no block findings.

I am not blocking on size: the work is 5 production files in one module and one component family. F's ~6-file cap is at its edge (5 files plus CHANGELOG). The warns that matter most for the next phases:

- **W-1:** call `check_membership` inside the blocking closure.
- **W-2:** move the #669 test helpers; do not copy them.
- **W-9:** the radius needs a test-file split approved before T starts.

Otherwise the plan is consistent with existing patterns. I verified each of the following against the code.

- **Lock order.** It matches ADR-0021 §7: the profile lock is taken before the pane lock, and the pane registry never calls into the profile registry under its own lock.
