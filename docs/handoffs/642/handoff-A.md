# Handoff-A: Phase 3 - #642 the OpenCode adapter (`HarnessPort` over OpenCode's HTTP API and a tmux-hosted TUI)  (up-front plan review)

**Date:** 2026-10-09
**Branch:** issue-642-implementation (at 53237d4, the brief commit on 9d61c9f)
**Brief reviewed:** docs/handoffs/642-brief.md   **Reuse map:** docs/handoffs/642-brief.md, "Reuse map (extend, do not duplicate)" (lines 502-529)   **Wireframe:** N/A (no UI surface)
**Verdict:** BLOCK

## Summary

BLOCK on two findings. Both need brief amendments, and neither needs a redesign. Most of the plan picks the right
objects: it implements the frozen `HarnessPort` unchanged and runs the merged conformance suite as is. It mirrors
`FakeHarness`'s `op` strings and error shapes without depending on the test kit at runtime, depends only on `holler-pane`
and existing workspace crates, and justifies every new object in writing.

The two blocks:

- **B-1:** the brief forbids any ADR-0021 edit, although the ADR defers `HarnessPort`'s final form to this story by name.
  The brief's own decisions also change what the verb stories built on the fake can rely on. The epic's established
  practice (#639, #676, #692, and the sibling #640 brief) is to update ADR-0021 in the same change.
- **B-2:** the `tui_target` resolver passes a bare tmux target to `respawn-pane -k` and to the title read. tmux prefix
  matching can then make `attach_tui` kill and observe another pane's TUI. The brief also leaves tmux target syntax to
  holler-cli's wiring.

W-1 is the warn the MO should settle in the same amendment: as the two plans stand, nothing stops the OpenCode server
that `serve` starts.

### Checked and consistent with existing patterns (no finding)

- **Object choice.** `HarnessPort`, `PaneError`, the closed codes, `run_harness_conformance` and `HarnessRig` are reused
  unchanged. `FakeHarness` is the right behavioural reference. The `op` strings are mirrored as constants with no runtime
  dependency on the test kit, and AC 7, 8 and 15 pin them as equal (the same approach as #641's `HostOp` row).
- **Dependency direction.** The crate depends on `holler-pane`, `serde_json` and `httparse` only, with no adapter, hub or
  body dependency (ADR-0021 §5). `holler-cli` stays the only place that wires adapters.
- **The HTTP client.** The hand-rolled blocking client is justified. The only OpenCode clients are async and live in
  `holler-body`. Enabling `reqwest`'s `blocking` feature would change a shared dependency's features for `holler-cli` and
  `holler-body`, and would hide the difference between "refused" and "connected but silent". Each adapter owning its own
  transport with per-method deadlines matches the #640 plan, which follows `control::send_over` without importing it.
  `httparse` is reused, not added.
- **The stub server.** A new stub HTTP server is justified: both existing fake OpenCode servers are tokio-based and private
  to other crates' test trees.
- **The `serve` process model.** The server gets its own process group, its pgid equals the returned pid, it runs without
  `unsafe`, and it outlives the CLI. This is the spike's recommendation 1, and the right shape for a stop by recorded pid
  (W-1).
- **Invariants.** I2 and I3: a switch counts only once the title confirms it, never on the server's `200 true`. I4: no
  keystrokes are sent. I6: the TUI's port is observed from tmux, not remembered.
- **Files, size and the changelog.** All files are planned under 600 lines, with named fallbacks. The `CHANGELOG.md` entry
  outside the issue's radius matches every #638 slice and the #640 and #641 briefs.
- **Real-OpenCode tests.** They are opt-in, use scratch dirs only, use ports 48100-48199 only, run on a private tmux
  server, and leave the default socket alone.
- **Logging.** None is planned, which is consistent with the #640 and #641 plans; no adapter logs today.
